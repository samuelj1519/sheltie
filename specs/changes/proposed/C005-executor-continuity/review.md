# C005 方向评估

结论：建议起草“执行者替换与任务接续”，分两阶段采用。第一阶段（人工接续）可以随 v0.3 交付；第二阶段（自动接续）等第一阶段的实验结果再决定。本文件记录方向讨论的依据。它不是实现后的独立 review。

基准：`296313c6f9fcfd0d6348927b73e7a49578581b6c`。日期：2026-09-27。参与者：用户、Claude Code，以及外部讨论者的书面意见。本 package 从 C004 讨论的第八至十一轮拆出，前七轮见 [C004 review](../C004-verifiable-delegation/review.md)。

## 1. 起点

用户补充了最初的需求：严格任务中，模型可能偷懒甚至作恶，希望由独立 agent 协调流程和审查，并给 agent 隔离的工作环境；必须支持全程一个 agent；简单部分交给更便宜的模型以节省 token；订阅有 5 小时和每周额度，需要为节点准备备选 agent。

## 2. 为什么从 C004 拆出

- C004 回答“这份候选凭什么接收”，C005 回答“接下来由谁、在什么条件下继续”，依赖关系不同：人工接续主要依赖外置状态；可信自动接收依赖 C004；自动切换还需要执行驱动和资源观测。
- 把审查语义、等待状态、执行代次、跨宿主接续和新实验全部放进 C004，会让一次验证变成大规模开发。
- 提案按语义责任划分，版本按已完成的可用闭环组织：C005 第一阶段不必因为编号而等到 v0.4。

## 3. 收敛的结论

1. **共同基础。** 更换执行者，不得自动放宽任务标准、权限范围和证据要求；最终接收依据来自预先授权的验证机制，不能仅凭执行者自报。执行者可以替换，已登记的审查发现不因替换而消失。
2. **接续分三级。** 人工、辅助、自动，承诺各不相同。skill 和状态卡只能做到“可接续”；自动接替必须有一个仍在运行、模型之外的主体。
3. **额度池。** 共用同一额度池的备选没有意义；同一 Claude 账号下的各种入口共享计划用量。
4. **失败分类。** 资源不可用、候选未通过验收、执行环境故障、权限或数据政策不允许、原因未知，五类分开处理；原因来源分提供方通道、宿主通道、人工报告和模型自报。
5. **分开计数。** 资源不可用不消耗业务重试；资源重试、切换次数和总等待期限各有上限，防止自报“不可用”造成无限重试。
6. **执行代次。** 旧代次的迟到提交拒收；这只保护经过引擎接口的提交，不停止旧进程。
7. **可恢复等待。** GF-14 当前只允许非门槛阻塞后取消，需要正式修改。到达重置时间不等于已恢复。
8. **执行配置与执行记录分开。** 配置保存用户选择与政策，记录保存观测；政策可以在派发时强制，能力在没有观测前只是声明，权限保证需要执行后端。
9. **身份来源不只驱动层。** 外部受信平台也能提供执行来源；驱动层只能证明“按某配置发起了执行”，请求配置、实际配置和会话身份要分开记录。驱动层单独不构成隔离。
10. **标准不随换人降低。** 合同要求独立审查时，额度不足不降级为作者自审。
11. **成本。** token 数不等于付费，也不等于订阅额度占用。便宜模型的级联成本可以写成 \(E = C_l + H + p(C_s + R)\)，划算条件是 \(p < (C_s - C_l - H)/(C_s + R)\)，但必须同时满足质量约束：漏检会让账面成本显得更低。
12. **收尾额度保留**只是内部分配策略，提供方不支持真正的预留。
13. **隔离随承诺触发**，不固定排在某个版本；协调者与 worker 使用同类模型时，不能一边假设 worker 会违规，一边默认协调者永远可信。

## 4. 讨论中纠正的错误

- 说“引擎观测不到额度，只能听协调者报告”，过于绝对：Codex app-server 和 Claude Code 状态栏都提供官方观测来源；
- 说“Claude 侧没有额度观测来源”，错误：状态栏输入含 `rate_limits`；
- 说“手动接续解释成本接近零时，驱动层的增量只剩无人值守”，低估了无人响应等待的损失；
- 把“只有 Opus 限额耗尽后换 Sonnet 才能立刻继续”当作规则，来源是二手博客，不写入设计；
- 把 Codex 的额度窗口当作固定的两个窗口，实际字段可以缺失，`secondary` 可能为空；
- 说“驱动层不带来任何安全提升”，过于绝对；改为“单独不构成隔离，执行记录可作为分离规则的输入”。

## 5. 被否决的方向

| 方向 | 否决原因 |
| --- | --- |
| 只靠 skill 和状态卡实现自动接替 | 协调者停住后没有主体启动后来者 |
| 引擎内置调度器 | 内核出现宿主词汇（GF-01），引擎从记状态变成做选择 |
| 常驻会话池、多 CLI 适配器农场 | 与 spec §6 的目的冲突；只接入少量经过验证的入口 |
| 用模型名或 `cheap / strong` 档位描述执行者 | 表达不了能力、政策、参与关系和额度池 |
| 把“是否参与过实现”写在配置里 | 必须从账本推导 |
| 额度缺失按零或按充足处理 | 两种都会导致错误切换 |
| 等“手动换工具成为高频抱怨”才研究驱动层 | 用户已明确提出离线推进需求；启动条件改为交接质量稳定 |
