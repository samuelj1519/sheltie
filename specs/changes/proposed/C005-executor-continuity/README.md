# C005：执行者替换与任务接续

状态：`proposed`
目标版本：`待定`（第一阶段候选随 v0.3.0，第二阶段待定）
兼容性：`待定`（第一阶段修改 GF-14 的阻塞语义，候选 minor）
基线：`296313c6f9fcfd0d6348927b73e7a49578581b6c`
Owner：`待采用时指定`
权威性：未采用；不得据此修改产品代码、根规格或决定记录

## 范围约束

**第一阶段验证的是：用户换一个宿主后，能否在不降低标准、不重新解释整段任务的前提下，继续同一个 Work。**

**第二阶段验证的是：用户不在场时，一个模型之外的驱动能否在预授权范围内等待、切换或暂停，并减少无人响应的等待。**

两个阶段分别采用。第二阶段的启动条件见下文“采用条件”。

**共同基础（与 C004 共用）：** 更换执行者，不得自动放宽任务标准、权限范围和证据要求；最终接收依据来自预先授权的验证机制，不能仅凭执行者自报。执行者可以替换，已登记的审查发现不因替换而消失。

本 package 回答“接下来由谁、在什么条件下继续”；“这份候选凭什么接收”由 [C004](../C004-verifiable-delegation/README.md) 负责。两者共用 Work、Attempt、候选快照、执行引用和证据记录，不另建进度系统。

## 要解决的问题

用户提出的实际需求：

1. 订阅有 5 小时和每周额度。某个节点的执行者额度耗尽时，需要备选执行者接手；
2. 额度耗尽的可能是协调者自己。此时它连“记录原因、选择备选、发起交接”都可能来不及做；
3. 严格任务需要独立审查者；审查者也会耗尽额度，不能因此把审查降级为作者自审；
4. 简单部分交给更便宜的模型，前提是总投入确实下降、质量不变差；
5. 必须支持全程只用一个 agent。

宿主原生机制只覆盖其中一部分，C005 以它们为对照基准，而不是假定它们不存在：

- Claude Code 的 `fallbackModel` 不在额度、计费或认证错误时切换；
- Claude Code 交互式会话在额度恢复后可以自动继续；动态 workflow（v2.1.271 起）碰到额度上限时暂停、恢复后继续。条件是：交互式会话、claude.ai 订阅登录、打开 `autoContinueAtUsageLimit`、额度在 24 小时内恢复、同一个 run 最多等两次。`-p`、Agent SDK、后台会话、Remote Control 和 agent team 队员会话不暂停，直接失败；
- workflow 只能在同一会话内恢复，或用 `--resume` 回到原会话后重新启动；中途失败的 agent 之后启动的所有 agent 都会重跑；运行中不接受人工输入，需要人签字的阶段只能拆成多个 workflow。

C005 的增量只在这些条件之外：非交互运行、周额度、跨宿主替换、协调者自己停住、中间有人工门槛的长任务。事实核查见 [review.md](review.md)。

现在换宿主继续工作，靠的是用户手动复制背景、重新解释约束。GF-14 规定非门槛原因的 `blocked` 只能取消，所以“等额度恢复后继续”也没有合法表达。

## 首批用户

与 C004 相同：个人开发者的本地 Git 仓库。另外，用户至少拥有两个宿主的可用订阅（例如 Claude Code 和 Codex）。只有一个宿主时，第一阶段仍提供“正确等待与恢复”。

## 成功判据

采用前（proposal 阶段）：

- [validation.md](validation.md) 第一阶段的人工接续实验已执行，按预先写定的口径分别报告：现有交接材料是否够用、重新解释量、约束丢失、重做量、响应等待和端到端时间；
- 若换宿主仍需大量重新解释，先改交接包，不进入第二阶段。

采用后（第一阶段）：

- 换宿主继续同一个 Work 时，旧的运行中 Attempt 被取代（记为 `superseded`，不消耗业务重试），新执行者领取新的 Attempt；被取代的 Attempt 通过引擎接口的迟到提交被拒绝；
- 资源不可用时，Work 可以进入可恢复的等待；等待按来源显示，模型自报显示为“暂停，未核实”；恢复需要新的观测或获准的实际尝试确认；
- 资源不可用不消耗业务重试次数；资源重试、切换次数和总等待期限各有上限，耗尽后停下来找人；
- 合同要求独立审查时，额度不足不会让审查降级为作者自审；没有合格备选时等待或找人（独立性判定随 C004 VD-10 启用）；
- 单 agent 全程执行仍被完整支持。

采用后（第二阶段）：

- 切换只在 Work 冻结的执行绑定内进行；新增候选或转入付费形成新的授权版本，原记录保留；
- 驱动层只执行引擎返回、且冻结的自动执行政策允许的操作；机器检查和 agent 审查可以自动执行，人工批准从不由系统生成；
- 其余细节采用第二阶段时细化。

## 不做什么

- 不建常驻会话池，不做多个 coding CLI 的适配器农场，不另建 Work 数据库；
- 不负责模型内部的工具循环、上下文压缩或会话运行时；
- 不接触、不保存账户 token；驱动层只调用官方认证过的入口；
- 不借换宿主绕过权限或数据政策，不悄悄转入 API 付费；
- 不承诺额度一定可用；“给收尾保留强模型额度”只是 Sheltie 内部的分配策略；
- 第一阶段不做按成本自动路由、不做级联升级，只允许用户按固定配置分工；
- skill 只教宿主调用 CLI，不保存状态、不做推进判断（GF-18）；
- 不宣称驱动层提供隔离或安全保证。

## 采用条件

第一阶段：

- C002 已完成，至少恢复闭合（GF-15 相关修复）已落地；
- validation.md 第一阶段的人工接续实验已执行；
- 人决定 GF-14 的修改方案（可恢复等待）；
- 与 C004 的共用接口（候选快照、执行引用、证据记录）已定稿；
- 仓库默认只允许一个 active change。v0.3 的顺序是 C002 → C004 → C005 第一阶段，逐个进入 active；也可以根据两份实验结果把 C005 第一阶段排在 C004 前面。
- 排在 C004 前面时，第一阶段承诺收窄为：状态卡、产物指针、冻结的 Workbook、取代运行中的 Attempt、资源等待与分开计数。交接包的验证结果与未处置发现字段、EX-07 的独立性判定、首批场景 2 和 4，在 C004 采用并实现后作为增量启用；期间不另建发现账本或身份记录。

第二阶段：

- 第一阶段交接质量稳定：换宿主后没有关键约束丢失；
- 实测中存在明显的无人响应等待，且它是接续的主要成本。用户已提出离线推进的需求，作为立项动机记录，但单凭这一需求不满足本条；
- 人审定 [design.md](design.md) 的 ADR-C（执行接入边界），并修订 spec §6 的非目标。
