# C005 产品 delta

状态：`proposed`，实验与实现均 `not_run`。基准：`296313c6f9fcfd0d6348927b73e7a49578581b6c`。本文件是候选变化，不是当前产品合同；采用后再同步到根 `spec.md`、`constitution.md`、`roadmap.md` 与 `contracts/`。

## 1. 定位

**一句话（候选）：** 执行者可以替换，标准和授权不随之变化；任务状态可以接续，换人后不必重新解释整段任务。

接续分三级，承诺各不相同：

| 级别 | 谁启动接续 | 可以承诺什么 | 阶段 |
| --- | --- | --- | --- |
| 人工接续 | 用户打开另一宿主，调用 skill | 不必重新拼接任务背景；标准、授权和已有发现不丢失 | 第一阶段 |
| 辅助接续 | 用户确认后，由工具准备交接并启动候选执行者 | 降低换人的操作成本 | 第二阶段 |
| 自动接续 | 模型之外的驱动层，或宿主原生机制 | 在预授权范围内自动等待、切换或暂停 | 第二阶段 |

**与宿主原生恢复分开。** 三种情况承诺不同，对照基准也不同：

| 情况 | 例子 | 谁已经能做 | C005 的增量 |
| --- | --- | --- | --- |
| 同宿主恢复 | 同一 Claude Code 交互式会话等额度恢复后继续 | 宿主原生（条件见 README） | 不重做；只记录中断与恢复，并处理迟到写入（EX-02） |
| 跨宿主替换 | Claude Code 停住，换 Codex 继续同一个 Work | 无 | 交接包、执行代次、标准不降低 |
| 换资源 | 同一宿主换模型、换账号或转入付费 | 部分宿主有模型 fallback，但不在额度错误时触发 | 只在冻结的执行绑定内切换（EX-08） |

“节点内部交给宿主”是实现上的默认做法，不是固定边界：宿主的行为破坏了 Sheltie 的某项承诺时（例如中途失败后下游全部重跑，造成重复的副作用），这部分不再完全交给宿主。

前两级只能称为“可接续”，不能称为“自动不断档”。协调者额度耗尽时，状态卡能让后来者恢复，但不能自己启动后来者；自动接续必须有一个仍在运行的、模型之外的主体。

**筛选原则：** 每项能力在单 agent 场景下也必须成立或无害。全程只用一个 agent 时，第一阶段仍提供正确的等待与恢复。

## 2. 首批场景

1. **工作执行者额度耗尽。** Claude Code 做到一半，5 小时额度用完。用户打开 Codex，调用 skill，拿到交接包，继续同一个 Work。
2. **审查者额度耗尽。** 候选快照 H 已通过机器检查，审查者做到一半额度用完。另一宿主继续审查同一候选；已登记的发现保留（C004 VD-09）。
3. **协调者额度耗尽。** 协调者自己停住。第一阶段由用户在另一宿主接手协调；第二阶段由驱动层接手。
4. **没有合格备选。** 合同要求独立审查，唯一可用的执行者正是作者。Work 进入可恢复的等待，或交给人决定；不降级为作者自审。

## 3. 候选能力

编号 `EX-nn` 只在本 package 内使用；采用时再并入根规格的 GF 编号。

### 第一阶段：人工接续

`EX-01` **交接包。** 一份有界的只读投影，内容包括：候选快照、合同与标准版本、已确认的决定、验证结果、未处置的发现、未完成事项、中断原因及其来源。它可以随时从 Store 重新生成（GF-15），不是第二套状态。skill 教新宿主读取它。

`EX-02` **执行代次。** 每次换执行者都产生新的 Attempt，并带递增的执行代次。旧代次通过引擎接口提交的结果一律拒收。这只保护经过引擎接口的正式提交：它不会停止旧进程，也不会阻止同权限程序直接改库。旧执行者无法确认已停止时，新执行者使用分开的工作区，交接包写明尚未消除的副作用风险。

`EX-03` **中断原因分类与来源。** 原因只取闭集：

| 原因 | 适合的处理 |
| --- | --- |
| 资源不可用 | 等待，或换合格执行者 |
| 候选未通过验收 | 保留缺陷，按 C004 返工 |
| 执行环境故障 | 修复环境或调整路径 |
| 权限或数据政策不允许 | 停止，交给人；不能借换宿主绕过 |
| 执行者能力不足 | 缺工具、上下文或模态等：在冻结的候选集合内换合格执行者；没有就等待或交给人 |
| 原因未知 | 交给人，或按合同允许的方式重试 |

“政策不允许”和“能力不足”必须分开：前者换谁都不能继续，后者换一个合格的执行者就能继续。宿主返回的失败类别要按后端版本映射到这个闭集，映射不了的记为“原因未知”（design.md §8）。

每个原因都记录来源：提供方通道、宿主通道、人工报告或模型自报。引擎只记录闭集值与来源，不从自然语言推断原因（INV-2）。模型自报的原因可以作为等待的依据，但不能作为系统事实（INV-6）。

`EX-04` **可恢复的等待。** 原因为“资源不可用”时，Work 进入可恢复的等待，而不是只能取消（修改 GF-14）。恢复需要新的观测，或一次获准的实际尝试确认可用。到达重置时间不等于已经恢复。

`EX-05` **分开计数。** 四种上限各自计数：

- 业务重试：沿用 `max_retries`、`max_visits`，只在内容失败时消耗；
- 资源重试：资源不可用后的重试次数；
- 切换次数：同一 Occurrence 内更换执行者的次数；
- 总等待期限：一个 Occurrence 处于等待状态的累计时长。

任何一项耗尽，Work 停下来找人。这防止执行者反复自报“不可用”，绕开业务上限产生无限重试。

`EX-06` **两份宿主 skill。** 为 Claude Code 和 Codex 各提供一份 skill，教它们接手一个进行中的 Work：读交接包、领取新 Attempt、遵守原合同。skill 不保存状态、不做推进判断（GF-18）。

`EX-07` **标准不随换人降低。** 合同要求独立审查时，额度不足不能让审查降级为作者自审；合同要求的执行者资格，不能因为只剩一个可用执行者而放宽。没有合格备选时，等待或交给人。

### 第二阶段：辅助与自动接续

`EX-08` **执行绑定。** 分三层，各管各的：

| 层 | 内容 | 谁写 |
| --- | --- | --- |
| Workbook | 节点的角色与要求（例如“需要独立审查”“需要能运行测试”），不写具体宿主或模型 | Workbook 作者；可分享 |
| 用户执行配置 | 把角色映射到具体的执行入口、模型、推理强度、额度池、计费模式、允许处理的数据范围 | 用户本机 |
| Work 执行绑定 | Work 开始时冻结的**允许选择**：执行配置版本、每个节点的候选集合与优先级、资格要求、切换规则、费用与数据使用边界、自动执行政策（EX-14） | 用户确认后由引擎冻结 |

冻结的是允许的选择，不是首选。某节点允许 A 为主选、B 为备选，A 额度耗尽后选 B，属于既有授权内的选择，不修改 Workbook，也不覆盖绑定。新增候选 C，或原本只允许订阅额度、现在需要转入 API 付费，都要形成一份显式的新授权版本；原记录保留，后续 Attempt 关联新的有效版本。

“允许处理的数据范围”是用户政策，引擎可以据此拒绝把任务派给不符合政策的候选，但不能限制执行者内部读取什么；“能力声明”在没有观测证据前只是声明。

执行绑定提供的是**配置与执行来源可追溯**：能说明当时要求用什么、实际用了什么。它不保证模型输出、依赖环境和服务端行为完全相同，不称为“严格复现”。

`EX-09` **执行记录。** 每次执行记录：依据的授权版本、从候选集合中实际选了谁、请求的配置、宿主报告的实际配置、会话身份，以及每项信息的来源。实际配置与请求不同（宿主 fallback、模型别名解析、配置覆盖）时记录差异，不改写已使用的配置版本。“是否参与过当前候选的实现”从账本推导（C004 VD-10），不写在配置里。

`EX-10` **额度观测。** 每条观测记录：对应哪个额度池、何时取得、通过什么通道取得、哪些窗口有数据、是否仍然新鲜。缺失既不能解释成额度为零，也不能解释成额度充足。窗口的种类和时长按实际响应解析，不写死为“5 小时 + 每周”。

`EX-11` **候选过滤与选择。** 只在 Work 执行绑定冻结的候选集合内进行。先机械过滤：符合政策、满足资格（含职责分离）、额度池没有被观测为耗尽、必需依赖就绪（[C006](../C006-delivery-and-readiness/README.md) 的准入检查）；再按用户给定的固定优先级选择。没有评分算法。共享同一额度池的候选视为同时耗尽。

`EX-12` **最小驱动层。** 在内核之外、以前台进程运行，负责启动、观察、取消和等待执行者，只调用官方认证过的执行入口（第一批为 `claude -p` 和 `codex exec`）。约束：

- 驱动层随时可以停止，Work 仍能人工接续；恢复后的驱动层只从引擎读取权威状态；
- 切换不得扩大权限、改变数据处理范围、绕过必需审查或悄悄转入付费；
- 覆盖工作执行者耗尽和协调者耗尽两种情况；
- 驱动层单独不构成隔离。它提供的执行记录可以作为职责分离规则的输入；能否支撑强保证，还取决于报告通道、权限和状态保护。

`EX-13` **收尾额度保留。** 用户可以指定为复杂修复和最终审查保留高能力执行者。这是 Sheltie 内部的分配策略：同账户的其他会话仍可能消耗同一额度，不承诺保留的额度一定可用。

`EX-14` **自动执行政策。** Work 执行绑定的一部分，由用户确认、Work 开始时冻结；不能由协调者或 C007 的规划者生成。

| 操作 | 可否自动执行 |
| --- | --- |
| 政策授权的机器检查 | 可以 |
| 政策授权的 agent 审查 | 可以 |
| 通知用户来审批 | 可以 |
| 生成人工批准 | 不可以（GF-12 的批准仍由 CLI 以当前 OS 用户身份写入） |

规则：**驱动层只执行引擎返回、且被冻结的自动执行政策允许的操作；执行前仍需满足当前授权、资源、依赖和执行者要求。**

- `next` 只剩一个选项，只是自动执行的必要条件，不是授权。反例是 GF-12：门槛阻塞时唯一合法的下一步是 `gate approve`，它恰恰不能自动执行；
- 领取时重新确认（GF-04、GF-15）：从读取 `next` 到领取之间，授权版本、资源、依赖或执行者资格可能已经变化；
- 修改政策形成新的授权版本，不改写已冻结的版本。

## 4. 承诺合同

| 承诺 | 信任前提与机制 | 强度 | 建议 |
| --- | --- | --- | --- |
| 旧代次的迟到提交不会覆盖新状态 | 引擎按执行代次拒收（EX-02）；前提是提交走 CLI | 正常接口会拒绝 | 第一阶段实现 |
| 旧执行者已经停止 | 需要进程控制或隔离 | 两种强度都不承诺 | 如实声明；分开工作区 |
| 资源不可用不消耗业务重试，也不会无限重试 | 分开计数（EX-05） | 正常接口会拒绝 | 第一阶段实现 |
| 换人不降低标准 | 合同冻结；资格检查（EX-07、EX-11） | 正常接口会拒绝 | 第一阶段实现 |
| 执行者身份与实际配置可核对 | 需要受信来源；驱动层只能证明“按某配置发起了执行” | 分项记录声明与观测，不合并为“身份可信” | 第二阶段实现 |
| 额度观测准确 | 依赖提供方或宿主通道；可能缺失或过期 | 只作观测值，允许未知 | 第二阶段实现 |
| 保留的收尾额度一定可用 | 提供方不支持预留 | 不承诺 | 只作内部策略 |
| 切换不超出冻结的执行绑定 | 候选集合、切换规则与费用边界随 Work 冻结（EX-08）；前提是切换经过引擎接口 | 正常接口会拒绝 | 第二阶段实现 |
| 驱动层不生成人工批准，也不执行政策之外的操作 | 自动执行政策冻结；领取时重新确认（EX-14） | 正常接口会拒绝；同权限程序仍可调用 `gate approve`（C004 ADR-B） | 第二阶段实现 |

## 5. 保证范围声明（对外用语候选）

可以说：

- 换一个宿主继续同一个任务时，任务标准、授权范围和已登记的问题保持不变；
- 额度不足时，任务可以等待恢复或交给合格的备选执行者，不会自动降低标准；
- 旧执行者通过 Sheltie 接口的迟到提交不会覆盖新进展。

不能说：

- 用 skill 和状态卡就能在额度耗尽时自动不断档（这需要第二阶段的驱动层）；
- Sheltie 保证旧执行者已经停止，或它没有改动工作区；
- Sheltie 知道每个执行者的准确剩余额度，或保留的额度一定可用；
- 驱动层提供了隔离或安全保证；
- 两个会话、两个模型就等于相互独立的审查；
- 固定执行配置就能严格复现一次执行的结果。

## 7. 后续决策与触发条件

| 方向 | 触发条件 | 已知约束 |
| --- | --- | --- |
| 按成本自动路由、级联升级 | 第一阶段的固定分工已有同类任务的质量与完整成本数据 | 升级比例不等于真实失败率；必须同时观察漏检、错误拒收、人工介入和总成本；按执行者统计要分任务类型与难度 |
| 隔离后端 | 某个版本开始承诺“执行者无法篡改证据”或“无法读取保留样本” | 隔离要同时覆盖实现阶段的 agent、验证阶段运行的候选代码，以及协调者对控制状态的写入路径 |
| 外部受信执行来源 | 团队仓库，或需要独立于本机的执行证明 | 例如 CI 平台的 OIDC 身份；它证明执行来源，不证明模型或上下文独立 |
| 审查者校准 | 审查作为必要条件后，错误阻断或漏检成为主要成本 | 预埋缺陷只用于离线评估或候选副本，不修改交给用户的正式产物 |
| 转入 API 付费 | 用户明确预授权 | 必须是显式配置，不能在额度耗尽时悄悄切换 |
