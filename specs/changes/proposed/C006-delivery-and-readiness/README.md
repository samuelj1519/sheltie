## 范围约束

本 package 包含两个互不依赖的单元，分别验证、分别采用、分别发布：

**单元一：成果交付。** 已接收的成果能否可靠地送到用户授权的位置：中断后可以恢复，送达可以核对，历史接收事实不被后来的文件变化改写。

**单元二：依赖就绪。** Attempt 开始前能否识别必需依赖（首批是 skill）缺失、被遮蔽或版本不对，避免执行到一半才暴露。

两个单元放在一个 package 里，是因为它们都来自同一轮路线图讨论，都涉及“管理根之外的东西”。它们不共享实现，任何一个单元都不等另一个。

## 要解决的问题

**单元一。**

1. 产物现在只在 `~/.sheltie/works/<work_id>/attempts/<node>/<n>/<retry>/` 深处，用户要自己找、自己复制。runtime 只写 `SHELTIE_HOME`（storage.md §6），不能直接交到项目目录或用户选的目录。
2. 直接把 Work 目录搬进项目目录也不合适：冻结副本、中间产物和原始证据会混进用户仓库；用户编辑会触发只读位和摘要不符（`ARTIFACT_MODIFIED`、`STORE_CORRUPT`）；`git clean -fdx` 会删除被忽略的文件。
3. 交付由独立组件完成之后，还有三个问题要回答：送达怎样证明；复制到一半中断怎样恢复；Work 已经是终态时，送达记录写在哪里（GF-14 规定终态 Work 不再接受写操作）。

**单元二。**

1. GF-28 只让 Workbook 按 `kind + name` 声明宿主资源，引擎把声明列进任务书，不检查宿主。skill 缺失或版本不对时，要等 agent 执行到一半才暴露。
2. `kind + name` 不足以确定身份：同名 skill 可能来自项目目录、用户目录或插件，内容不同；宿主按自己的搜索顺序选中其中一份。
3. 只给出警告不够：必需依赖不满足时仍然开始执行，失败会被记成执行失败，还要消耗业务重试。

## 首批用户

与 C004 相同：个人开发者的本地 Git 仓库。单元二首批只支持一个宿主。

## 成功判据

采用前（proposal 阶段）：

- [validation.md](validation.md) 两个单元的探针已执行，按预先写定的口径分别报告；
- 机制正确性与用户价值分开报告（GF-19）。

采用后（单元一）：

- 交付位置在 Work 创建时授权；交付由独立导出组件完成，runtime 仍只写管理根；
- 送达由导出组件的回执证明，协调者的“已复制”只记为自报；
- 回执丢失、复制中断、目标已被用户修改时，恢复先核对目标，不盲目覆盖；
- 终态 Work 只能追加与已接收产物绑定的送达记录，执行结果和接收结论不变；
- “已接收未送达”“已送达”“曾送达、目标副本当前缺失”分别表达。

采用后（单元二）：

- 依赖身份包含来源和版本或摘要；
- 每个检查对象按层记录“满足 / 不满足 / 未知”三种状态；启动前的准入检查与运行中的使用记录分开；
- 必需依赖不满足或未知时，Attempt 不开始，改为等待、换合格备选或交给人；可选依赖只警告。

## 不做什么

- 不把管理根搬进项目目录；中间产物和原始证据留在管理根；
- 不自动修改 `.gitignore`，是否忽略由用户决定；
- 导出组件只写授权目标根内、导出清单列出的路径，不获得任意改写用户文件的权力；不删除目标根里的其他文件；
- 不保证送达后的副本不被修改；交付副本本来就允许用户编辑；
- 不替用户合并、提交或部署；
- 单元二不安装任何东西（GF-20 的安装工具仍后置），不写宿主配置（INV-3）；
- 不判断 skill 内容好坏，只判断身份与可用性；
- skill 只教宿主调用 CLI，不保存送达状态，不判断是否需要重试（GF-18）。
