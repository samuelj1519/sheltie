# C006 方向评估

结论：建议起草“成果交付与依赖就绪”，两个单元分别采用。本文件记录方向讨论的依据。它不是实现后的独立 review。

基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。日期：2026-09-27。参与者：用户、Claude Code，以及外部讨论者的书面意见。

## 1. 起点

用户的路线图里有两项与本 package 相关：

- 自定义 Work 输出目录：默认、项目内、自定义三种；
- 检查节点需要的 skill 是否可用。

用户同时问：当前 Work 目录结构和文件组织，是否适合放在项目目录或自定义目录中？

## 2. 收敛的结论

1. **三个根分开**：管理根、执行工作区、结果根。管理根保存事实，结果根提供副本。
2. **不搬管理根**：把整个 Work 目录放进项目目录，会让冻结副本和原始证据暴露给编辑，`git clean -fdx` 会删除被忽略的内容。
3. **结果根只放三类东西**：交付副本、证据摘要、来源清单；交接材料按需导出。
4. **缺失分三种**：交付副本缺失（重新导出）、暂时不可访问（不当作删除）、管理根唯一原件缺失（证据缺口）。
5. **`confine()` 的目的不变**：每次文件操作都必须在该操作获准使用的根目录内完成；按用途区分根目录，绑定记录用途与版本；只改受影响的合同。
6. **导出由独立组件完成**：runtime 仍只写管理根；导出组件消费交付请求，可以由协调者或驱动层自动调用，不需要用户回到终端。
7. **组件独立不能省略交付合同**：送达需要工具回执；恢复先核对目标；GF-14 的终态规定需要显式例外，只允许追加与已接收产物绑定的送达记录。
8. **依赖检查分四层、三种状态**：存在、可解析、可用、已使用；满足、不满足、未知。准入检查与使用记录分开。
9. **必需依赖不满足或未知就不开始**：改为等待、换合格备选或交给人；可选依赖只警告。
10. **两个单元各自验收、各自发布**，互不等待。

## 3. 讨论中纠正的本方错误

- 说宪章 INV-3 的条文写着“引擎只写 `~/.sheltie`”。条文只说不写宿主配置、不安装；“只写 `SHELTIE_HOME`”在 architecture.md 的 INV-3 实现行、storage.md §6、AGENTS.md 和 CONTEXT.md；
- 说 skill 检查默认只警告。必需依赖不满足或未知时应当不开始；
- 把导出组件独立当作可以省去交付合同；
- 用一个 `kind + name` 当作依赖身份。

## 4. 被否决的方向

| 方向 | 否决原因 |
| --- | --- |
| 把 `works/<work_id>/` 直接放进项目目录 | 见 §2 第 2 条 |
| runtime 直接写结果根 | 用户目录访问混入所有运行操作；恢复与事务纠缠（design.md ADR-D） |
| 协调者复制后自报送达 | 自报不等于经过核对的送达 |
| 自动修改 `.gitignore` | 属于用户的选择 |
| 依赖检查默认只警告 | 必需依赖缺失会被记成执行失败，还消耗业务重试 |
