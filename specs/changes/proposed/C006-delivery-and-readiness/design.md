# C006 候选设计

状态：`proposed`，实现 `not_run`。基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。本文件是候选机制，不是当前架构；ADR 草案在采用时移入 `specs/decisions/` 并编号。

## 1. 分层

| 层 | 知道什么 | 不知道什么 |
| --- | --- | --- |
| sheltie-core | 送达状态闭集；“终态只追加送达记录”的规则；依赖检查的三种状态与四层；`attempt begin` 的准入结构检查（纯函数） | 目标根在哪里；skill 是什么、放在哪 |
| sheltie-runtime | 存取根绑定、交付请求、回执、送达观测、准入结果与使用记录；`confine()` 只针对管理根 | 目标目录里的文件；宿主的搜索路径 |
| 外围：导出组件 | 目标根、导出清单、覆盖策略、符号链接与重名处理 | Work 怎样推进（只能通过 CLI） |
| 外围：依赖检查器 | 某个宿主某个版本的搜索路径和优先级；怎样判断遮蔽 | Work 怎样推进 |

GF-01 不变：内核里不出现 skill 目录、宿主名或 Git 词汇。

## 2. 根绑定

每个根一条绑定记录：

| 字段 | 含义 |
| --- | --- |
| 用途 | 闭集：管理、结果 |
| 位置 | 绝对路径，只在绑定记录里出现 |
| 版本 | 同一 Work 同一用途内单调递增 |
| 授权来源 | Work 创建时的用户选择，或之后的显式修改 |

`confine()` 的目的不变：每次文件操作都必须在该操作获准使用的根目录内完成。runtime 只拿到管理根；导出组件只拿到当前有效的结果根绑定。其他记录里的位置一律写成“根绑定 + 相对路径”。

## 3. 交付协议

```text
① 引擎事务：生成交付请求（产物摘要、导出清单、结果根绑定版本、覆盖策略、请求标识）
② 导出组件：从管理根读源文件，核对摘要
③ 导出组件：在目标根内写入。每个文件先写临时名，再原子改名；来源清单最后写
④ 导出组件：通过 CLI 提交回执（实际写入的文件及摘要、请求标识）
⑤ 引擎事务：记录回执，送达状态转为“已送达”
```

- ③ 与 ⑤ 之间没有原子性。恢复时按 spec.md DL-06 先检查目标：来源清单里的请求标识和摘要是判断依据；
- 临时名带请求标识，恢复时能认出哪些残留属于本次请求；不属于本次请求的文件不动；
- 覆盖策略只取闭集：`refuse`（默认：目标已存在同名文件就记为冲突）与 `replace-own-unmodified`（只覆盖本 Work 以前送达、且摘要仍与当时回执一致的文件）；
- 目标路径的任何一段是指向目标根之外的符号链接时，拒绝写入并记为送达失败；导出清单里的相对路径同样拒绝绝对路径、`..` 与空段；
- 导出组件只写，不删除目标根里的任何文件。

**交付内容：**

| 内容 | 来源 |
| --- | --- |
| 交付副本 | 已接收产物，按导出清单复制 |
| 证据摘要 | 从证据记录生成的只读投影：每个条件的结果、写入方式和原件指针（采用 C004 时） |
| 来源清单 | Work 标识、Workbook 版本与摘要、候选标识、每个文件的摘要、结果根绑定版本、请求标识、生成时间 |
| 交接材料 | C005 EX-01，只在请求时导出 |

证据摘要只给指针，原始日志和原始证据留在管理根。

## 4. 依赖检查器

```text
Workbook 声明（kind、name、来源、版本或摘要、必需/可选）
   └── 外围检查器（按宿主与版本）：逐层检查存在、可解析、可用
          └── CLI 写入准入结果（检查器与版本、宿主与版本、执行工作区、逐项逐层状态、证据指针）
                 └── attempt begin：必需依赖全部“满足”且结果有效，才允许开始
```

- “可解析”要列出同名候选以及宿主会选中哪一份；判断不了宿主的选择顺序时记为未知；
- “可用”中能直接检查的（引用的文件是否存在）给出满足或不满足；需要运行才能知道的（外部工具在执行时是否可用）记为未知；
- 准入结果带失效条件（spec.md DR-06）；`attempt begin` 发现条件已变化时拒绝开始并要求重新检查；
- 使用记录分声明与观测。观测需要宿主通道；宿主没有提供通道时，只有声明。

首批宿主由采用时决定；检查器与导出组件一样，先以外部脚本形式参与探针实验，证据标为“外部回填”。

## 5. ADR-D 草案：交付组件边界

状态：`proposed`
日期：2026-09-27
关联 change：C006

### 背景

用户需要把成果交到项目目录或自选目录。storage.md §6 与 architecture.md 的 INV-3 实现行规定 runtime 只写 `SHELTIE_HOME`。GF-14 规定终态 Work 不再接受写操作。

### 候选

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| E1 runtime 直接写结果根 | 扩大 `confine()` 的根集合，runtime 在生成产物时同时写结果根 | 实现最少 | 用户目录访问混入所有运行操作；中断恢复与 Store 事务纠缠 |
| E2 独立导出组件 | runtime 只写管理根；导出组件消费交付请求，写结果根并提交回执 | 边界清楚；恢复协议独立；与安装工具的思路一致 | 需要交付请求、回执和终态例外 |
| E3 维持现状 | 用户自己从管理根复制 | 零新增 | 用户价值缺口不变 |

### 建议

采用 E2。导出组件是独立二进制，还是 `sheltie` 里拥有自己 `confine()` 范围的命令组，采用时决定；核心要求是它拥有足够且有限的交付能力，不因为运行在管理根之外就获得任意改写用户文件的权力。

### 否决方案

- **把整个 Work 目录放进项目目录。** 冻结副本和原始证据会暴露给用户编辑，破坏摘要核对；`git clean -fdx` 会删除被忽略的内容。
- **协调者复制文件后自报送达。** 违反 INV-6 的精神；自报只能记为声明。
- **终态 Work 上直接改写状态字段记录送达。** 与 GF-14 的字面含义冲突，也会让后来的缺失改写历史事实。

### 后果

- GF-14 增加终态例外（spec.md DL-07）；
- storage.md §6 按用途区分根目录；
- protocol.md 增加交付请求与回执；
- 导出组件需要自己的失败路径测试。

### 确认方式

- 回执丢失后恢复，目标文件与请求一致时只补记；
- 目标文件被用户修改后恢复，记为冲突，不覆盖；
- 符号链接越界时拒绝写入；
- 终态 Work 上追加送达记录成功，其他写操作仍被拒绝。
