# C006 独立审阅答复（2026-09-27）

答复对象：[independent-review-2026-09-27.md](independent-review-2026-09-27.md)。逐条核对审阅所引的原文（修订前的 C006 各文件，行号以基线版本为准）与根规格后给出判断，并按采纳的意见修订了方案。本答复不改变 `proposed` 状态；探针与失败路径测试仍为 `not_run`。依赖就绪单元已拆到 [C008](../C008-dependency-readiness/README.md)，第 1 条的修订落在那里。

两项需要人决定的事项，本轮已由用户按答复建议定下：导出组件采用独立 crate 与独立二进制（第 6 条）；依赖就绪拆成独立 package（第 2 条）。

## 逐条答复

### 1. 四层依赖检查与准入规则自相矛盾 —— 采纳

**判断。** 前提成立。原 spec.md DR-02 把「已使用」列为只能执行后得知，DR-05 却规定必需依赖「任何一层」未知都不开始。原 design.md §4 实际只查三层，所以这首先是 DR-05 的措辞错误；但审阅指出的更实质问题也成立：原 design.md §4 把「需要运行才能知道的」可用性一律记为未知，按 DR-05 会让依赖外部工具的必需 skill 永远无法开始。

**修改。** C008 spec.md DR-02、DR-05：准入只看存在、可解析、可用（可预检）三层；「已使用」只作事后记录；运行时才知的可用性由 Workbook 声明 `stop` 或 `attempt-once`，未知在任何政策下都不改写为满足。C008 validation.md §3 增加「三层满足、已使用未知仍可开始」正例和「只有可解析不满足」的单条件遮蔽反例。

### 2. 两个独立单元需要独立生命周期入口 —— 采纳，已拆分

**判断。** 前提成立。原 README 写「分别采用、分别发布」，而 changes/README.md 规定目录位置就是状态、默认只允许一个 active change。一个目录无法同时表示两种状态。

**修改。** 目录更名为 `C006-result-delivery`，只保留成果交付；依赖就绪移入新的 [C008-dependency-readiness](../C008-dependency-readiness/README.md)，各自有 README、spec、design、validation 与采用条件。C006 review.md 顶部注明拆分，正文保留讨论原貌。

### 3. 交付恢复必须按目标上的实际字节判定 —— 采纳

**判断。** 基本成立。原 design.md §3 写「来源清单里的请求标识和摘要是判断依据」，原承诺表也写「核对来源清单与摘要」，来源清单确实被当成了判断依据。有一处审阅说得略重：原 DL-06 第二行「部分文件已写入且与请求一致」本来就是按请求比对，正是处理清单尚未写入的情况。

**修改。** spec.md DL-03 明确交付请求保存在 Store、不可变，是恢复与回执核对的唯一基准；DL-06 改为逐个目标文件读取实际字节比对请求，来源清单只作辅助；DL-05 规定回执携带请求标识、绑定版本和实际读回的摘要，引擎逐项核对。design.md §3.2 列出审阅要求的三个故障窗口和重复提交回执；validation.md §3 增加对应场景，并要求在文件写入、清单写入、回执提交前后分别杀进程。

### 4. 目标根路径不能只靠事先检查符号链接 —— 采纳，硬链接一项降级

**判断。** 前提成立。原 design.md §3 只在写入前检查一次符号链接，检查与写入之间存在替换窗口。硬链接一项过度：原方案已经是临时名加原子改名，改名替换的是目录项，不会打开已有目标文件写入，因此不会顺着硬链接写到根外。审阅还漏了一点：目标根若与管理根重叠，导出组件就能改写 Store 原件。

**修改。** 新增 design.md §3.3「目标根写入合同」，与 C002 T04 的受限句柄和安全原子写同一写法：目标根身份（设备号 / inode）核对、逐段不跟随链接的相对打开、父目录句柄内独占创建临时名、`sync_all` 后同目录原子替换、只清理本请求临时名；目标根不得等于、包含或位于管理根之内；硬链接说明为何不作为拒绝条件。支持的平台逐一验证，不能提供等价语义的平台不提供导出。validation.md 的拒绝例都带根外哨兵。

### 5. 交付前提与名称要随 C004 是否采用而变化 —— 采纳，并收紧交付条件

**判断。** 前提成立。原 README、DL-02、DL-03、DL-07 无条件使用「已接收」，而未采用 C004 的分支只是「终点的 Attempt 成功」，GF-11 明确 `succeeded` 不代表结论合格。审阅还漏了一点：GF-14 要求 Work `succeeded` 还需「无未批准门槛」，只看终点 Attempt 成功会在门槛未批时就触发交付。

**修改。** spec.md DL-03：交付条件改为 Work 已 `succeeded`；DL-02、§3、§4 与 README：未采用 C004 时称「流程完成后的产物副本」，不称「已接收」，也不给质量结论；「已接收」只在采用 C004 时使用。validation.md 增加「终点成功但门槛未批不交付」「未采用 C004 时的交付包用语」两个场景。

### 6. 先固定外部写入的授权边界 —— 纠正引用，接受结论

**判断。** 引用的事实有误：宪章 INV-3（constitution.md:28）条文只规定不写宿主配置、不安装，没有「引擎只写 `~/.sheltie`」。这句话出自 architecture.md §6 的 INV-3 实现行、AGENTS.md 硬边界、CONTEXT.md 的「引擎」词条和 GF-27。C006 review.md 在讨论阶段已经纠正过同一点，但当时把出处之一误写成「storage.md §6」（storage.md §6 是历史文件与当前投影），本轮一并更正。实质担忧成立：原 design.md ADR-D 允许导出组件做成 `sheltie` 的一个命令组，那样 AGENTS.md 与 CONTEXT.md 里「引擎」的写入边界就有歧义；原 spec §6 的受影响条款也漏了 AGENTS.md 和 CONTEXT.md。

**决定与修改。** 用户按建议选定：导出组件是独立 crate 与独立二进制（暂名 `sheltie-deliver`），只写授权目标根；它对管理根只读，经 `sheltie` 的公开命令读取交付请求、提交回执，由 `sheltie` 写 Store。这样两个写入者各写各的根，「引擎只写 `~/.sheltie`」字面不变，也与 architecture.md 把宿主安装工具放进独立 crate 与二进制的既定思路一致。design.md ADR-D 改为 E2a / E2b 对照并建议 E2b；spec.md §5 受影响条款补上 architecture.md（crate 清单、INV-3 实现行、「不拆独立安装器」一节）、AGENTS.md（「三个 crate，单二进制」的描述）、CONTEXT.md 与 GF-27（`self` 是否一起分发第二个二进制）。

## 审阅未列出的补充修订

- **DR-05 离不开 C005。** 原 DR-05 的「改为等待、换合格备选」依赖 C005 的执行绑定和可恢复等待，而原 README 声称两个单元都不依赖 C005。C008 README 与 spec.md DR-05 写明：未采用 C005 时，准入未满足只会让 `attempt begin` 拒绝，Work 状态不变，`next` 提示重新检查或交给人；不把 Work 置为现行 GF-14 下只能取消的 `blocked`。等待与换备选只在采用 C005 后提供。
- **引擎无法自己发现准入结果过期。** 原 DR-06 与 design.md §4 要求 `attempt begin` 发现宿主版本、工作区变化时拒绝，但 DR-08 同时规定引擎不检查宿主。C008 DR-06 改为：检查器上报失效键与有效期，引擎只比较有效期和它自己持有的键；宿主侧未经重新检查的变化明确列入「不承诺」。
- **单元一探针借用了 C004 样本。** 原 validation.md §2 复用 C004 阶段 1 的任务样本，与「不以 C004 为前提」不一致。现改为自备样本并先测手工交付基线。
- **路径约束出处。** 原 README 与 spec §6 把「runtime 只写 `SHELTIE_HOME`」标为 storage.md §6，实为 architecture.md §6；已更正。

## 推进建议答复

同意。C006 先让用户在真实 Work 上手工找到并核对交付文件测出基线，再用外部脚本在临时目标根中演练中断、目标编辑与重复调用（validation.md §2）。C008 先选一个宿主和一份真的带必需 skill 的 Workbook，测误拦、未知比例和必需依赖出现率；出现率过低就不采用（C008 README 采用条件）。两个 package 分别采用、分别安排 Owner 与真实 CLI / 文件系统反例；C008 不把「开始前检查通过」写成「执行时已经使用」。

## 复审（e87eb07）答复

复审对象：上述修订后的提案（提交 e87eb07）。复审没有写入文件，意见以对话形式给出；本节按原编号记录与 C006 相关的两条。

### S1. 回执摘要由导出组件自报，可以伪造（高）

**判断：采纳。** e87eb07 的 DL-05 让引擎把回执里的“实际摘要”与请求比对，但这些摘要是导出组件报的。组件在目标文件缺失时照样可以提交与请求一致的摘要，引擎会记为已送达。宪章 INV-6 把文件摘要列为系统事实，并以“接受工作 agent 自报的输出文件 sha256”为反例；导出组件不是工作 agent，但它报的摘要同样不是引擎取得的。复审给了两种改法：降低“已送达”的承诺，或由引擎自己读回。本答复选后者：`workbook add` 已经只读访问管理根之外的目录，读回不需要新的边界类别。

**处理：** 回执核对时，`sheltie` 按绑定只读打开目标根、核对根身份，按与写入相同的逐段不跟随链接方式打开每个清单文件，自己计算摘要；引擎摘要等于期望摘要、组件陈述与之一致才记为已送达。回执保存引擎摘要、读取时间和组件陈述。承诺限定为“回执核对那一刻目标上的字节”，读回之后的改动按 DL-08 记为送达观测。architecture.md 的 `confine()` 条款列入受影响上游：runtime 可只读访问当前有效的结果根绑定。

**修改位置：** spec.md §1 表、DL-05、DL-08、§3 承诺表、§5 上游表；design.md §1、§2、§3.1 ⑤、§3.2（新增故障窗口）、§4 确认方式；validation.md §3 新增两行。

### Spec4. 覆盖策略在检查与改名之间有竞态（中）

**判断：采纳，附一条局限声明。** §3.3 第 4 步“原子改名到目标名”用的是会静默替换目标的普通改名。检查“目标不存在”或“目标仍与旧回执一致”之后、改名之前，用户或其他进程创建或改动了目标文件，改名会把它覆盖，覆盖策略就落空了。

**处理：** `refuse` 改用原子的“不替换”改名（Linux `renameat2(RENAME_NOREPLACE)` 或 `linkat`，macOS `renamex_np(RENAME_EXCL)`），目标名在检查后才出现时改名失败，记为冲突。`replace-own-unmodified` 改用原子交换（`RENAME_EXCHANGE` / `RENAME_SWAP`），交换后读取换出的字节与旧回执比对，不一致就换回原状并记为冲突。没有原子交换的平台只提供 `refuse`，两种原子操作都没有的平台不提供导出。

**异议（局限，不是否定）：** 已经持有旧文件打开句柄的写入者，可以在交换之后继续写被换出的旧文件，任何基于目录项的方案都拦不住。这部分写入列为承诺之外，并在 §3 承诺表中写明。

**修改位置：** spec.md §3 承诺表新增一行；design.md §3.2、§3.3 第 4 步与平台验证说明、§4 确认方式；validation.md §3 新增三行。
