# C006 产品 delta

状态：`proposed`，实验与实现均 `not_run`。基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。本文件是候选变化，不是当前产品合同；采用后再同步到根 `spec.md`、`architecture.md`、`roadmap.md` 与 `contracts/`。依赖就绪的候选变化已拆到 [C008](../C008-dependency-readiness/spec.md)。

## 1. 三个根

| 根 | 放什么 | 谁写 | 用户能否编辑 |
| --- | --- | --- | --- |
| 管理根（`~/.sheltie`） | 权威 Store、冻结的 Workbook 副本、输入、Attempt 的原始产物、原始证据、交付请求与回执 | `sheltie`（runtime 经 `confine()` 限定在管理根内；核对回执时只读结果根，见 DL-05） | 不应编辑；改动会被摘要核对发现 |
| 执行工作区 | agent 编辑代码的地方：用户仓库，或由宿主、外围组件提供的环境 | 宿主、agent、外围组件；Sheltie 记录环境身份与对应关系（C004 design.md §3.4） | 可以 |
| 结果根 | 交付副本、证据摘要、来源清单，以及按需导出的交接材料 | 独立导出二进制，按 Work 创建时的授权 | 可以；交付副本本来就给用户用 |

**原则：** 管理根保存事实，结果根提供副本。结果根里的文件变化、缺失或暂时不可访问，都不改写管理根里的历史事实。两个写入者各写各的根：`sheltie` 不写结果根，导出组件不写管理根。

## 2. 候选能力

编号 `DL-nn` 只在本 package 内使用；采用时再并入根规格的 GF 编号。

`DL-01` **交付位置在 Work 创建时授权。** 三选一：默认位置、项目目录内的位置、自定义位置；默认值在采用时确定。授权记录目标根、用途和绑定版本。首版只允许不替换已有不同字节文件的写入。目标根不得等于、包含或位于管理根之内；授权时拒绝，每次导出前再核一次（design.md §3.3）。修改目标形成新的绑定版本，旧的送达记录仍按旧绑定解析。

`DL-02` **管理根与结果根分工。** 管理根保留原始记录、冻结产物和原始证据；结果根只接收三类东西：交付产物的副本、面向用户整理的证据摘要、来源清单。证据摘要与来源清单使用由请求标识确定的独立相对路径，内容由请求创建时冻结的字段和原始证据生成；同一请求重复执行得到相同字节，新请求不得覆盖旧请求的文件。交付产物在采用 C004 时是经过接收出口的候选；未采用时是「流程完成后的产物副本」，引擎不对其内容作任何认定（GF-11）。交接材料（C005 EX-01）只在请求时导出。中间产物不导出。

`DL-03` **交付请求。** 达到交付条件后，引擎给出一个交付请求。交付条件是 Work 已 `succeeded`：按 GF-14，终点节点的 Attempt 成功且无未批准门槛；采用 C004 时，终点只能经接收出口到达（C004 VD-06 装入校验），因而同时意味着候选已经过接收出口。只有终点 Attempt 成功、仍有未批准门槛时不生成交付请求。请求关联：

- 交付产物版本及其摘要；
- 导出清单：每项源产物对应管理根内的冻结来源、目标相对路径及期望摘要；每项按请求固定的元数据（证据摘要、来源清单）对应有界的完整字节、目标相对路径及期望摘要；
- 目标根的绑定版本；
- 写入规则：目标已有不同字节文件时拒绝，不提供覆盖选项；
- 请求标识。

请求保存在 Store 里，一经生成就不再修改；要改只能取消后重新请求。它是恢复与回执核对的唯一基准。

`DL-04` **独立导出组件。** 导出组件是独立 crate 与独立二进制（暂名 `sheltie-deliver`），不在 `sheltie` 里：它经 `sheltie` 的公开命令读取交付请求，只读地打开管理根里的源文件并核对摘要，只写目标根内、导出清单列出的路径，不删除目标根里的其他文件，不直接写管理根；回执经 `sheltie` 的命令提交，由 `sheltie` 写入 Store。目标根的打开、逐段约束、临时文件与发布按 design.md §3.3 的合同执行。协调者、驱动层或用户都可以在交付条件满足后调用它，不必等用户回到终端；skill 可以教宿主调用，但不保存送达状态，也不判断是否需要重试（GF-18）。

`DL-05` **送达回执。** 送达只由导出组件提交、经 `sheltie` 读回核对的回执证明。导出组件提交请求标识、结果根绑定版本、它自己读回的每个文件摘要和完成时间，写入方式标为「导出组件」；这些摘要是组件的陈述，只用于交叉核对，不作为系统事实（INV-6）。`sheltie` 接收回执时：

1. 核对请求存在且尚未有回执、绑定版本与请求一致；
2. 按绑定记录只读打开目标根，核对根身份，以与写入相同的逐段不跟随链接方式打开导出清单列出的每个文件，自己读取字节并计算摘要（design.md §3.1 ⑤）；
3. 引擎算出的摘要必须等于请求的期望摘要，组件陈述的摘要也必须与之一致。

任一不符就拒绝，不记为已送达；目标文件缺失、根身份不符、某段是符号链接，都按不符处理。回执保存的摘要是引擎读到的摘要与读取时间，组件陈述另存。这个承诺只覆盖「回执核对那一刻目标上的字节」，之后的变化按 DL-08 记为送达观测。协调者说「已经复制好了」，只能记为自报，不能等同于经过核对的送达。

`DL-06` **可恢复交付。** 最常见的中断是：文件已经写到目标，进程在回写送达状态前退出。恢复以 Store 中不可变的交付请求为基准，对导出清单中的每个目标文件重新读取实际字节并计算摘要；来源清单只是辅助标识，不作为判断依据：

| 某个目标文件的实际状态 | 处理 |
| --- | --- |
| 存在，摘要与请求一致 | 视为本请求已写入，不重写 |
| 不存在（可能留有本请求标识的临时名） | 清理本请求的临时名后补写 |
| 存在，摘要与请求不一致（用户已编辑，或有其他内容） | 记为送达冲突，停下来交给人；用户可授权新的结果位置，不覆盖此文件 |

全部交付产物与证据摘要一致后写本请求的来源清单：不存在则以不替换方式写入，已存在且摘要相同则跳过，不同则冲突；随后提交回执。不能直接重跑覆盖，因为用户可能已经开始编辑目标文件。GF-15 的幂等要求是设计基础，但它不会让管理根的数据库和外部文件系统形成一个原子事务，所以导出需要自己的恢复协议。

`DL-07` **终态后只追加送达记录。** GF-14 规定终态 Work 不再接受写操作。本 package 提出一条显式例外：终态 Work 的执行结果（以及采用 C004 时的接收结论）保持不变；交付过程可以追加与指定交付请求绑定的请求、回执和送达观测。这些记录在同一个 Store 里单独保存，不另建数据库；除此之外，终态 Work 仍不接受任何写操作。

`DL-08` **送达状态与后来的观测分开。**

送达状态：未请求、已请求未送达、已送达、送达冲突、送达失败。

回执记录的是引擎在回执核对那一刻读到的目标字节。送达之后的观测另行记录，不覆盖送达状态，也不覆盖历史回执：

| 观测 | 含义 | 处理 |
| --- | --- | --- |
| 目标副本缺失 | 管理根的原件完好，只是交付副本不见了 | 可以从管理根重新导出，形成新的交付请求 |
| 目标暂时不可访问 | 外置磁盘未挂载、网络目录断开等 | 记为不可访问，不当作已删除 |
| 管理根的唯一原件缺失 | 证据缺口 | 按现有规则报 `STORE_CORRUPT`；交付副本不能反过来充当原件 |
| 交付副本被修改 | 用户在用它 | 不算证据缺口；与回执摘要比对，区分「送达时的原样」和「后来改过」 |

`DL-09` **持久引用不用绝对路径。** 交付请求、回执和来源清单里的位置，都记为 Work 标识 + 根绑定（用途与版本）+ 相对路径。任务书仍可给出绝对路径，因为它服务的是当次执行。

`DL-10` **不替用户改 `.gitignore`。** 目标根在 Git 仓库内时，是否忽略由用户决定。被忽略的交付副本会被 `git clean -fdx` 删除，这按「目标副本缺失」处理；未被忽略的会出现在 `git status` 里，这也是用户的选择。

## 3. 承诺合同

| 承诺 | 信任前提与机制 | 强度 | 建议 |
| --- | --- | --- | --- |
| `sheltie` 只写管理根 | `confine()` 限定管理根；结果根只由独立导出二进制写 | 正常接口会拒绝 | 实现 |
| 导出组件不写授权范围之外的位置 | 目标根身份核对 + 逐段不跟随链接的受限句柄 + 同目录内原子不替换发布；目标根不与管理根重叠（design.md §3.3） | 正常接口会拒绝 | 实现；只在逐平台验证通过的平台上承诺；同权限程序仍可改写用户文件 |
| 不覆盖已有目标文件，包括检查之后才出现的文件 | 最终写入使用原子的「不替换」改名（design.md §3.2、§3.3）；已存在且摘要相同的文件只读核对、不重写 | 正常接口会拒绝 | 实现；平台不能提供等价操作时不提供导出；其他程序仍可修改目标文件 |
| 「已送达」有工具回执 | 回执由导出组件提交；`sheltie` 只读读回目标文件、自己计算摘要并与请求比对，组件陈述的摘要只作交叉核对（DL-05）；自报另记 | 正常接口会拒绝 | 实现；同权限程序仍可在读回之后改写目标，这按送达观测处理 |
| 中断后不盲目覆盖用户已编辑的文件 | 恢复以交付请求为基准逐文件核对实际字节（DL-06） | 正常接口会拒绝 | 实现 |
| 后来的变化不改写历史事实 | 回执记送达时字节；送达观测只追加（DL-07、DL-08） | 正常接口会拒绝 | 实现 |
| 送达后的副本保持原样 | 用户可以编辑 | 不承诺 | 与回执摘要比对识别改动 |
| 交付的产物内容合格 | 未采用 C004 时引擎不认定内容；采用时只到 C004 的证据范围 | 不承诺 | 用语区分「流程完成后的产物副本」与「候选已经过接收出口」 |

## 4. 保证范围声明（对外用语候选）

可以说：

- 流程完成后，成果会送到你在创建任务时授权的位置；送达有工具回执，按目标上的实际文件核对，中断后可以恢复，不会盲目覆盖你已经改过的文件；
- 交付副本丢了，可以从管理根重新导出；它后来的变化不影响历史送达记录；
- （采用 C004 时）交付的是经过接收出口的候选，证据范围见交付包。

不能说：

- 送达后的文件一定保持原样；
- （未采用 C004 时）交付的成果已被接收或内容合格；
- 导出组件阻止了其他程序改写目标目录。
