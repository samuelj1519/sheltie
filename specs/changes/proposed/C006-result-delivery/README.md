## 范围约束

流程完成后的成果能否可靠地送到用户授权的位置：中断后可以恢复，送达可以按目标上的实际字节核对，历史送达事实不被后来的文件变化改写。

本 package 原本同时包含「依赖就绪」单元。按[独立审阅](independent-review-2026-09-27.md)第 2 条，两个单元需要各自的生命周期入口，依赖就绪已拆到 [C008](../C008-dependency-readiness/README.md)。两者不共享实现，互不等待。

## 要解决的问题

1. 产物现在只在 `~/.sheltie/works/<work_id>/attempts/<node>/<n>/<retry>/` 深处，用户要自己找、自己复制。runtime 只写 `SHELTIE_HOME`（architecture.md §6 的 INV-3 实现行），不能直接交到项目目录或用户选的目录。
2. 直接把 Work 目录搬进项目目录也不合适：冻结副本、中间产物和原始证据会混进用户仓库；用户编辑会触发只读位和摘要不符（`ARTIFACT_MODIFIED`、`STORE_CORRUPT`）；`git clean -fdx` 会删除被忽略的文件。
3. 交付由独立组件完成之后，还有三个问题要回答：送达怎样证明；复制到一半中断怎样恢复；Work 已经是终态时，送达记录写在哪里（GF-14 规定终态 Work 不再接受写操作）。

## 首批用户

个人开发者的本地 Git 仓库。

## 成功判据

采用前（proposal 阶段）：

- [validation.md](validation.md) 的探针已执行，按预先写定的口径报告；
- 机制正确性与用户价值分开报告（GF-19）。

采用后：

- 交付位置在 Work 创建时授权；交付由独立导出二进制完成，`sheltie` 仍只写管理根；
- 交付条件是 Work 已 `succeeded`（GF-14，含无未批准门槛）；未采用 C004 时，交付物称为「流程完成后的产物副本」，不称「候选已经过接收出口」，也不表示内容合格（GF-11）；
- 送达由导出组件的回执证明，回执按目标上的实际字节核对；协调者的「已复制」只记为自报；
- 回执丢失、复制中断、目标已被用户修改时，恢复以 Store 中不可变的交付请求为基准逐个核对目标文件，不盲目覆盖；
- 终态 Work 只能追加与交付请求绑定的送达记录，执行结果不变；
- 「已请求未送达」「已送达」「曾送达、目标副本当前缺失或已改」分别表达。

## 不做什么

- 不把管理根搬进项目目录；中间产物和原始证据留在管理根；
- 不自动修改 `.gitignore`，是否忽略由用户决定；
- 导出组件只写授权目标根内、导出清单列出的路径，不获得任意改写用户文件的权力；不删除目标根里的其他文件；目标根不得与管理根重叠；
- 不保证送达后的副本不被修改；交付副本本来就允许用户编辑；
- 不替用户合并、提交或部署；
- skill 只教宿主调用 CLI，不保存送达状态，不判断是否需要重试（GF-18）。
