# C006 独立方案审阅（2026-09-27）

审阅对象：本 package 的五份提案文档；对照 INV-3/INV-7、GF-14/GF-28、现行存储合同及 C002 计划。本文件不改变 `proposed` 状态。两个单元的探针和失败路径测试均为 `not_run`。外部依据见 [一手来源笔记](../../../research/2026-09-27-agent-rust-guidance.md)。

## 结论与产品价值

**成果交付有清楚的用户问题，值得优先做低成本探针；依赖就绪的首批范围应再收窄。** 原始产物只在管理根内，用户需自行寻找并核对版本。独立导出、来源清单和中断恢复能减少实际交付摩擦，且保留 Store 为唯一事实来源。依赖检查针对同名 skill 遮蔽比仅按 `kind + name` 判断更准确。两单元都可通过现有 Work 做外部脚本探针，现阶段无须先修改 Rust 状态机。

设计正确承认 SQLite 事务与目标目录写入不能一起原子提交；Rust 的 `rename`、`copy` 和同步语义也不能替代跨两处的恢复协议。实际价值仍取决于用户每次手动交付耗时和依赖故障发生率。若少量样本里基本没有必需宿主资源，单元二的架构成本可能高于收益。

## 采用前需修订

1. **高：四层依赖检查与准入规则自相矛盾。** DR-02 把「已使用」列为第四层，并明确只能执行后得知；DR-05 却规定必需依赖「任何一层未知」都不得开始。首次 `attempt begin` 时「已使用」必然未知，所有必需依赖都会被拒绝。应把准入限定为执行前可验证的存在、可解析、可用三层；已使用只做事后记录。对不可预检的「可用」再定义明确政策：必需且未知时停下，还是允许一次受限尝试；不能把未知当满足。给真实入口补「预检三层满足、使用尚未知仍可开始」正例和单条件遮蔽反例。
2. **高：两个独立单元需要独立生命周期入口。** `README.md` 写明单元一、二「分别采用、分别发布」，而仓库规则规定目录位置就是 change 状态、默认只允许一个 active change，计划也是 active package 的唯一实施进度。一个 C006 目录无法同时表示「单元一 active、单元二 proposed」，也难给两次发布分别关闭同一 package。采用前把它们拆成各自的 change package，或由人先选定只采用一个单元并为另一个另立 proposal。不得以同一 `completed` 状态覆盖未做的单元。
3. **高：交付恢复必须按目标上的实际字节判定。** DL-06 说「来源清单存在且摘要一致」即可补记回执，但来源清单只能证明清单自身，不能证明目标文件仍是这些字节；「部分文件已写入」时来源清单又尚未写入（`design.md` §3 明定最后写清单）。恢复应以 Store 中不可变的交付请求为基准，对每个目标文件重新读取和核对摘要，再决定补写、补记或冲突；清单只是辅助标识。回执写入也应核对请求标识、绑定版本和实际目标摘要。增加「清单仍在但文件被改」「清单不存在但部分文件存在」「回执提交后目标立即变化」三个故障窗口，分别保留历史送达与当前观测。
4. **高：目标根路径不能只靠事先检查符号链接。** `design.md` §3 只规定路径某段指向根外时拒绝；目标目录可在检查后、写入前被替换，或出现硬链接、重名与目标根别名。C002 已在管理根要求受限句柄和安全原子写。导出组件需要同样明确的目标根打开、逐段约束、临时文件创建、最终替换与崩溃清理合同；适用平台分别验证，拒绝例用根外哨兵证明没有越界写入。没有这些证据时，不应承诺「只写授权目标根」。
5. **中：交付前提与名称要随 C004 是否采用而变化。** DL-03 未采用 C004 时用终点 Attempt 成功作为交付条件，而当前 GF-11 明定 `succeeded` 不是内容合格。不能在这个分支称产物「已接收」或说证据证明质量；应标为「流程完成后的产物副本」，由 Workbook/用户决定内容是否可用。若 C004 采用，再显示其受控接收状态和证据范围。
6. **中：先固定外部写入的授权边界。** INV-3 当前写「引擎只写 `~/.sheltie`」，提案允许独立组件写结果根。若它与 `sheltie` 同一二进制或同一命令组，现行字面边界有歧义。采用前由人选定组件形态与授权来源，先修宪章、架构和存储合同；导出权限不能靠改称「外围」绕过。

## 推进建议与验收口径

先让用户在真实 Work 上手工找到并核对交付文件，测出基线；外部脚本只复制明确授权的文件，在临时目标根中演练中断、目标编辑与重复调用。依赖就绪先选一个宿主和一份真的带必需 skill 的 Workbook，核对该宿主版本的搜索顺序、遮蔽与未知比例。若收益成立，两个单元分别采用、分别安排 Owner 与真实 CLI/文件系统反例。单元一还要在文件写入、清单写入、回执提交的各窗口杀进程；单元二不得把「开始前检查通过」写成「执行时已经使用」。

**建议状态：两个单元均保留 proposed；先修准入矛盾与 change 生命周期，再按各自探针决定是否采用。**
