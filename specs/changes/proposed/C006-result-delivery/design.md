# C006 候选设计

状态：`proposed`，实现 `not_run`。基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。本文件是候选机制，不是当前架构；ADR 草案在采用时移入 `specs/decisions/` 并编号。依赖检查器的设计已拆到 [C008](../C008-dependency-readiness/design.md)。

## 1. 分层

| 层 | 知道什么 | 不知道什么 |
| --- | --- | --- |
| sheltie-core | 送达状态闭集；「终态只追加送达记录」的规则；交付条件（Work `succeeded`）；回执与请求的结构比对（纯函数） | 目标根在哪里；目标文件的内容 |
| sheltie-runtime | 存取根绑定、交付请求、回执、送达观测；写入的 `confine()` 只针对管理根；回执核对时只读打开结果根，读取导出清单列出的文件并计算摘要 | 目标目录里的其他文件；不写结果根 |
| 导出组件（独立 crate 与二进制） | 目标根、导出清单、不替换写入合同（§3.3）、恢复协议 | Work 怎样推进（只能通过 `sheltie` 的公开命令）；不写管理根 |

GF-01 不变：内核里不出现宿主名或 Git 词汇。

## 2. 根绑定

每个根一条绑定记录：

| 字段 | 含义 |
| --- | --- |
| 用途 | 闭集：管理、结果 |
| 位置 | 绝对路径，只在绑定记录里出现 |
| 身份 | 授权时记录的目标根设备号与 inode（或平台等价物），导出时核对 |
| 版本 | 同一 Work 同一用途内单调递增 |
| 授权来源 | Work 创建时的用户选择，或之后的显式修改 |

`confine()` 的目的不变：每次文件操作都必须在该操作获准使用的根目录内完成。`sheltie` 写入只拿到管理根，回执核对时对当前有效的结果根绑定只读；导出组件只写当前有效的结果根绑定，对管理根只读。其他记录里的位置一律写成「根绑定 + 相对路径」。

## 3. 交付协议

### 3.1 正常路径

```text
① sheltie 事务：Work 已 succeeded 时生成交付请求（产物摘要、导出清单与每项期望摘要、生成元数据的有界完整字节、结果根绑定版本、请求标识），保存在 Store，不再修改
② 导出组件：经 sheltie 公开命令读取请求；只读打开管理根里的源文件，核对摘要
③ 导出组件：按 §3.3 打开目标根并逐个写入；每个缺失文件先写本请求标识的临时名，再在同一目录句柄内原子地以不替换方式发布；已存在且摘要相同的文件不重写，摘要不同则停止；本请求独立路径下的来源清单最后写，同样只允许缺失时新增或相同字节时跳过
④ 导出组件：逐个读回目标文件的实际字节并计算摘要，经 sheltie 命令提交回执（请求标识、绑定版本、组件陈述的每个文件摘要）
⑤ sheltie：核对请求存在且无回执、绑定版本一致；按绑定只读打开目标根并核对根身份，按 §3.3 第 3 步的逐段不跟随链接方式打开每个清单文件，自己读取并计算摘要；引擎摘要等于期望摘要、组件陈述与引擎摘要一致时，在一个事务里写入回执（引擎摘要、读取时间、组件陈述）并记为「已送达」；任一不符则拒绝
```

### 3.2 恢复

⑤ 的读回发生在写事务之前，读回与提交之间目标仍可能被改；回执只声明读取时间点的字节，之后的变化按 DL-08 记为观测。③ 与 ⑤ 之间没有原子性。恢复不看来源清单是否存在，只以 ① 的交付请求为基准，按 spec.md DL-06 对每个产物副本与证据摘要读取实际字节并计算摘要：一致的不重写；缺失的清理本请求临时名后补写；不一致的记为送达冲突并停下。随后核对本请求的来源清单：缺失则写入，相同则跳过，不同则冲突；再走 ④ ⑤。

需要单独覆盖的故障窗口：

| 窗口 | 处理 |
| --- | --- |
| 来源清单仍在，但某个目标文件已被改 | 按实际字节判为不一致，送达冲突；来源清单不能覆盖这个判断 |
| 本请求的来源清单不存在，部分文件已写入 | 已写且一致的不重写，补写其余，再新增本请求的来源清单 |
| 回执已提交后，目标文件立即被改 | 回执保持为送达时的历史事实；之后的变化只作为送达观测追加（DL-08），不回写回执 |
| 回执提交前进程被杀 | 重新走恢复，回执只提交一次；重复提交被拒绝，因为请求已有回执 |
| 目标文件缺失或被改，组件仍提交与请求一致的摘要 | 引擎读回的摘要与请求不符，拒绝；组件陈述不能替代读回 |

首版只有不替换写入：最终一步用原子的「不替换」改名（平台 API 在采用时逐一验证）。目标名在检查之后才出现时，改名失败，记为送达冲突，临时名清理掉。已存在且摘要相同的文件只读核对，不需要覆盖；摘要不同则停止，让用户决定是否改用新的结果位置。不存在“先检查、后用普通改名覆盖”的分支。导出组件只清理本请求标识的临时名，不删除目标根里的其他文件。

### 3.3 目标根写入合同

与 C002 T04 管理根的受限句柄和安全原子写用同一套写法，只是作用于结果根：

1. **根的重叠检查。** 授权时和每次导出前，确认目标根不等于、不包含、也不位于管理根之内（按规范化路径与设备号 / inode 双重比较）；任一成立就拒绝，记为送达失败。
2. **根身份。** 导出时打开目标根得到目录句柄，核对设备号与 inode 与绑定记录一致；不一致（目标根被替换或重新挂载为别的目录）就拒绝。
3. **逐段约束。** 导出清单中的相对路径拒绝绝对路径、`..`、空段和平台保留名。从根目录句柄出发，逐段以不跟随符号链接的方式相对打开父目录（`openat` + `O_NOFOLLOW | O_DIRECTORY` 或平台等价物），缺失的目录在父句柄内创建；任何一段是符号链接或不是目录就拒绝。不重新解析完整路径字符串，因此检查之后、写入之前替换某段目录也不会把写入带到根外。
4. **临时文件与发布。** 在最终父目录句柄内以独占方式创建带请求标识的临时名，写入后 `sync_all`，再在同一父目录句柄内做原子的「不替换」改名（§3.2），并同步目录。不使用会静默替换目标的普通改名。
5. **硬链接。** 发布只新增目录项，不会打开已有目标文件写入，因此目标文件的其他硬链接不会被写穿到根外；读取已有目标文件计算摘要时同样不跟随链接。硬链接不作为拒绝条件，只在恢复核对中按实际字节处理。
6. **崩溃清理。** 只清理当前父目录句柄下带本请求标识的临时名，不跟随链接，不触碰其他文件。

采用时列出支持的平台，每个平台分别验证 3、4 两步的 API 语义（包括「不替换」改名）；不能提供等价逐段约束或不替换发布的平台不提供导出，而不是退化为路径字符串检查。拒绝例都放置根外哨兵文件，证明其字节与权限不变。

### 3.4 交付内容

| 内容 | 来源 |
| --- | --- |
| 交付副本 | 交付产物，按导出清单复制 |
| 证据摘要 | 从证据记录生成的只读投影：每个条件的结果、写入方式和原件指针（采用 C004 时）；未采用 C004 时只说明「流程完成」，不给质量结论 |
| 来源清单 | 每个请求独立的相对路径；内容含 Work 标识、Workbook 版本与摘要、候选标识（采用 C004 时）、每个交付产物及证据摘要的摘要（不含本清单自身）、结果根绑定版本、请求标识；生成时间取请求的创建时间，重复生成字节相同 |
| 交接材料 | C005 EX-01，只在请求时导出 |

证据摘要只给指针，原始日志和原始证据留在管理根。证据摘要与来源清单按请求标识分别命名，路径与期望摘要在请求里固定；生成输入不得含本次导出的运行时间。来源清单是给用户看的辅助标识，不是产物恢复的判断依据；清单自身仍由引擎按请求的期望摘要核对后才记送达。

## 4. ADR-D 草案：交付组件边界

状态：`proposed`
日期：2026-09-27
关联 change：C006

### 背景

用户需要把成果交到项目目录或自选目录。architecture.md §6 的 INV-3 实现行规定 `sheltie-runtime` 只写 `SHELTIE_HOME`；CONTEXT.md 与 AGENTS.md 把「引擎」定义为 `sheltie` 二进制，且只写 `~/.sheltie`。宪章 INV-3 的条文本身只禁止写宿主配置和安装。GF-14 规定终态 Work 不再接受写操作。

### 候选

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| E1 runtime 直接写结果根 | 扩大 `confine()` 的根集合，runtime 在生成产物时同时写结果根 | 实现最少 | 用户目录访问混入所有运行操作；中断恢复与 Store 事务纠缠；「引擎只写 `~/.sheltie`」失效 |
| E2a 导出命令组在 `sheltie` 内 | runtime 只写管理根；同一二进制里的独立命令组写结果根 | 分发简单 | 「引擎」是否包含这个命令组产生歧义；需要改 AGENTS.md、CONTEXT.md 的引擎边界 |
| E2b 独立 crate 与独立二进制 | `sheltie` 只写管理根；导出二进制只写结果根，经 `sheltie` 公开命令读请求、交回执 | 两个写入者各写各的根，引擎边界字面不变；与宿主安装工具放在独立 crate 与二进制的既定思路一致（architecture.md「不拆独立安装器」） | 多一个二进制的分发与版本配套（GF-27） |
| E3 维持现状 | 用户自己从管理根复制 | 零新增 | 用户价值缺口不变 |

### 建议

采用 E2b。导出二进制不依赖 `sheltie-runtime`，不写管理根；它对管理根只读，写入 Store 的唯一途径是 `sheltie` 的回执命令。受限文件操作是复用 C002 T04 的实现（抽成共享 crate）还是在导出 crate 内另写，采用时决定，但语义必须满足 §3.3。

### 否决方案

- **把整个 Work 目录放进项目目录。** 冻结副本和原始证据会暴露给用户编辑，破坏摘要核对；`git clean -fdx` 会删除被忽略的内容。
- **协调者复制文件后自报送达。** 违反 INV-6 的精神；自报只能记为声明。
- **终态 Work 上直接改写状态字段记录送达。** 与 GF-14 的字面含义冲突，也会让后来的变化改写历史事实。
- **把导出称作「外围」而放在 `sheltie` 内部绕开边界讨论。** 写入权限由二进制边界表达，不由命名表达。

### 后果

- GF-14 增加终态例外（spec.md DL-07）；
- architecture.md、AGENTS.md、CONTEXT.md、GF-27 按 spec.md §5 修订；
- storage.md 增加交付记录与恢复窗口；protocol.md 增加交付请求读取与回执命令；
- 导出组件需要自己的失败路径测试与逐平台验证。

### 确认方式

- 回执丢失后恢复，目标文件与请求一致时只补记；
- 来源清单仍在但目标文件被改，记为冲突，不覆盖；
- 目标根被替换、某段目录在检查后被换成符号链接、目标根与管理根重叠时拒绝写入，根外哨兵不变；
- 目标文件缺失但组件提交正确摘要时，回执被拒绝；
- 检查之后、改名之前出现同名文件或旧文件被改时，不覆盖，记为冲突；
- 终态 Work 上追加送达记录成功，其他写操作仍被拒绝；
- `sheltie` 集成测试在只读假 `$HOME` 下仍通过，导出二进制的测试证明它不写管理根。
