# C004 产品 delta

状态：`proposed`，实验与实现均 `not_run`。基准：`296313c6f9fcfd0d6348927b73e7a49578581b6c`。本文件是候选变化，不是当前产品合同；采用后再同步到根 `spec.md`、`constitution.md`、`roadmap.md` 与 `contracts/`。

## 1. 定位

**一句话（候选）：** Sheltie 是面向代码库变更的可验收委派层。人写清“做到什么算完”，agent 去做，Sheltie 在固定的候选快照上运行项目已有的本地验收命令，保证验收条件和证据一一对应，失败时把证据交回 agent 继续修，最后交出一份能审阅的交付包。

**范围约束：** v0.3 验证的是，在已有本地验收条件的代码库中，Sheltie 能否通过可接续、可核对、可返工的任务闭环，减少用户的总投入。

**共同基础（与 C005 共用）：** 更换执行者，不得自动放宽任务标准、权限范围和证据要求；最终接收依据来自预先授权的验证机制，不能仅凭执行者自报。执行者可以替换，已登记的审查发现不因替换而消失。

**与 C005 的分工：** 本 package 回答“这份候选凭什么接收”；[C005](../C005-executor-continuity/README.md) 回答“接下来由谁、在什么条件下继续”。两者共用 Work、Attempt、候选快照、执行引用和证据记录，不另建进度系统。

**内部结构：** 合同 + 账本 + 受控接收点。

- 合同：Work 开始时冻结的验收条件，执行中途不能被悄悄改掉；
- 账本：沿用 SQLite 唯一状态权威（INV-7），记录每次尝试、每份证据及其来源；
- 受控接收点：只有当每个必需条件都有有效证据时，正常接口才允许把候选标为“已接收”。

**原则：静态政策、动态计划。** 验收条件、授权范围、重试上限在一个授权版本内保持不变；agent 在范围内怎样拆解、怎样修由它自己决定。放宽政策只能通过一次新的显式授权（新 Workbook 版本或人批准的新合同），不能靠运行中改写。

**筛选原则（不写成不变式）：** 下一版的每项能力，都必须在单宿主、单 agent 场景下带来可测的价值。只在多 agent 下才有意义的能力，推迟到实测瓶颈出现后再决定。

## 2. 首个场景

个人开发者的本地 Git 仓库中一件边界清楚的变更（修 bug、加小功能、重构一个模块）。项目已经具备本地验收条件：工具链、依赖缓存和所需服务已就绪，有能直接运行的验收命令。

```text
人写任务与验收条件 ─▶ Work 开始，合同冻结
        │
        ▼
agent 在编辑工作区实现并提交 ─▶ 本地快照验证器在临时工作区检查 ─▶ Sheltie 接收证据
        ▲                                                         │
        │                有条件失败，且在上限内                      │
        └─────────────────── 证据交回 agent ◀──────────────────────┤
                                                                  │ 全部必需条件有有效证据
                                                                  ▼
                                                   交付包 ─▶ 人审阅，决定合并
        越权、耗尽上限、验证前提缺失、或有“未验证、需人判断”的条件 ─▶ 停下来找人
```

合并、部署都不在 Sheltie 的范围内。Sheltie 交出交付包就结束。

## 3. 候选能力

编号 `VD-nn` 只在本 package 内使用；采用时再并入根规格的 GF 编号。

`VD-01` **验收合同冻结。** Work 开始时，验收条件作为冻结输入进入 Work。每个条件有稳定 id、自然语言说明（给人和 agent 看），以及机器可判断的证据要求：用哪条冻结的验收命令、对应哪一个候选。合同还列出受保护路径和需要带入临时工作区的额外文件（目标相对路径，以及是否允许覆盖提交中的同名文件）。执行中合同不能修改；要改只能取消后以新合同重开，或走一次人批准的授权。

`VD-02` **证据接收与来源记录。** 每份证据至少记录：对应的条件 id、候选标识、完整的验证输入（提交标识，加上额外文件清单及实际交付字节的摘要）、验收规则的冻结版本、执行方式、结果、验证器故障（如有）、起止时间、证据写入方式（验证器取得还是外部回填）。候选、额外文件或规则变化后，旧证据失效，不能沿用：相同提交、不同额外文件属于不同的验证输入。证据接收合同不绑定执行器；v0.3 的执行器是本地快照验证器，具体取得方式见 [design.md](design.md) ADR-A。

`VD-03` **结果闭集，不做等级排序。** 引擎只把证据结果归入 `satisfied | failed | not_verified` 三类。命令完整运行并判定不通过是 `failed`；命令没有启动、超时或被中断是 `not_verified`，并另记验证器故障，不能满足必需条件，也不算作 agent 执行失败。故障原因无法判定时记为“原因未知”，不猜测归类。证据按属性描述（来源、产物、标准、环境、覆盖、局限、是否仍有效），不排高低等级。

`VD-04` **验收命令覆盖不到的条件如实标记。** 合同里有些条件没有对应的机器检查（例如“公开 API 未改变语义”“文档说法准确”），这些条件在交付包里固定标为“未验证、需人判断”。它们不阻止返工闭环结束，但会阻止交付包被标为“全部已验证”。

`VD-05` **返工闭环。** 有必需条件 `failed` 时，失败证据作为输入交回实现节点。这可以用现有的 `back` 边、`max_visits`、`max_retries` 表达。在授权范围和上限内，闭环不需要人插手；越权、耗尽上限、或验证前提缺失时，Work 停下来找人。引擎不读失败日志下结论（INV-1、INV-2），读失败证据、决定怎么修的是协调者。

`VD-06` **受控接收点。** 一个声明了验收合同的节点，只有在每个必需条件都有 `satisfied` 且仍有效的证据，并且合同要求的审查条件满足（VD-09、VD-10）时，才会向 `next` 暴露“接收”出口。这是结构检查，不是业务判断：引擎只比较条件 id、候选标识、规则版本和结果枚举，不理解它们的含义。验证日志、agent 新增测试的结果只是报告，不影响 `next`。

`VD-07` **交付包。** Work 结束时生成一份有界的交付文档：候选标识、合同版本、每个条件的状态和证据指针、尝试次数与返工轮次、未验证条件清单、验证器故障记录、已知局限。交付包是投影，不能反向推进状态（INV-7）。

`VD-08` **本地快照验证器（内核之外）。** 按固定输入、执行检查、记录结果、结束与恢复四个环节，在 `~/.sheltie/tmp` 下的临时工作区运行冻结的验收命令。它只接受已存在的 commit，验证前固定完整提交标识，复制后核对临时工作区确实使用该提交，失败时记为快照准备失败、不退回 `HEAD`；不写用户仓库；不安装工具链、不拉起服务、不补凭据，缺少前提就报告缺什么；不宣称隔离。细节见 [design.md](design.md) §3。

`VD-09` **审查声明与阻断项。** 合同为审查指定一种作用，Work 开始时冻结，执行中不能改（协调者不能在看到结果后把“必要条件”改成“提供建议”）：

| 审查作用 | 对接收的影响 |
| --- | --- |
| 提供建议 | 记录发现，不影响接收 |
| 构成必要条件 | 必需审查已完成、且没有未处置的阻断项，接收出口才合法 |
| 触发升级 | 审查声明带合同定义的升级标记时，Work 停下来找人 |

审查仍由普通节点完成。它提交的是**带来源的结构化声明**：对应的候选快照、审查是否完成、发现列表（每条有稳定 id 和“是否阻断”标记）。引擎只核对这些闭集字段，不读发现的自然语言内容，也不判断发现是否成立。四条规则：

1. **未完成不等于通过。** 审查缺失、中断、格式错误、来源不满足合同要求时，审查条件保持未满足。
2. **审查者可以接替。** 审查者因额度、故障或能力不足中断时，合格的备选执行者可以继续审查同一候选；已有记录保留。
3. **发现不因替换消失。** 已登记的阻断项在被处置前一直有效。另一审查者可以复核，但不能覆盖原发现。提交新候选后，受影响的条件重新检查，旧阻断项延续，需要逐条处置，不能因为快照改变就清空。
4. **误判有处置路径。** 处置类型只有三种：已解决（附证据指针）、不适用、接受风险。v0.3 只允许用户处置（单用户批准语义，ADR-B）。原报告不删除；处置不能豁免合同规定不可放宽的条件。

`VD-10` **执行身份分三栏记录。** 每个实现与审查尝试的执行身份分开记录：

- **声明**：谁声称执行了这次尝试（v0.3 中来自协调者报告）；
- **观测**：系统实际观测到了什么、通过什么通道（v0.3 通常为空，受信来源见 [C005](../C005-executor-continuity/README.md)）；
- **强制**：哪些分离要求得到了实际实施。

合同要求“作者与审查者分离可验证”时，只有声明、没有观测的记录不满足该条件，接收条件保持未满足；不能一边标为“自报”，一边显示“独立审查已满足”。低保证模式（按声明的执行者关系检查）必须在 Work 开始前由合同选定，交付包如实显示所用模式。

参与关系沿本候选相关的实现尝试与产物来源推导，不只看最后一次 Attempt：A 完成主要实现、B 只整理格式时，A 仍算参与者。推导只覆盖 Sheltie 管理范围内的记录；“账本中没有参与记录”只说明没有已知记录。

`VD-11` **可选的保留验收样本。** 合同可以声明一组保留样本：它们对应公开的任务要求，不作为任务输入交给实现者，由验证器在验收时运行。三条约束：

- 保留样本不能暗藏未告知的新要求；因未告知的要求失败，记为标准缺口，不记为执行失败；
- 样本内容一旦在失败反馈中完整返回给执行者，即视为已暴露，交付包如实标注，不再算作独立检查；
- 当前未隔离的单用户模式不保证执行者无法读取样本；候选代码在验收阶段运行时同样可能接触样本。它能否减少对已知测试的过度适配，是实验要回答的问题，不是已知收益。

这是可选模板，不是默认要求。

## 4. 承诺合同

每条承诺都必须写明信任前提，并区分两种强度：**正常接口会拒绝**（通过 Sheltie 命令做不到）和 **执行者无法绕过**（即使执行者有同样的 OS 权限也做不到）。在单用户信任模型下，v0.3 大多只能做到前一种。

| 承诺 | 信任前提与机制 | 强度 | v0.3 建议 |
| --- | --- | --- | --- |
| 正常接收接口不会把缺条件的候选标为已接收 | 引擎在接收点做结构检查（VD-06）；前提是执行者只通过 CLI 操作 Store | 正常接口会拒绝 | 实现；对外公开单用户信任前提 |
| 执行者不能伪造验收证据或接收状态 | 本地验证时，项目代码以用户身份运行，能改写 `~/.sheltie`；只有签名证明等执行方独立于本机的方案才可能做到 | 执行者无法绕过 | 本地路径下明确声明不承诺；交付包显示证据写入方式 |
| 动作符合用户的授权范围 | 门槛批准绑定具体 Work 和节点；主体取真实 OS 身份（依赖 C002 N04） | 正常接口会拒绝 | 保留单用户批准语义；不声称真人在场 |
| 执行期间访问不到范围外的资源 | 依赖宿主的沙箱和权限机制，不由引擎提供；临时工作区只分开工作目录 | 两种强度都不承诺 | 利用宿主已有机制，列为待验证的防误操作措施；不承诺隔离 |
| 必需审查未完成或有未处置阻断项时，不暴露接收出口 | 引擎对 VD-09 的闭集字段做结构检查；前提同第一行 | 正常接口会拒绝 | 实现 |
| 换审查者不会抹掉已登记的发现 | 发现只追加、不覆盖；处置单独记录（VD-09） | 正常接口会拒绝 | 实现 |
| 作者与审查者确实分离 | 需要受信来源的执行观测；v0.3 只有协调者声明（VD-10） | 严格模式：缺观测即条件未满足，不承诺已分离；低保证模式：按声明检查，正常接口会拒绝 | 实现两种模式与交付包标注；强制分离留给受信来源 |
| 标为“验证器取得”的证据确实由验证器运行检查产生 | 该写入方式只能由验证器命令自己运行冻结命令产生，不接受外部传入结果；其他写入一律标“外部回填”（design.md §4.4） | 正常接口会拒绝；同权限程序仍可改库 | 实现；不宣称身份边界 |
| 证据指向的验证输入就是实际运行的内容 | 验证前固定完整提交标识；复制后核对；额外文件按实际交付字节记摘要（design.md §3.2 a、d）；前提是验证器和参照记录本身完好 | 正常接口会拒绝 | 实现；准备期间源仓库变化的场景要有测试 |
| 保留样本不被实现者读取 | 只保证不作为任务输入交出；读取限制需要隔离（VD-11） | 两种强度都不承诺保密 | 作为可选模板，如实声明 |

## 5. 保证范围声明（对外用语候选）

可以说：

- 在声明并冻结的验收合同内，缺证据、证据失效或检查未实际通过的候选，不会通过 Sheltie 的正常接口被标为已接收；
- 交付包里每个“已验证”都能追到一次具体的检查运行、一个具体的候选快照和一个冻结的规则版本；
- 验收命令覆盖不到的条件会被明确列为“未验证、需人判断”；
- 无需为了启动验收而推送远端或配置 CI 接入；在项目依赖与本地服务已准备好的情况下，可以直接运行已有的验收命令；
- 合同要求审查时，审查未完成、或有未处置的阻断问题，候选不会通过正常接口被接收；换审查者不会让已登记的问题消失；
- 交付包写明每次审查的执行身份是声明还是观测，以及合同选用的分离模式。

不能说：

- Sheltie 保证了作者与审查者独立（v0.3 只有声明，除非另有受信来源）；
- 审查通过说明候选正确，或审查发现一定成立；
- 保留样本对执行者保密，或已证明能减少投机；

- Sheltie 验证了真人当场批准（它只记录 OS 用户）；
- Sheltie 能防止同等 OS 权限的程序篡改控制状态或伪造证据；
- 检查通过就是业务正确；
- 临时工作区或 worktree 提供了隔离；
- 本地验证一定不需要网络或凭据（取决于项目）；
- “不支持部署”保证了验收命令没有外部影响（这只是范围声明，项目的构建脚本和测试可能有副作用）。

## 7. 后续决策与触发条件

下列方向不在本版本内。每项写明什么情况下才重新讨论。

| 方向 | 触发条件 | 已知约束 |
| --- | --- | --- |
| CI 证据来源 | 团队仓库，或需要独立于本机的证据 | 外围用已登录的 `gh` 读取，引擎不存凭据；来源限定和 CODEOWNERS 只在团队仓库有意义（design.md §3.5） |
| 验证缓存 | 阶段 1 显示冷构建是主要摩擦 | 缓存不能在快照之间传递污染，不能写到 `~/.sheltie` 以外 |
| 并行草稿（GF-25） | 实测显示单 agent 串行是被接受任务的主要耗时来源 | 要限制的是待审、待集成的在制品数量，而不是 agent 数量；写集不相交也可能有语义冲突 |
| 动态展开（GF-26） | 一个 Workbook 版本无法表达真实任务的拆分，且回环方案已证实不够 | 与 GF-25 分开决策 |
| 强制职责分离 | 出现受信执行来源（C005 驱动层、宿主可信事件或外部平台） | 请求配置、实际配置与会话身份分开记录；两个会话不等于两个模型，两个模型不等于错误相互独立 |
| 审查者自动接替、执行者选择、额度与等待 | 见 C005 | VD-09 的发现保留规则对 C005 同样生效 |
| 第二宿主（GF-23，MCP 接口与多宿主） | 由 C005 第一阶段的人工接续实验先行验证 skill 层面的两宿主 | 宿主差异由 skill 吸收 |
| 增强授权 | 出现无人值守或多用户需求 | 授权绑定具体动作（交易授权）；无人值守采用预授权 |
| 预算门禁（GF-24） | 有真实运行数据可建基线 | 预算分三栏：能强制的、估算的、不可知的；每栏配质量判据 |
