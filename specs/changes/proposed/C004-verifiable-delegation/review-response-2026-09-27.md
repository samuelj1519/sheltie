# C004 对独立审阅的答复（2026-09-27）

答复对象：[independent-review-2026-09-27.md](independent-review-2026-09-27.md)。本文件逐条说明采纳情况和修订位置；package 状态仍为 `proposed`，阶段 1、阶段 2 实验与失败路径测试均为 `not_run`。修订只改本目录内的提案文档，不改根规格、合同或代码。

判断分四类：**采纳**（前提成立，按建议修改）、**部分采纳**（前提部分成立或改法有调整）、**已覆盖**（方案已有，只做措辞对齐）、**纠正**（审阅的事实前提有误）。

## 逐条答复

### 1. 接收规则限定可接受的证据来源（高）

**判断：采纳。**

**理由：** 原 VD-06 写明引擎“只比较条件 id、候选标识、规则版本和结果枚举”，比较项里没有来源。原 design.md §2 只要求证据“满足 VD-02 的全部字段”，有来源字段不等于限定其取值。对外部回填的约束只出现在交付包展示上（原 ADR-A 确认方式、validation.md §6），接收出口没有随之关闭。回填的 `satisfied` 因此可能打开 `main` 边。

**修改位置：**

- spec.md VD-01：每个条件新增“允许的证据来源”闭集。v0.3 只允许“本地验证器取得”，“外部回填”不能列入。
- spec.md VD-02：写明外部回填的证据照常记录，但不满足任何必需条件。
- spec.md VD-06：比较项加入证据来源；明确外部回填的 `satisfied` 不能打开接收出口。
- design.md §2、§4.4：说明接收出口核对来源；ADR-A 的后果与确认方式同步修改。
- validation.md §6：新增一对反例。两份证据其余字段相同，一份由验证器命令取得，另一份只把来源改为外部回填；前者打开接收出口，后者不打开。
- validation.md §3、ADR-A 建议：注明阶段 1 的证据全部是外部回填，所以阶段 1 不检验接收门控。

承诺强度不变，仍是“正常接口会拒绝”，不升级为同权限防伪造。

### 2. 明确 `not_verified` 的状态转换（高）

**判断：采纳。**

**理由：** 原 design.md §2 只定义了“全部 `satisfied` → `main`”和“有 `failed` → 只有 `back`”。只有 `not_verified` 时哪条边合法没有规定。原 spec.md §2 写“验证前提缺失 → 停下来找人”，但按 GF-14，非门槛 `blocked` 只能 `work cancel`。审阅指出的缺口属实。

**修改位置：**

- spec.md VD-05 改为四行的走向表。只有 `not_verified` 或缺证据时，验证节点的 Attempt 不能提交，只能 `attempt fail`，并在同一 Occurrence 内按 `max_retries` 重试；不走 `back`，不消耗实现节点的 `max_visits`；重试耗尽时 Work `blocked(retries_exhausted)`，只能 `work cancel`。
- design.md 新增 §2.2，逐类写出快照准备失败、前提缺失、超时、中断、原因未知的可观察下一步。
- spec.md §2 流程图的停止条件同步修改。

C005 的可恢复等待不作为硬依赖：v0.3 如实停止，用户补好环境后以同一合同重开 Work；若 C005 以后被采用，可以把这类停止变为可恢复。README 的“依赖”写明了这一点。

### 3. 受控接收点与现有完成语义的关系（高）

**判断：部分采纳。**

**理由：** 原设计其实已隐含答案：接收就是 `verify` 的 `main` 边，`deliver` 是终点（原 design.md §2）。但 spec.md §1 和原承诺表写“标为已接收”，读起来像另有一个状态，审阅要求统一用语是对的。审阅没有指出一个更关键的缺口：Workbook 若存在不经合同节点就到终点的路径，Work 会 `succeeded`，而候选从未被接收。

**修改位置：**

- spec.md §1、VD-06、VD-07：写明“接收 = 经过接收出口”，不另设接收状态，也不另加命令；交付包只用“候选已经过接收出口”和“候选未接收”两种说法。
- spec.md VD-06、design.md 新增 §2.1：声明合同的 Flow 在装入时校验，每条到终点的路径在最后一次经过候选生产节点之后，必须经过接收出口。该校验与 C007 的路径覆盖是同一种算法。
- design.md §2.1 用一张表说明四种情形下 `next`、Work 终态与交付包用语一致：无机器条件、只有需人判断的条件、审查未完成、设了 `gate`。
- spec.md §6：写明采用后先修改宪章 INV-1、INV-5、INV-6 和 GF-11、GF-14 与协议，再进入 Rust；GF-14 行改为终点可达性校验和新增停止原因。

### 4. 收窄“冻结验收规则”的可执行承诺（中）

**判断：采纳，并补两处审阅未列出的矛盾。**

**理由：** 原 design.md §3.2 c 的“构建配置中影响测试选择的部分”无法作为机器可判定的清单。另外：

- 原文同一句写“对应条件判 `failed`，交给人判断”，但按 design.md §2，`failed` 会自动走 `back` 返工，并不会停下找人。
- 判断“改动了受保护路径”需要冻结的基线提交，而原 VD-01 没有冻结基线。

**修改位置：**

- spec.md VD-01：冻结基线提交、验收命令与脚本、声明的环境输入、受保护路径的显式 glob 清单；清单之外的因素作为已知局限写进交付包。
- design.md §3.2 c 重写：命中受保护路径即越权，Work `blocked(scope_violation)` 停下找人，不判 `failed`，不走 `back`；并写明不从“验收命令运行成功”推出规则未被改变。
- spec.md VD-05 走向表中，越权排在最高优先级。承诺表新增两行（越权、验证器故障），§5 “不能说”新增一句。
- design.md §9 第 10 问：越权后是否允许用户一次批准送回实现节点，按阶段 1 中越权的实际频率决定。
- validation.md：新增“清单之外的文件影响测试选择”一行；阶段 1 记录受保护路径命中次数和清单之外影响的实例。审阅要求的“源仓库并发变化”“候选 checkout 不符”两行已在原表中。

### 5. 把 VD-09 设为条件性范围（中）

**判断：已覆盖，做措辞对齐。**

**理由：** “先测量、结果不支持就推迟”已写在原 design.md §9 第 8 问、review.md §8、README 采用条件和 validation.md §3。审阅指出的真实问题是措辞不一致：原承诺表对 VD-09 相关行写“实现”，§5 对外用语也写成无条件承诺。

**修改位置：**

- spec.md VD-09 开头加入条件说明。
- 承诺表中 VD-09 相关两行改为“视阶段 1 结果而定”；VD-10 严格模式影响接收的部分同样改为条件性。
- §5 相应用语加“若 VD-09 随 v0.3 实现”。
- validation.md §6 表末注明，VD-09 相关各行只在其实现时执行。
- README 采用条件写明按阶段 1 的两项计数决定。

## 复审（e87eb07）答复

复审对象：上述修订后的提案（提交 e87eb07）。复审没有写入文件，意见以对话形式给出；本节按原编号记录与 C004 相关的三条。

### Spec1. 装入校验按节点做，接收出口却是边（高）

**判断：采纳。** 原 VD-06 与 design.md §2.1 要求“每条路径最后一次经过候选生产节点之后必须经过接收出口”，又称与 C007 的路径覆盖“是同一种算法”。C007 删的是节点；接收出口是合同节点的一条 `main` 边。合同节点另有一条 `branch` 边直通终点时，每条路径都经过了合同节点，按节点判定会通过，但候选没有经过接收出口，“Work `succeeded` 蕴含经过接收出口”随之失效。本节上文第 3 条答复中“同一种算法”的说法由此更正。

**处理：** 改为按边校验：从图中删去接收出口这条边后，入口与每个候选生产节点都不能到达任一终点。与 C007 的关系改写为“同一类可达性检查，删去的对象不同”。验证节点也被标为候选生产节点时，结构上没有漏洞；它验证之后改动候选的情况，由证据绑定候选快照（VD-02）在运行时处理。

**修改位置：** spec.md VD-06；design.md §2.1；validation.md §6 新增“合同节点另有 `branch` 边直通终点”反例。C007 design.md §3 的对应表述同步修改。

### Spec2. VD-09 推迟时，“合同要求审查”仍然悬空（高）

**判断：采纳。** VD-09 是否实现取决于阶段 1，但 README 的采用后成功标准和 §2.1 的组合表都无条件写着“合同要求审查时……接收条件保持未满足”。VD-09 推迟时没有审查条件可以核对，这两处就是没有机制支撑的承诺。复审给了两种改法：降低承诺，或禁止声明加替代路径。本答复选后者，因为它不需要新机制。

**处理：** VD-09 推迟时，把审查作用声明为“构成必要条件”的合同装入失败；需要人把关审查的，用现有机制在审查节点设 `gate = true`；交付包写明“审查不属于接收条件”，列出审查节点的执行事实与批准记录。“提供建议”仍可声明，只做记录。README 成功标准与 §2.1 组合表中的相应行改为以 VD-09 是否实现为条件。

**修改位置：** spec.md VD-09；design.md §2.1（接收节点说明与组合表）；README.md 采用后成功标准；validation.md §6 新增两行。

### Spec6a. 验证器故障的计数与 C005 对齐（中）

**判断：采纳。** C004 让验证器故障以 `attempt fail` 消耗验证节点的 `max_retries`，C005 EX-05 却写“业务重试只在内容失败时消耗”。两份都采用时口径互相矛盾。

**处理：** 以 C005 EX-05 的新措辞为准：节点自身的执行失败（`attempt fail`）消耗 `max_retries`，验证器故障属于此类；执行者中断与资源等待不消耗。VD-05 补一句说明。

**修改位置：** spec.md VD-05。
