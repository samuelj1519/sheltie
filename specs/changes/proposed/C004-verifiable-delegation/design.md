# C004 候选设计

状态：`proposed`，实现 `not_run`。基准：`296313c6f9fcfd0d6348927b73e7a49578581b6c`。本文件是候选机制，不是当前架构；两份 ADR 草案在采用时移入 `specs/decisions/` 并编号。

## 1. 分层：内核仍然业务无关

GF-01 要求内核代码里不出现 Git、Cargo 等业务词汇。本设计把知识分三层：

| 层 | 知道什么 | 不知道什么 |
| --- | --- | --- |
| sheltie-core | 条件 id、候选标识（不透明字符串）、证据记录的结构、结果闭集 `satisfied / failed / not_verified`、审查执行 / 发现 / 处置的闭集字段、接收点的结构检查 | 候选标识是不是 commit；验收命令是什么；审查发现说的是什么 |
| sheltie-runtime | 存取证据记录、摘要、主体、事务 | 条件是否“合理”；日志说了什么 |
| 外围（Workbook + 本地快照验证器） | 候选就是 commit SHA；快照怎样导出；运行哪条验收命令；哪些路径受保护 | Work 状态怎样推进（只能通过 CLI） |

本地快照验证器不是 Workbook 的一部分：Workbook 是纯定义，`workbook add` 不执行脚本（GF-17）。验证器是内核之外的组件，只通过公开接口写入证据。它的形态（外部脚本、独立命令组、独立 Cargo 包）由 ADR-A 决定。

core 的接收检查是纯函数：输入是冻结的合同、当前证据集和审查记录，输出是每个条件的状态和“接收”出口是否合法。它不做 I/O，也不读自然语言（INV-1、INV-2）。

## 2. 用现有图结构表达返工闭环

返工闭环不需要新的边类型。一个代码变更 Workbook 可以这样写（示意，不是合同）：

```text
implement ──main──▶ verify ──main──▶ deliver
    ▲                  │
    └──────back────────┘
```

- `implement`：agent 在宿主提供的编辑工作区里实现，自己提交 commit，输出候选标识；
- `verify`：声明验收合同的节点。该节点的 Attempt 调用本地快照验证器取得证据；每个必需条件都 `satisfied` 时 `main` 边才出现在 `next` 中（VD-06）；有 `failed` 时只有 `back` 边合法，失败证据作为 `implement` 下一次到达的输入；
- `max_visits` 与 `max_retries` 就是重试上限，耗尽后 Work `blocked`，交给人；
- `deliver`：生成交付包；是否设 `gate = true` 由 Workbook 作者决定。

合同要求审查时，在 `verify` 之后加一个普通的 `review` 节点，审查规则见 §4：

```text
implement ──main──▶ verify ──main──▶ review ──main──▶ deliver
    ▲                  │                 │
    └──────back────────┴──────back───────┘
```

新增的只有合同节点“按证据和审查声明限定出边”这一条规则。它与路线图“其他保留决定”里的机器路由有交集，采用时要一并定下：是加一种显式节点类型，还是作为合同节点的固定行为。默认仍然是协调者选边；受控接收点只收窄 `next`，不替协调者选边。

**哪些结果只是报告，哪些是接收条件。** 验证日志、agent 新增测试的结果、验证器的耗时，都是供协调者理解的报告，不影响 `next`。只有合同中声明为必需的条件，且其证据满足 VD-02 的全部字段、结果为 `satisfied`、仍然有效，才构成接收的必要条件。

## 3. 本地快照验证器

编辑和验证分开：agent 继续使用宿主提供的编辑工作区；提交候选后，由验证器在一个临时工作区里检查。这样 Sheltie 不需要同时管理编辑工作区、agent 会话和验证环境。

### 3.1 四个环节

| 环节 | 必须讲清楚的事情 |
| --- | --- |
| 固定输入 | 完整的验证输入是什么：候选提交的完整标识、额外文件清单（目标相对路径与实际交付字节的摘要）、验收规则的冻结版本；复制后核对临时工作区确实使用这个提交 |
| 执行检查 | 在哪个临时工作区、用什么命令和环境变量运行；需要哪些已经准备好的前提；超时多长 |
| 记录结果 | 检查结果、日志摘要、起止时间与候选快照、规则版本关联；候选或规则变化后，旧结果不自动沿用 |
| 结束与恢复 | 超时、中断、清理失败怎样记录；先保存证据，再清理本次创建的临时资源 |

### 3.2 边界

**a. 不写用户仓库（INV-3）。** Sheltie 不替 agent 做 commit，只接受已存在的 commit SHA。临时工作区建在 `~/.sheltie/tmp/` 下，不在用户仓库里执行 `git worktree add`，因为那会写入用户仓库的 `.git/worktrees/`。候选做法是从用户仓库 `git clone --local --no-hardlinks --no-checkout` 到临时目录，再 detached checkout 到候选 SHA；这只读取用户仓库。`--no-hardlinks` 复制对象文件而不是建立硬链接，避免临时工作区与用户仓库共用对象文件。不选 `git archive`，因为它遵守 `.gitattributes` 的 `export-ignore` 和 `export-subst`，导出内容可能与 commit 不一致，而 `.gitattributes` 本身又是 agent 能改的文件。

**快照一致性另有两条验收条件。** `--no-hardlinks` 只改变对象的复制方式，不把整个操作变成原子快照；Git 文档仍警告本地 clone 可能与源仓库的并发修改发生竞争。所以：

- 开始验证前，候选已经固定为完整的提交标识，之后不再按分支名或 `HEAD` 重新解析；
- 复制完成后，核对临时工作区确实包含并检出了这个提交。缺失或复制异常，记为“快照准备失败”（验证器故障，结果 `not_verified`），不退回复制时的 `HEAD`。

首版只保留本地复制一种实现；是否改用 Git 的常规传输路径，由失败路径测试的结果决定（§9 第 9 问）。要用测试证明的是：源仓库在准备期间变化，不会让系统验证了另一个候选、却仍标记为原候选。

**b. 验证命令的副作用不属于引擎写入。** 验收命令会写构建缓存、依赖缓存（例如 `~/.cargo`），项目的 `build.rs` 和测试也可能访问其他资源。INV-3 在本设计中的解释是：引擎和验证器自己的写入只在 `~/.sheltie`；验收命令运行项目代码产生的副作用属于项目自身，列入“不承诺”。这条解释需要在采用时写进宪章或 ADR，不能默认成立。

**c. 规则必须冻结，不能只记录版本。** 如果验收脚本放在候选代码里，记录它的版本只能说明它被改过，挡不住篡改；而且“能发现被改过”本身有前提：用作参照的记录和验证器自己没有被改动。验收命令和脚本取自冻结合同（Workbook 资源或 `work start` 输入）或基线快照；候选改动了受保护路径（验收脚本、既有验收测试、`.gitattributes`、构建配置中影响测试选择的部分），对应条件判 `failed`，交给人判断。agent 新增的测试照常运行，结果与既有验收基准分开报告，不参与接收判断。

**d. 额外文件进入验证输入的身份。** 默认只用已提交的内容。`.env`、本地配置等需要的文件在合同里显式列出，由验证器复制进临时工作区；未列出的不复制。临时工作区一旦包含提交之外的文件，一个提交标识就不足以描述本次验证输入。验证输入记为：

```text
提交标识 + 额外文件清单（每项：目标相对路径、实际交付给验证器的字节摘要）+ 验收规则版本
```

- 相同提交、不同额外文件，是不同的验证输入，不能复用已有的“通过”结论；
- 摘要按复制进临时工作区的实际字节计算，不按源文件的声明；
- 额外文件覆盖提交中的同名文件，必须由合同显式允许，并写进验证输入的描述；未经允许的覆盖记为“快照准备失败”。

这与“输入按字节冻结、输出不可变”的现有方向一致，只是把额外的输入来源完整纳入。

**e. 检查失败与验证器故障分开。**

| 发生了什么 | 证据结果 | 另记 |
| --- | --- | --- |
| 命令完整运行，按验收规则判定通过 | `satisfied` | — |
| 命令完整运行，判定不通过 | `failed` | — |
| 快照准备失败（临时工作区缺少候选提交、复制异常、未经允许的覆盖） | `not_verified` | 验证器故障：快照准备失败，不退回 `HEAD` |
| 命令没有启动（缺工具链、缺前提） | `not_verified` | 验证器故障：前提缺失，附缺失项 |
| 超时或被中断 | `not_verified` | 验证器故障：超时或中断 |
| 清理失败 | 不改变已记录的结果 | 验证器故障：清理残留，附路径 |

验证器进程正常结束不等于任务验收通过；非零退出也不一概算作 agent 执行失败。这延续了“执行事实与业务结论分开”（GF-11）。

**f. 超时清理。** 超时后终止整个进程组，因为测试可能拉起常驻服务。macOS 没有 cgroup，清理不干净的情况如实记录，不宣称已清理。

**g. 冷构建与缓存。** 每个快照都是新目录，Rust 等项目会从头编译。共享 target 目录能提速，但 `build.rs` 的缓存会在快照之间互相污染，而且会写到 `~/.sheltie` 以外。v0.3 默认不共享；冷构建耗时作为阶段 1 的重点摩擦测量，再决定是否提供受控的缓存选项。

### 3.3 不承诺的事

- **临时工作区不是隔离。** 它只分开工作目录。验证命令与 agent 以同一 OS 用户运行，能访问同样的文件、网络和凭据。
- **“由 Sheltie 拉起”只证明执行来源。** 它不证明进程权限受限，也不证明项目代码没有影响其他资源。
- **证据可被同权限程序伪造。** 项目代码在验证时以用户身份运行，理论上可以改写 `~/.sheltie` 下的状态。在单用户信任下，这是公开的非承诺。
- **不需要网络是有条件的。** 是否需要网络、凭据或本地服务取决于项目；以 Cargo 为例，离线运行依赖本机已有的依赖缓存。

### 3.4 验证环境合同

验证 clone 不作为长期的特例保留，而是一般规则的第一种实现：**内核声明环境要求、记录结果；外围组件按授权提供环境。首版只支持已经验证过的一种实现。**

| 环节 | 由谁负责 | 要记录的内容 |
| --- | --- | --- |
| 环境要求 | 冻结合同 | 需要什么样的环境：对应哪个候选或基线、需要哪些输入 |
| 提供环境 | 外围组件（首版：本节的验证 clone） | 实际使用的基线或候选、环境由哪个组件以什么方式创建、带入了哪些输入 |
| 核对对应 | 外围组件，结果写入 Store | 环境是否确实对应要求的候选；不对应时记为准备失败 |
| 保留与释放 | 外围组件 | 先保存证据再释放；释放时间；释放失败的残留 |

宿主创建的环境同样要核对对应关系，不能假定宿主已经对好。例如 Claude Code 的 worktree 默认从远端默认分支创建（`worktree.baseRef: "fresh"`），不是当前 `HEAD`；没有 remote 时又退回本地 `HEAD`。同一配置在不同机器上可能得到不同基线。worktree 还会写入仓库共享的 `.git` 数据，属于授权范围和测试的问题，首版不采用。

C005 中“新执行者使用分开的工作区”沿用同一合同。

### 3.5 CI 作为后续证据来源

证据接收合同不绑定执行器：VD-02 和 VD-06 对本地验证和 CI 一视同仁。CI 接入后置，由团队仓库或需要独立于本机的证据时触发。届时的做法和信任前提：

- 外围集成用用户已登录的 `gh` 读取运行结果（`gh run view --json` 可给出 `headSha` 和结论），核心引擎不保存凭据；
- 必需检查绑定特定 GitHub App；workflow 文件受 CODEOWNERS 约束；skipped、neutral 一律 `not_verified`；`headSha` 必须等于候选快照；
- **这些前提只在团队仓库中有意义。** 个人仓库里 agent 使用用户本人的凭据，能改 workflow 文件，CODEOWNERS 的审批人就是用户自己，token 权限足够时甚至能改分支保护。所以在个人场景下，CI 的可信度并不高于本地验证，这是 v0.3 选择本地优先的主要理由。

## 4. 审查声明与阻断项

### 4.1 三类记录分开保存

| 记录 | 内容 | 写入后 |
| --- | --- | --- |
| 审查执行 | 哪次 Attempt、对应哪个候选快照、是否完成、执行身份三栏（VD-10） | 不可改；中断的执行保留为未完成 |
| 审查发现 | 稳定 id、是否阻断、首次登记的候选、登记它的审查执行 | 只追加，不覆盖，不删除 |
| 处置决定 | 针对哪条发现、处置类型（已解决、不适用、接受风险）、证据指针、处置人、对应候选 | 只追加；v0.3 处置人只能是用户 |

发现的自然语言说明放在审查文档里给人和 agent 看；引擎只读 id、阻断标记和处置类型。发现 id 由审查者在结构化声明中给出，引擎只核对格式和唯一性，不判断两条发现是否说的是同一件事。

GF-05 已经要求重试和回环产生新记录、不覆写旧的，这三类记录沿用同一原则；新增的只是它们如何影响接收。

### 4.2 接收条件

合同作用为“构成必要条件”时：

```text
可接收 =
    每个必需机器条件都有有效的 satisfied 证据（VD-06）
    且当前候选有一次已完成、来源满足合同要求的审查执行
    且每条阻断发现都有合同允许的处置
    且必要授权满足
    且证据、审查执行都对应当前候选与规则版本
```

审查缺失、中断、格式错误、来源不满足，都让第二项不成立。无审查的合同不承担这些条件，GF-14 对无审查 Flow 的支持不变。

### 4.3 替换与新候选

| 情况 | 规则 |
| --- | --- |
| 审查者中断，尚无完整结论 | 合格备选继续审查同一候选；已有记录保留；中断不算通过 |
| 已有有效的阻断发现 | 另一审查者可以复核并登记新发现，原发现持续有效，直到被处置 |
| 原发现可能是误报 | 用户以“不适用”处置并写明理由；原报告不删除 |
| 提交了新候选 | 机器条件重新验证；新候选需要一次新的完成审查；旧阻断发现延续，逐条处置，“已解决”必须指向新候选上的证据 |

这里的基本规则是：**执行者可替换，已登记的审查发现不因替换而消失。** 它同时防止“反复换人直到有人给出通过”，也支持额度中断后的审查接替。谁有资格接替、怎样选择备选，由 C005 决定。

### 4.4 协调者的写入边界

协调者可以发起合法状态转换（领取、提交、选择合法出边），可以提交带来源标记的声明；不能把自己提交的内容标成验证器观测，也不能改写已有证据和发现。

只把某个命令命名为“验证器写入接口”，并不形成身份边界：如果协调者也能调用同一接口、填写同一来源字段，区分就只是约定。所以“验证器取得”这一写入方式只能由验证器命令自己运行冻结的验收命令后产生，接口不接受外部传入的结果；其他路径写入的证据一律标为“外部回填”。这让“验证器以独立命令组交付”（§9 第 5 问）更有理由。

在单用户信任下，这仍然只是“正常接口会拒绝”：同权限程序可以直接改 Store。文档必须写明哪些边界只是接口约束，哪些得到了实际保护。

## 5. 可选的保留验收样本

区分三种东西：公开的任务要求（例如“过期时间使用毫秒”）、可复现的开发检查、不交给实现者的保留样本。保留样本只用来检查实现是否过度贴合已知测试，必须对应公开要求。

- 样本放在合同引用的冻结资源里，由验证器在验收时带入临时工作区；它不出现在任务书中；
- 失败反馈只给出失败的条件和必要的诊断，不回传完整样本；若为调试需要回传了完整样本，该样本记为已暴露；
- 当前单用户模式下，样本对同一 OS 用户可读，候选代码在验证时也能接触它。宿主的文件读取限制或沙箱可以降低风险，但属于宿主加固（§6），不是 Sheltie 的承诺。

## 6. 宿主权限加固与受限调用通道（待验证，不作承诺）

可以用宿主的权限配置降低误操作风险，例如禁止 agent 直接写 `~/.sheltie/store.db`。但有两个已知限制，所以它只算防误操作加固：

- 宿主沙箱的禁写规则同样作用于 agent 调用的 `sheltie` 子进程，简单禁写会让正常 CLI 操作失败；
- 宿主的 Bash 权限规则按命令文本匹配，换一种写法就能绕开，不是安全边界。

本 package 不写宿主配置（INV-3），只在文档里给出建议配置。建议配置在列入文档前，必须走真实宿主路径测试两件事：该拒绝的确实被拒绝；正常的 Sheltie 操作没有被挡住。

### 6.1 GF-22 实验登记：通过宿主受限调用通道访问 Sheltie 控制操作

这项实验属于 GF-22（隔离与权限求值），不是 C004 或 C005 的采用前提，登记在这里是因为它直接关系 §3.3 和 §4.4 的承诺强度。Claude Code 的 `sandbox.excludedCommands` 是候选实现之一，它能让某个命令在沙箱外运行，但没有 managed-only 的锁定方式。

实验要分开验证三件事：让某个命令在沙箱外运行；允许 agent 调用这个命令；允许这个命令执行哪些操作。只做到前两件，不等于形成了可信的控制接口。

| 风险路径 | 为什么 | 实验要证明 |
| --- | --- | --- |
| 排除整个 `sheltie` 后自批门槛 | 直接写 `store.db` 被挡住，但沙箱外的 `gate approve` 仍能更新状态；Bash 权限规则按命令文本匹配，不是围绕某个程序的完整边界 | 正常任务操作可用；批准、修改政策、伪造验证来源等操作仍受各自约束 |
| 沙箱外的验证入口把候选代码带到外面 | 验证命令会运行项目代码（如 Cargo 的 `build.rs`），子进程继承验证入口的非受限权限 | 受信组件核对请求、准备验证、记录结果；候选代码在低权限验证环境中运行；控制状态、批准凭证和证明材料不进入候选代码的执行环境 |
| 内置 Bash 沙箱与整进程沙箱混写 | 内置沙箱只约束 Bash 命令及其子进程；文件工具、hooks、MCP 要另外覆盖。整进程沙箱把这些都纳入外层边界，但命令排除不能解除外层限制 | 实验先声明采用哪一种边界。内置沙箱：逐项覆盖其他工具与通道。整进程隔离：需要外部预先存在的受限请求处理机制，可由宿主或前台组件提供，不必是系统服务 |
| agent 改写宿主配置扩大权限 | 用户主动关闭保护属于用户的选择；要防的是执行者代替用户改变边界 | agent 修改沙箱或权限配置的路径被拒绝或被发现 |

社区报告的 `excludedCommands` 问题（#89931）未能取得原文核实，以固定版本的本机实验为准。

## 7. ADR-A 草案：验证执行边界与证据接收合同

状态：`proposed`
日期：2026-09-27
关联 change：C004

### 背景

VD-02 要求证据可信地进入 Sheltie。INV-6 规定模型输出不得写入系统事实：agent 自报“测试通过”不能成为证据。内核不能出现业务词汇（GF-01），引擎自己的写入只在 `~/.sheltie`（INV-3）。v0.3 的首批用户是个人开发者的本地仓库，要求验收低摩擦，不需要推送和等待远端。

### 候选

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| L1 本地快照验证器 | 外围验证器按 §3 在 `~/.sheltie/tmp` 的临时工作区运行冻结的验收命令，通过公开接口写入证据，标为“本地验证器取得” | 不需要推送；返工闭环延迟低；个人场景下可信度不低于 CI | 会在本机执行 agent 能修改的项目代码；证据可被同权限程序伪造；冷构建慢 |
| C1 通过 `gh` 读 CI 结果 | 外围集成用用户已登录的 `gh` 读取指定运行，核对 `headSha` 后写入证据 | 执行在远端；团队仓库可配置来源限定 | 每轮返工要推送并等待；个人仓库中信任前提基本不成立（§3.5） |
| A3 签名证明 | 执行方对结果签名，引擎只验签 | 唯一可能做到“执行者无法绕过”的方案 | 复杂度高；需要额外配置签名流程和密钥保管 |

### 建议

- 采用前的阶段 1 实验用外部脚本实现 L1 的四个环节，证据标为“外部回填”，不改产品代码；
- 阶段 1 证明有净收益后，v0.3 把 L1 做成产品组件，放在内核之外；
- C1 与 A3 保留为后续证据来源，由团队仓库或独立证据需求触发；
- 无论选哪个，证据记录都必须带“写入方式”字段，交付包据此显示可信度。

### 否决方案

- **agent 在输出文件里写测试结果，引擎照单全收。** 违反 INV-6。
- **在用户仓库里建 worktree 或替 agent 提交 commit。** 违反 INV-3。
- **只冻结验收命令字符串。** 脚本内容仍可变化，没有冻结检查。
- **验证器负责安装工具链和拉起服务。** 会迅速膨胀成环境管理产品，偏离 v0.3 范围。
- **给证据排可信等级阶梯。** 证据的可信度由多个属性共同决定，排成单一等级会掩盖局限。

### 后果

- Store 可能需要新增证据表，是否升结构版本在采用时确定；
- 宪章需要补充 INV-3 对“验收命令副作用”的解释（§3.2 b）；
- 承诺表第二行在 L1 路径下长期为“不承诺”；
- 合同需要定义验收命令、受保护路径、未跟踪文件清单的格式，只能是闭集字段，不能变成可执行的 DSL；
- “验证器取得”只能由验证器命令自己运行检查产生（§4.4），这倾向于把验证器做成 `sheltie` 的独立命令组。

### 确认方式

- agent 通过 CLI 写入伪造证据时，交付包如实标为“外部回填”，不显示为已验证；
- 候选变化、规则变化后旧证据失效；
- 候选改动验收脚本或 `.gitattributes` 时，对应条件 `failed`；
- 命令未启动、超时时结果为 `not_verified` 并记为验证器故障；
- 验证前后用户仓库的 `.git` 目录没有新增条目（除 agent 自己的提交外）；
- 准备期间源仓库变化，证据仍对应固定的候选提交；临时工作区缺少该提交时记为快照准备失败；
- 相同提交、不同额外文件的验证输入不共用结论。

## 8. ADR-B 草案：授权信任边界

状态：`proposed`
日期：2026-09-27
关联 change：C004

### 背景

GF-12 说批准记录以“当前操作系统用户身份”写入，但实现取的是 `USER` 环境变量，任何进程都能伪造（C002 N04，已在本机复现）。即使修复成真实 OS 身份，同一 OS 用户下运行的 agent 也能调用 `gate approve`。Sheltie 目前无法区分“人批准”和“agent 以人的身份批准”。

### 选择（候选）

v0.3 维持单用户信任模型：

- 主体取真实 OS 身份，由 C002 N04 修复；
- 对外只说“单用户批准”，不说“真人批准”或“真人在场”；
- 不保证抵抗同权限程序修改控制状态；
- 门槛批准记录绑定 Work、节点和 Occurrence，这一点现在已经做到；
- 宿主权限配置作为逐项验证的加固措施（§6），不扩大为安全承诺。

后续需要增强授权时，方向是：

- 授权绑定具体动作内容，参考 OWASP 的交易授权：用户批准的是“对这个候选、这份合同的接收”，而不是一个泛化的“继续”；
- 无人值守场景采用预授权：人事先批准范围和上限，范围内不再打扰人；
- 需要独立真人时，缺认证能力的配置直接拒绝（与路线图“人类多用户”一致）。

### 否决方案

- **v0.3 做 Touch ID 或系统弹窗认证。** 不绑定具体动作内容的认证只证明“有人按了一下”，而且会把产品拉向安全平台，偏离可验收委派的价值。
- **做常驻守护进程持有 Store 写权限。** 这能分离权限，但引入进程管理、升级和恢复的复杂度，而单用户模型下收益有限。
- **把身份修复描述为真人认证。** 这是误导性承诺。

### 后果

- 承诺表第三行的强度停留在“正常接口会拒绝”；
- 宪章 §5“人点头只出现在两处”的措辞，采用时要补充“在单用户信任模型下”；
- 阻断项的处置（§4.3）归入 §5 第 2 条“门槛与越权”：阻断项让接收出口不合法，用户处置相当于一次放行，不新增第三处人工介入；处置记录同样绑定 Work、候选和发现 id。

### 确认方式

- 伪造 `USER` 后批准人仍记为真实 OS 用户（依赖 C002 的测试）；
- 文档与 CLI 输出中不出现“真人认证”“真人在场”一类措辞。

## 9. 待定问题

1. `verify` 节点由谁调用验证器：协调者在 Attempt 内运行验证器命令，还是由 `attempt begin` 触发？前者引擎更瘦，后者执行来源更清楚。
2. 合同条件的机器部分放在 Workbook 的冻结资源里，还是作为 `work start` 的输入？前者随 Workbook 版本冻结，后者允许同一 Workbook 用于不同任务。
3. 交付包是否复用 `work stats` 的事实视图，还是新开一个只读命令？
4. 冷构建耗时若成为主要摩擦，是否提供受控的缓存选项，以及怎样防止缓存在快照之间传递污染？
5. 验证器以什么形态交付：外部脚本、`sheltie` 的独立命令组，还是独立 Cargo 包？§4.4 倾向独立命令组。
6. 阻断项的处置是否在以后允许获授权的复核机制代替用户？触发条件是用户处置成为实测中的主要人工负担。
7. “触发升级”的升级标记是否只需要一个布尔值，还是需要少量闭集类别？闭集之外的内容一律留在文档里。
8. VD-09 需要多少实际价值才值得三条宪章修订：若阶段 1 显示协调者从不无视审查结论，而误判阻断的处理成本高，VD-09 可推迟，只保留 VD-10 的身份标注。
9. 快照复制保持本地 clone，还是改用 Git 常规传输路径（例如向空仓库 fetch 指定提交）？首版只维护一种，按失败路径测试结果选择。
