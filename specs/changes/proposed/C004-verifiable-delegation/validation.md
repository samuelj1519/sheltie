# C004 验证

Candidate: `none`

状态：proposal 阶段。采用前必须完成的实验全部为 `not_run`。本文件先固定实验口径，避免事后调整指标。

## 1. 要回答的问题

在同一个模型、同一个宿主、等价的本地工作区条件下，Sheltie 能否降低个人开发者把一件代码库变更委派出去并得到可接受结果的人工成本，同时不降低质量？

只证明“Sheltie 的状态机工作正常”不能回答这个问题（GF-19）。Sheltie 要证明的增益来自任务合同复用、状态接续、证据关联、返工反馈和人工接管的组织方式，而不是来自“Sheltie 用干净快照、原生组用脏目录”这类条件差异。

## 2. 两组条件对等

| 项 | 原生组 | Sheltie 组 |
| --- | --- | --- |
| 模型与宿主版本 | 相同 | 相同 |
| 本地工作区条件 | 相同仓库、基线 commit、工具链、依赖缓存、本地服务 | 相同 |
| 验收标准与命令 | 相同命令、相同环境变量 | 相同，作为冻结的验收合同 |
| 宿主权限配置 | 相同 | 相同 |
| 任务说明 | 相同文字，放在 skill 或任务说明中 | 相同文字，放在合同与任务书中 |
| 干净环境 | 允许并鼓励使用 worktree、宿主的本地环境 setup scripts、基础验收脚本；不得刻意在正在编辑的脏目录里测试 | 本地快照验证器的临时工作区 |
| 返工方式 | 用户或 agent 自己看验收结果决定是否继续 | 按 design.md §2 的闭环 |
| 辅助 | 认真配置的 skill，含“跑验收、失败就修”的指示 | Sheltie skill + 代码变更 Workbook |

原生组必须认真配置，否则对照没有意义。两组的配置由同一人完成，配置时间计入各自的首次使用成本。

## 3. 阶段 1：摩擦探针（3 个任务）

目的：在正式对照之前暴露流程摩擦和设计缺口，不用于证明价值。

- 选 3 个真实任务：一个修 bug，一个小功能，一个预期验收会至少失败一次的任务；
- 只跑 Sheltie 组。验证器用外部脚本实现 design.md §3.1 的四个环节，证据标为“外部回填”，不改产品代码。按 VD-06，外部回填不能打开接收出口，所以阶段 1 不检验接收门控，只测闭环摩擦；门控的正反例在 §6 的失败路径测试中执行；
- 3 个任务合计至少覆盖一次“验收失败后返工”和一次“中断后接续”。自然发生的和人为注入的分开标注、分开报告；
- 记录每一次人工介入的原因和耗时、每一处“文档或 Workbook 表达不了”的地方，以及每次验证的耗时（含冷构建）；另记验证器故障按类别的次数、受保护路径命中次数，以及已发现的“清单之外影响验收”的实例（用于评估冻结范围与 design.md §9 第 10 问）；
- 至少一个任务含审查节点。记录两项计数：协调者无视审查结论、仍选择继续的次数；审查误报造成的阻断次数及其人工处理分钟。这两项决定 VD-09 是否值得随 v0.3 实现（design.md §9 第 8 问）；
- 审查者额度中断、由另一宿主继续审查同一候选的场景，放在 C005 第一阶段实验中执行，两份实验共用任务样本；
- 输出：摩擦清单，并归入下面两种诊断之一，据此修改 design.md 和实验任务集，然后再进入阶段 2：

| 诊断 | 表现 | 处理 |
| --- | --- | --- |
| 环境问题为主 | 本地环境跑不起来，时间耗在补前提上 | 收窄支持范围，或重新考虑执行路径 |
| 闭环问题为主 | 验证运行顺利，但用户仍需反复解释、追问、手动组织返工 | 检查 Sheltie 的工作闭环是否真正提供了价值；若无法改进，转为 rejected |

## 4. 阶段 2：对照实验（5–8 个任务）

- 任务在实验开始前选定并登记在本目录，包括仓库、基线 commit、验收条件和验收命令；
- 每个任务两组各跑一次，顺序随机，避免学习效应偏向某一组；
- “被接受”由外部标准和一致的审阅方式判定：同一位审阅者按预先写好的验收条件审阅最终 diff，并且不知道 diff 来自哪一组。**不使用 Sheltie 自己的接收状态作为真值。**

## 5. 指标

主指标：**每个被接受任务花费的人工分钟数**。人工时间包括：配置、写任务说明、处理失败尝试、排障、接管、返工和最终审阅。首次使用（含配置）和规则复用（第二个任务起）分开报告。

次要指标，与主指标一起报告，缺一不可：

| 指标 | 口径 |
| --- | --- |
| 质量 | 审阅者按验收条件逐条判定的通过数；审阅中发现的缺陷数 |
| 错误拒收 | 候选实际满足条件，却被接收点挡住的次数及原因 |
| 错误接收 | 接收点放行，但审阅者判定不满足的次数 |
| 验证器故障 | 前提缺失、超时、中断、清理残留的次数，与 agent 执行失败分开 |
| 未完成 | 耗尽上限或放弃的任务数 |
| 错误阻断 | 审查误报导致的额外返工轮次和人工处置分钟 |
| 总成本 | 宿主观测到的 token 用量（不用模型自报）、墙钟时间、验证耗时（含冷构建） |

按宪章 §6“每条成本指标配一条质量判据”，只报人工时间下降、不报质量，不算结论。

## 6. 失败路径测试（与用户价值分开报告）

这些是脚本化的机制测试，证明承诺表的每一行在声明强度内成立，不能当作用户价值证据。采用后才能执行。快照准备、额外文件变化等场景可以直接用程序测试，不需要调用模型。

| 场景 | 应观察到 | 不能出现 |
| --- | --- | --- |
| 必需条件缺证据 | 接收出口不在 `next` 中 | 接收出口出现在 `next` 中 |
| 证据对应旧候选 | 证据失效，条件回到 `not_verified` | 旧证据满足新候选 |
| 规则版本变化 | 旧证据失效 | 用旧规则的结果接收 |
| 候选改动受保护清单中的路径（验收脚本、既有验收测试、`.gitattributes`） | 记录命中路径，Work `blocked(scope_violation)`，只能 `work cancel` | 判 `failed` 后走 `back` 自动返工；用被改过的规则判定通过 |
| 候选改动清单之外、但影响测试选择的文件（例如未列出的测试配置） | 照常验证；交付包的已知局限写明冻结范围 | 声称验收规则未被改变 |
| agent 新增测试 | 照常运行，结果单独报告 | 参与接收判断 |
| 验收命令未启动（缺工具链或前提） | `not_verified`，记验证器故障 `prerequisite` 并列出缺失项；验证节点只能 `attempt fail`，在本节点重试 | 记为 agent 执行失败；暴露 `back`；消耗 `implement` 的 `max_visits`；自动安装工具链 |
| 验收命令超时 | `not_verified`，进程组被终止，记验证器故障 `timeout`；只能 `attempt fail` 重试 | 结果为 `satisfied`；残留进程不报告 |
| 只有 `not_verified` 时对验证节点 `attempt submit` | 拒绝；`next` 只有 `attempt fail` 与 `work cancel` | 提交成功后因无合法边进入 `blocked(no_legal_edge)` |
| 验证器故障重试耗尽 | Work `blocked(retries_exhausted)`，只能 `work cancel`；交付包写明故障类别 | 记为候选失败；走 `back` |
| 同时有 `failed` 与 `not_verified` | 只有 `back` | 接收出口出现 |
| 验证器在写入结果前被杀，恢复后 | Attempt 仍为 `running`，没有完整证据，接收出口不出现；`attempt fail` 记 `interrupted` | 把部分结果当作证据 |
| 清理失败 | 已记录的结果不变，另记残留路径 | 丢失证据 |
| 合同未列出的未跟踪文件 | 不进入临时工作区 | 被静默复制 |
| 固定候选后、复制前源仓库出现新提交或分支移动 | 证据仍对应固定的提交标识 | 验证了新的 `HEAD` 却标为原候选 |
| 临时工作区缺少候选提交或复制异常 | 快照准备失败，`not_verified`，记验证器故障 | 退回复制时的 `HEAD` 继续验证 |
| 相同提交、额外文件内容变化 | 视为新的验证输入，旧结论不复用 | 沿用旧的 `satisfied` |
| 额外文件覆盖提交中的文件，合同未允许 | 快照准备失败 | 静默覆盖后照常验证 |
| 额外文件覆盖提交中的文件，合同已允许 | 覆盖写进验证输入的描述 | 报告只指向提交标识 |
| 额外文件目标命中受保护路径，即使合同允许覆盖同名提交文件 | 复制前记 `scope_violation`，Work 停止且只允许取消 | 只看基线与候选的 Git diff，运行被额外文件覆盖的验收脚本 |
| 验证前后的用户仓库 | `.git` 目录除 agent 自己的提交外没有新增条目 | 出现 `.git/worktrees/` 条目或 Sheltie 创建的 commit |
| 同一条件、同一候选的一对证据：一份由验证器命令取得；另一份其余字段相同，只是来源为外部回填 | 前者满足条件，接收出口出现；后者不满足，接收出口不出现，交付包标为“外部回填” | 两者效果相同；回填显示为已验证 |
| Workbook 声明合同，但存在从候选生产节点不经接收出口到达终点的路径 | `workbook add` 装入失败并指出路径 | 装入成功，Work `succeeded` 而候选从未经过接收出口 |
| 接收出口之后有一个 `gate = true` 的非终点节点，未列入 `not_candidate_producers`，可以不经接收出口到达终点 | `workbook add` 装入失败，指出该节点到终点的路径（门槛节点默认计入候选生产节点） | 因为它是门槛节点而默认不计入，装入成功 |
| 合同节点除接收出口外另有一条 `branch` 边直通终点（每条路径都经过合同节点） | `workbook add` 装入失败，指出该边 | 按“经过接收节点”判为通过 |
| VD-09 推迟时，合同把审查声明为“构成必要条件” | `workbook add` 装入失败 | 装入成功，审查却不影响接收 |
| VD-09 推迟，审查节点设 `gate = true` | 门槛未批准不 `succeeded`；交付包写“审查不属于接收条件” | 交付包写审查已满足 |
| 合同只有需人判断的条件 | 接收出口按审查条件（如有）出现；交付包写“无机器验证条件” | 交付包显示全部已验证 |
| 接收节点设 `gate = true`，机器条件有 `failed` | 批准后 `next` 仍只有 `back` | 门槛批准打开接收出口 |
| 重试耗尽 | Work `blocked`，交给人 | 无限返工 |
| 合同中有无机器检查的条件 | 交付包列为“未验证、需人判断” | 交付包显示全部已验证 |
| 伪造 `USER` 后批准门槛 | 批准人记为真实 OS 用户 | 记为伪造名（依赖 C002） |
| 合同要求审查，审查尚未完成或中断 | 接收出口不在 `next` 中 | 因为“没有否决”而放行 |
| 审查声明格式错误或来源不满足合同 | 审查条件未满足 | 被当作通过 |
| 另一审查者复核后给出通过 | 原阻断发现仍有效，接收出口仍不合法 | 原发现被覆盖或消失 |
| 用户以“不适用”处置误报 | 原报告保留，新增处置记录，接收条件重新计算 | 原报告被删除 |
| 提交只改一行注释的新候选 | 旧阻断发现延续，需要逐条处置 | 所有发现清零 |
| 严格分离模式下只有声明身份 | 分离条件未满足，交付包写明缺观测证据 | 显示“独立审查已满足” |
| 执行中尝试把审查作用从“必要条件”改为“提供建议” | 拒绝 | 合同被改写 |
| 通过接口传入结果并标为“验证器取得” | 拒绝；或只能记为“外部回填”，不满足必需条件 | 显示为验证器取得；打开接收出口 |
| 保留样本在反馈中被完整返回 | 该样本标为已暴露 | 继续算作独立检查 |

涉及审查作用、阻断发现、处置和严格分离模式的各行，只在 VD-09 随 v0.3 实现时执行（spec.md VD-09）。
