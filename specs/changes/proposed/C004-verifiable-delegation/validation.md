# C004 验证

Candidate: `none`

状态：proposal 阶段。采用前必须完成的实验全部为 `not_run`。本文件先固定实验口径，避免事后调整指标。

## 1. 要回答的问题

在同一个模型、同一个宿主、等价的本地工作区条件下，Sheltie 能否降低个人开发者把一件代码库变更委派出去并得到可接受结果的人工成本，同时不降低质量？

只证明“Sheltie 的状态机工作正常”不能回答这个问题（GF-19）。Sheltie 要证明的增益来自任务合同复用、状态接续、证据关联、返工反馈和人工接管的组织方式，而不是来自“Sheltie 用干净快照、原生组用脏目录”这类条件差异。

## 2. 两组条件对等

| 项 | 原生组 | Sheltie 组 |
| --- | --- | --- |
| 模型与宿主版本 | 相同 | 相同 |
| 本地工作区条件 | 相同仓库、基线 commit、工具链、依赖缓存、本地服务 | 相同 |
| 验收标准与命令 | 相同命令、相同环境变量 | 相同，作为冻结的验收合同 |
| 宿主权限配置 | 相同 | 相同 |
| 任务说明 | 相同文字，放在 skill 或任务说明中 | 相同文字，放在合同与任务书中 |
| 干净环境 | 允许并鼓励使用 worktree、宿主的本地环境 setup scripts、基础验收脚本；不得刻意在正在编辑的脏目录里测试 | 本地快照验证器的临时工作区 |
| 返工方式 | 用户或 agent 自己看验收结果决定是否继续 | 按 design.md §2 的闭环 |
| 辅助 | 认真配置的 skill，含“跑验收、失败就修”的指示 | Sheltie skill + 代码变更 Workbook |

原生组必须认真配置，否则对照没有意义。两组的配置由同一人完成，配置时间计入各自的首次使用成本。

## 3. 阶段 1：摩擦探针（3 个任务）

目的：在正式对照之前暴露流程摩擦和设计缺口，不用于证明价值。

- 选 3 个真实任务：一个修 bug，一个小功能，一个预期验收会至少失败一次的任务；
- 只跑 Sheltie 组。验证器用外部脚本实现 design.md §3.1 的四个环节，证据标为“外部回填”，不改产品代码；
- 3 个任务合计至少覆盖一次“验收失败后返工”和一次“中断后接续”。自然发生的和人为注入的分开标注、分开报告；
- 记录每一次人工介入的原因和耗时、每一处“文档或 Workbook 表达不了”的地方，以及每次验证的耗时（含冷构建）；
- 至少一个任务含审查节点。记录两项计数：协调者无视审查结论、仍选择继续的次数；审查误报造成的阻断次数及其人工处理分钟。这两项决定 VD-09 是否值得随 v0.3 实现（design.md §9 第 8 问）；
- 审查者额度中断、由另一宿主继续审查同一候选的场景，放在 C005 第一阶段实验中执行，两份实验共用任务样本；
- 输出：摩擦清单，并归入下面两种诊断之一，据此修改 design.md 和实验任务集，然后再进入阶段 2：

| 诊断 | 表现 | 处理 |
| --- | --- | --- |
| 环境问题为主 | 本地环境跑不起来，时间耗在补前提上 | 收窄支持范围，或重新考虑执行路径 |
| 闭环问题为主 | 验证运行顺利，但用户仍需反复解释、追问、手动组织返工 | 检查 Sheltie 的工作闭环是否真正提供了价值；若无法改进，转为 rejected |

## 4. 阶段 2：对照实验（5–8 个任务）

- 任务在实验开始前选定并登记在本目录，包括仓库、基线 commit、验收条件和验收命令；
- 每个任务两组各跑一次，顺序随机，避免学习效应偏向某一组；
- “被接受”由外部标准和一致的审阅方式判定：同一位审阅者按预先写好的验收条件审阅最终 diff，并且不知道 diff 来自哪一组。**不使用 Sheltie 自己的接收状态作为真值。**

## 5. 指标

主指标：**每个被接受任务花费的人工分钟数**。人工时间包括：配置、写任务说明、处理失败尝试、排障、接管、返工和最终审阅。首次使用（含配置）和规则复用（第二个任务起）分开报告。

次要指标，与主指标一起报告，缺一不可：

| 指标 | 口径 |
| --- | --- |
| 质量 | 审阅者按验收条件逐条判定的通过数；审阅中发现的缺陷数 |
| 错误拒收 | 候选实际满足条件，却被接收点挡住的次数及原因 |
| 错误接收 | 接收点放行，但审阅者判定不满足的次数 |
| 验证器故障 | 前提缺失、超时、中断、清理残留的次数，与 agent 执行失败分开 |
| 未完成 | 耗尽上限或放弃的任务数 |
| 错误阻断 | 审查误报导致的额外返工轮次和人工处置分钟 |
| 总成本 | 宿主观测到的 token 用量（不用模型自报）、墙钟时间、验证耗时（含冷构建） |

按宪章 §6“每条成本指标配一条质量判据”，只报人工时间下降、不报质量，不算结论。

## 6. 失败路径测试（与用户价值分开报告）

这些是脚本化的机制测试，证明承诺表的每一行在声明强度内成立，不能当作用户价值证据。采用后才能执行。

| 场景 | 应观察到 | 不能出现 |
| --- | --- | --- |
| 必需条件缺证据 | 接收出口不在 `next` 中 | 候选被标为已接收 |
| 证据对应旧候选 | 证据失效，条件回到 `not_verified` | 旧证据满足新候选 |
| 规则版本变化 | 旧证据失效 | 用旧规则的结果接收 |
| 候选改动验收脚本、既有验收测试或 `.gitattributes` | 对应条件 `failed`，Work 交给人 | 用被改过的规则判定通过 |
| agent 新增测试 | 照常运行，结果单独报告 | 参与接收判断 |
| 验收命令未启动（缺工具链或前提） | `not_verified`，记验证器故障并列出缺失项 | 记为 agent 执行失败；自动安装工具链 |
| 验收命令超时 | `not_verified`，进程组被终止，记验证器故障 | 结果为 `satisfied`；残留进程不报告 |
| 清理失败 | 已记录的结果不变，另记残留路径 | 丢失证据 |
| 合同未列出的未跟踪文件 | 不进入临时工作区 | 被静默复制 |
| 验证前后的用户仓库 | `.git` 目录除 agent 自己的提交外没有新增条目 | 出现 `.git/worktrees/` 条目或 Sheltie 创建的 commit |
| agent 通过 CLI 写入伪造证据 | 交付包标为“外部回填”，不显示为已验证 | 交付包显示为已验证 |
| 重试耗尽 | Work `blocked`，交给人 | 无限返工 |
| 合同中有无机器检查的条件 | 交付包列为“未验证、需人判断” | 交付包显示全部已验证 |
| 伪造 `USER` 后批准门槛 | 批准人记为真实 OS 用户 | 记为伪造名（依赖 C002） |
| 合同要求审查，审查尚未完成或中断 | 接收出口不在 `next` 中 | 因为“没有否决”而放行 |
| 审查声明格式错误或来源不满足合同 | 审查条件未满足 | 被当作通过 |
| 另一审查者复核后给出通过 | 原阻断发现仍有效，接收出口仍不合法 | 原发现被覆盖或消失 |
| 用户以“不适用”处置误报 | 原报告保留，新增处置记录，接收条件重新计算 | 原报告被删除 |
| 提交只改一行注释的新候选 | 旧阻断发现延续，需要逐条处置 | 所有发现清零 |
| 严格分离模式下只有声明身份 | 分离条件未满足，交付包写明缺观测证据 | 显示“独立审查已满足” |
| 执行中尝试把审查作用从“必要条件”改为“提供建议” | 拒绝 | 合同被改写 |
| 通过接口传入结果并标为“验证器取得” | 拒绝，或只能记为“外部回填” | 显示为验证器取得 |
| 保留样本在反馈中被完整返回 | 该样本标为已暴露 | 继续算作独立检查 |
