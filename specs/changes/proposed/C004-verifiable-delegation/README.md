状态：`proposed`
目标版本：`待定`（候选 v0.3.0，排在 C002 之后）

基线：`296313c6f9fcfd0d6348927b73e7a49578581b6c`
Owner：`待采用时指定`
权威性：未采用；不得据此修改产品代码、根规格或决定记录

## 范围约束

**v0.3 验证的是：在已有本地验收条件的代码库中，Sheltie 能否通过可接续、可核对、可返工的任务闭环，减少用户的总投入。**

超出这句话的能力（多 agent 调度、通用环境搭建、隔离、CI 接入、多用户）不进入 v0.3。

**共同基础：** 更换执行者，不得自动放宽任务标准、权限范围和证据要求；最终接收依据来自预先授权的验证机制，不能仅凭执行者自报。执行者可以替换，已登记的审查发现不因替换而消失。

本 package 回答“这份候选凭什么接收”。“接下来由谁、在什么条件下继续”由 [C005](../C005-executor-continuity/README.md) 负责；两者共用 Work、Attempt、候选快照、执行引用和证据记录。

## 要解决的问题

v0.1.0 证明了引擎能记状态、限定合法下一步、守门槛，但产品价值仍押在“固定 flow 帮 agent 记步骤”上。模型越强，这部分价值越薄（宪章 §7）。另一条候选方向是“多 agent 组织调度与隔离”，本 package 的评估结论是：它不能作为下一版的核心价值。原因有三：并行探索式的多 agent 方案 token 成本是单 agent 的数倍（这一经验值不适用于把工作分给便宜模型的分工，见 review.md §8）；多数失败来自规格和验收缺口，而不是调度；Sheltie 在本地单用户信任下做不出可信的隔离。评估过程见 [review.md](review.md)。

个人开发者把一件代码库变更交给 agent 后，真正费人的环节是：

1. 讲清楚“做到什么算完”，并且在执行中途不被悄悄改掉；
2. 判断 agent 说的“做完了”是否可信，也就是检查是否真的按约定的规则、在这次的候选上跑过；
3. 检查失败后，把证据交回 agent 继续修，而不是每次都叫人；
4. 合同要求审查时，确认审查真的做完了、提出的问题被处理了，而不是协调者看过报告后照样继续；
5. 最后拿到一份能审阅的交付包：改了什么、哪些条件被验证了、哪些没被验证、为什么。

本 package 提议把下一版的产品重心定为 **可验收委派**：Sheltie 管理任务合同、接续状态、验收条件与证据的对应、返工闭环和交付包；验收由一个最小的**本地快照验证器**完成：在固定的候选快照上运行项目已有的本地验收命令。在单宿主、单 agent 场景下，这些价值也必须成立。

## 首批用户

个人开发者的本地 Git 仓库，并且已经具备本地验收条件：工具链、依赖缓存和所需服务已就绪，有能直接运行的验收命令。不具备这些条件的项目不在 v0.3 支持范围内，Sheltie 只准确报告缺什么。

## 成功判据

采用前（proposal 阶段）：

- [validation.md](validation.md) 的 3 任务摩擦探针和 5–8 任务对照实验已执行，并按预先写定的口径报告；
- 主指标是“每个被接受任务花费的人工分钟数”，Sheltie 组相对原生组有可复现的下降，同时质量、错误拒收率和未完成率没有变差；
- 若未达到，本 package 转为 rejected 或改写，不能凭论证直接采用。

采用后（实现阶段，采用时细化到 plan.md）：

- [spec.md](spec.md) §4 的承诺表逐行有正例、反例和信任前提，承诺范围之外的内容不出现在对外用语中；
- 返工闭环在授权范围和重试上限内不需要人插手，越权或耗尽上限时停下来找人；
- 交付包逐条列出每个验收条件是“已验证 / 验证失败 / 未验证、需人判断”，并附证据来源；
- 合同要求审查时，审查未完成、有未处置阻断项，或严格分离模式下缺少执行身份的观测证据，接收条件都保持未满足；
- GF-01 仍然成立：内核代码里不出现 Git、Cargo、CI 等业务词汇；
- INV-3 仍然成立：引擎自己的写入只在 `~/.sheltie`，不写用户仓库。

## 不做什么

- 不把多 agent 调度、并发 Work、动态展开（GF-25、GF-26）放进本版本。它们是后续独立决策，由实测瓶颈触发。
- 不承担通用环境搭建：不自动安装工具链、不拉起复杂服务、不补齐凭据。缺少前提就准确报告。
- 不做通用 runner 平台、跨平台环境管理器或安全沙箱。临时工作区只分开工作目录，不宣称隔离。
- 不在 v0.3 接入 CI。CI 作为另一种证据来源保留在设计中，由团队仓库等真实需求触发。
- 不做常驻守护进程，不做 Touch ID 或其他真人在场认证，不做多用户。
- 不宣称“检查通过等于业务正确”，也不宣称“已阻止执行者篡改控制状态或伪造证据”。
- 不做执行者选择、备选接替、额度观测、可恢复等待和执行代次，这些属于 C005。
- 不把保留验收样本设为默认要求，也不宣称它对执行者保密。
- 不修改 C002 的范围。C002 的 N04（身份取可伪造的 `USER`）是本 package 的前置条件，不在这里重复修。
