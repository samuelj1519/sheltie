# C007 验证

Candidate: `none`

状态：proposal 阶段。全部实验为 `not_run`。本文件先固定实验口径，避免事后调整指标。

## 1. 要回答的问题

分开回答，分开报告：

1. **生成流程是否减少了用户的配置负担。** 用户借助“生成 + 检查 + 确认”得到一份可用 Workbook，花的人工时间是否少于手写，且质量不下降？
2. **检查器是否按承诺工作。** 在给定映射与 \(P\) 下，绕过必需条件的草案是否都被判为不通过，“无法结构判定”的条目是否都进入未决清单？
3. **映射与 \(P\) 的错误由谁发现。** 图结构合规、但映射或 \(P\) 有误的草案，是在用户确认时发现、运行后暴露，还是没有被发现？这一问不计入检查器的拦截率。

问题 2 通过，不说明问题 1 有价值（GF-19）；问题 3 的结果不能记为检查器已拦截。

## 2. 两组条件对等

| 项 | 手写组 | 生成组 |
| --- | --- | --- |
| 任务 | 相同的任务目标与验收条件 | 相同 |
| 约束 | 相同的约束快照，作为手写时的要求清单 | 相同，作为规划者的输入 |
| 参照材料 | Workbook 合同、示例 Workbook | 相同，另加 authoring skill |
| 模型与宿主 | 手写组可以让 agent 协助写文件，但不使用生成流程与检查器 | 相同的模型与宿主 |
| 检查 | 用户自行检查，或用同一检查器事后评分（不反馈给写作过程） | 检查器在确认前运行 |

手写组可以借助 agent，否则对照的是“有没有 AI”，不是“有没有生成流程”。

## 3. 第一阶段：authoring 实验（3–5 个任务）

- 与 C004 阶段 1 共用任务样本；任务在实验开始前登记在本目录；
- 每个任务两组各做一次，顺序随机；
- 生成组按 design.md §5 的路径执行，不改产品代码；
- 两组产出的 Workbook 都安装并运行到结束，运行按 C004 的外部审阅判定结果；
- 另外准备两类人为构造的“有缺陷草案”，分开报告：
  - **图路径类**（至少 2 份）：绕过审查的 `branch` 边、返工后不经测试直达终点。应由检查器判为不通过；
  - **输入类**（至少 2 份）：把审查条件映射到一个什么也不做的空壳节点；把真正改动候选的节点列进 \(P\) 的排除清单。图结构本身合规，检查器必然通过；按“确认时发现 / 运行后暴露 / 未发现”报告，不计为检查器拦截；
- 两组都在实验开始前固定输入闭包：约束快照、项目默认要求文件及其位置、authoring skill 版本、检查器版本。

## 4. 指标

主指标：**得到一份可用 Workbook 的人工分钟数**。“可用”指：安装成功，运行到结束，结果被外部审阅接受。人工时间包括：写或改约束、写任务目标、阅读并修改草案、处理检查结果、确认。首次使用和第二个任务起分开报告。

次要指标，与主指标一起报告：

| 指标 | 口径 |
| --- | --- |
| 结构缺陷 | 按同一检查器事后评分，两组各自漏掉的必需条件与可绕过路径数 |
| 确认质量 | 映射与 \(P\) 错误（含输入类缺陷草案）按“确认时发现 / 运行后暴露 / 未发现”三栏计数 |
| 规划者的放宽建议 | 差异说明中建议放宽的条目数；用户接受的条目数 |
| 运行结果 | 被接受的任务数；返工轮次；人工介入次数 |
| 过度结构 | 运行中从未被到达的节点数；每个任务的节点数 |
| 成本 | 生成过程的 token 用量（宿主观测）；墙钟时间 |

只报告人工时间下降、不报告结构缺陷和运行结果，不算结论（宪章 §6）。

## 5. 失败路径测试（与用户价值分开报告）

检查器的测试全部可以用程序完成，不需要调用模型；第一阶段检查器是外部脚本时即可执行。

| 场景 | 应观察到 | 不能出现 |
| --- | --- | --- |
| 草案通不过 `workbook add` 的装入校验 | 不通过，报告装入错误；正式管理根没有新增 Workbook 行或目录 | 继续检查其他规则；在正式管理根试装 |
| 可装入检查通过后正式安装同一草稿 | 正式 `workbook add` 成功，没有 `WORKBOOK_EXISTS` | 因检查时已在正式管理根登记而撞版本 |
| 约束中的必需条件没有映射 | 不通过，列出缺失条件 | 当作可选 |
| 映射引用不存在的节点 | 不通过 | 忽略该映射 |
| 存在一条不经过必需节点的 `branch` 路径 | 不通过，指出路径 | 因为“图中有这个节点”而通过 |
| 返工后经 `back` 边重新产生候选，可以不经测试到达终点 | 不通过（候选之后规则） | 通过 |
| 未列入排除清单的非门槛节点位于测试节点之后，且可以不经测试到达终点 | 不通过（默认计入 \(P\)） | 因规划者未声明它产生候选而通过 |
| 审查条件映射到空壳节点（图结构合规） | 检查器通过；报告注明映射真实性需用户确认 | 计为检查器已拦截 |
| 真正改候选的节点被列进排除清单（图结构合规） | 检查器通过；排除清单在确认材料中逐条展示 | 排除清单不展示；计为检查器已拦截 |
| 必需门槛映射到未声明 `gate = true` 的节点 | 不通过 | 通过 |
| 某节点 `max_visits` 超过约束上限 | 不通过 | 通过 |
| 尝试次数上界超过 `max_attempts_total` | 不通过，报告计算值 | 通过 |
| 约束中含 token 或费用预算 | 进入未决清单；锁定文件 `rule_verdict` 与 `unresolved` 分开记录 | 列为通过；报告写成整份约束已满足 |
| 约束中含“不改变鉴权语义”一类要求 | 列为“需运行时控制或需人判断” | 列为通过 |
| 规划者在差异说明中建议删去审查 | 仍按原约束判定不通过 | 按建议判定 |
| 确认后、安装前修改草稿中的任一文件 | 安装前重新计算，报告不一致 | 按旧锁定文件继续且不报告 |
| 安装前核对通过后、正式安装前修改草稿 | 正式 `workbook add` 返回的 `digest` 与确认时的临时装入摘要不同，报告不一致 | 不比较安装摘要 |
| 修改约束快照或约束映射 | 对应摘要不一致，报告不一致 | 静默接受新约束 |
| 仓库内的项目默认要求文件与仓库外记录的确认摘要不一致 | 要求用户重新确认 | 静默使用新文件 |
| 第一阶段：Workbook `requires` 不在约束快照的允许名单内 | 不通过 | 通过 |
| C004 未采用时，约束中含 `machine_check` 条件 | “证据绑定”规则标为不适用并注明 | 判为通过并称证据已绑定 |
