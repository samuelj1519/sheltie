# C007 方向评估

结论：建议起草“运行前生成 Workbook”，第一阶段只做实验，不改产品代码。本文件记录方向讨论的依据。它不是实现后的独立 review。

基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。日期：2026-09-27。参与者：用户、Claude Code，以及外部讨论者的书面意见。

## 1. 起点

用户的路线图里有两项灵活性需求：

- 配置一份简洁宽泛的 Workbook，只在关键节点设置审核，其余由 agent 自主完成；
- 协调者先安排方案 agent 创建临时流程，再按流程推进；流程按“示例 + 规范”用自然语言创建，由流程检查器检查。

第一项不需要新机制：现有 Workbook 就能写成少量交付阶段包住 agent 的自主工作。第二项形成本 package。

## 2. 收敛的结论

1. **运行前生成与运行中展开分开。** 运行前生成符合根规格“AI 可以起草，人确认后冻结，运行中不改图”；运行中展开需要展开槽、继承规则和总预算，属于 GF-26，后置。
2. **检查器必须对照一份用户授权的约束。** 规划 agent 既生成计划又决定什么算完成，就可能降低标准让工作显得成功。
3. **不另写新章程。** 约束直接复用 C004 的验收合同和 C005 的执行绑定、自动执行政策，合成为生效约束快照：项目默认要求 + 本次确认的差异 + 执行政策限制。
4. **规划者可以建议修改约束，建议不自动成为授权。**
5. **绑定约束版本与计划摘要。** 之后修改计划或放宽约束，都走对应的确认规则。
6. **检查器检查路径覆盖，不只检查节点存在。** 有审查节点，也可能存在绕过它的路径。
7. **结构检查的边界写清楚。** 总预算需要运行时累计；“不改变鉴权语义”这类要求需要实际验证或审查证据；结构检查通过只证明被检查的结构条件满足。
8. **第一个实验走现有 `workbook add`。** 先验证生成流程是否减轻用户负担，再决定是否增加临时启动入口；两条路径必须共用校验与冻结逻辑。
9. **固定授权与交付要求，脚手架按效果调整。** 为补某一代模型短板而加的拆分和审查频率，可以随效果调整。

## 3. 本轮起草时新发现的问题

根规格写明“引擎不知道哪个节点是 Review”。因此检查器只能核对“约束条件 → 节点”的映射在图上的覆盖，不能判断被映射的节点是否真的在做审查。本 package 把映射列为用户确认的内容；采用 C004 时，接收点要求证据，映射错误会在运行时表现为缺证据（spec.md WG-05）。

## 4. 讨论中纠正的本方错误

- 早先把“规划 agent 生成临时流程”直接收敛为“父 Workbook 的展开槽”，过早引入 GF-26 的复杂度；
- 早先把检查器描述为检查“有没有审核节点”，没有覆盖可绕过的路径和返工后的候选。

## 5. 被否决的方向

| 方向 | 否决原因 |
| --- | --- |
| 运行中任意修改流程 | 违背 GF-03；需要的展开机制留给 GF-26 |
| 规划者按 skill 自检 | 生成者与判定者是同一方（design.md ADR-E 的 E3） |
| 为 C007 另写一份约束合同 | 与 C004、C005 含义重叠，需要同步维护 |
| 首版就把检查写进 `workbook add` | 尚未证明生成流程有用，就修改装入合同与引擎边界 |
| 首版就增加临时启动入口 | 现有安装路径足够完成第一个实验 |
