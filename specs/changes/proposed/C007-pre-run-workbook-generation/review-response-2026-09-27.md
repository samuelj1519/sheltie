# C007 审阅答复（2026-09-27）

答复对象：[independent-review-2026-09-27.md](independent-review-2026-09-27.md)。本 package 仍为 `proposed`，authoring 实验与检查器失败路径测试仍为 `not_run`。本文件记录逐条判断与本轮修订位置；修订只改本目录的候选文档，不改根规格、合同或产品代码。

## 逐条答复

### 1. 第一阶段的保证强度与入口不一致（高）

**判断：采纳。** 旧 spec.md §5 的对外用语写「生成的流程必须满足你事先确认的检查、审查和门槛要求；规划 agent 不能自己删掉它们」「不存在绕过检查的捷径」，没有分阶段；而 design.md §4 已承认用户可以跳过检查器直接 `workbook add`，`contracts/workbook.md` §1 的 `workbook add` 也不读锁定文件。旧 WG-06「安装前检查器重新计算，内容不一致就拒绝继续」同样超出外部脚本的能力。审阅关于第二阶段的判断也成立：只核同权限可改的摘要，只证明字节一致。

**修改位置：**

- spec.md §5：分成「第一阶段可以说」「第二阶段的前提」「任何阶段都不能说」。第一阶段只说「经指定检查器处理、且用户确认映射的草稿，在已检查的结构规则上通过」；「绕过捷径」限定为相对于已确认的映射。
- spec.md WG-06：「拒绝继续」改为「检查器报告不一致，由用户停止安装」，并写明第一阶段拦不住直接 `workbook add`。
- spec.md §4：拆出「映射与 \(P\) 忠实反映计划」「锁定文件摘要一致表示用户授权」两行，都标为不承诺；首行写明第二阶段须先有可信签发来源与 `work start` 核对合同。
- design.md §4、ADR-E 建议、README 采用条件：同步上述前提。

### 2. 「可装入」检查必须无产品副作用（高）

**判断：采纳；前提部分成立。** 旧 WG-03 只写「草稿通过 `workbook add` 的全部装入校验」，并未规定直接在正式管理根运行 add；但方案也没有给出无副作用的入口。现行协议没有纯校验命令（`workbook verify` 只核已装版本），而同 id、同版本重复 add 会报 `WORKBOOK_EXISTS`（`contracts/storage.md` §5.2 第 4 步），审阅担心的「撞同一版本」属实。第一阶段不改产品代码，临时 `SHELTIE_HOME` 是唯一现成的办法。

**修改位置：**

- spec.md WG-03「可装入」：检查在隔离的临时 `SHELTIE_HOME` 中进行，不在正式管理根留下状态。
- design.md §5：改为七步。检查时在临时 home 试装并记录 `digest`；确认后重算锁定文件中的摘要，再把最终目录装入另一个临时 home 得到 \(D\)；正式 `workbook add` 返回的 `digest` 必须等于 \(D\)。
- 审阅未提、本轮补上：正式安装后的摘要比对，堵住「确认后、正式安装前」的窗口。
- validation.md §5：补「装入失败时正式管理根无新增」「检查通过后正式安装不撞 `WORKBOOK_EXISTS`」「安装前核对后再改草稿」三行。

### 3. 静态检查的输入可信度（高）

**判断：采纳，是真实缺口。** design.md §3 写明 \(P\) 由规划者声明、用户确认，WG-05 承认映射只是声明；但 validation.md 的缺陷草案只有图路径类，§5 只测了「缺映射」「映射引用不存在的节点」，没有图结构合规、输入本身错误的负例。

**修改位置：**

- spec.md WG-02 与 design.md §3：\(P\) 改为**默认全选**，即除门槛节点和终点节点外的全部节点；排除必须在映射中逐个显式列出，由用户确认。漏标因此只能以可见的排除声明出现。
- spec.md WG-03 后新增一段、design.md §3 新增一段：检查器的结论只对给定的映射与 \(P\) 成立，空壳映射和 \(P\) 错误排除不计为检查器拦截。
- validation.md：§1 新增问题 3；§3 把缺陷草案分成「图路径类」「输入类」两类；§4「确认质量」按「确认时发现 / 运行后暴露 / 未发现」三栏计数；§5 新增默认计入 \(P\) 的反例和两条输入类场景；§6 新增一行执行状态。

### 4. 未采用 C004/C005 时收窄约束字段（中）

**判断：部分采纳。** 方案原本已有部分收窄，审阅没有承认：README「采用条件」写明用候选字段作格式参照并在报告中注明，「依赖」写明未采用 C004 时只含现有 Workbook 能表达的门槛与上限。但 WG-01 的「执行政策限制」一行、WG-03 的「不越权」规则都没有区分阶段；README 采用后判据里的「证据绑定被接收的候选」在 WG-03 规则表中也没有对应规则。

**修改位置：**

- spec.md WG-01：表格加「第一阶段」列；执行政策限制只作实验记录。
- spec.md WG-03：「不越权」第一阶段只核 `requires` 允许名单；新增规则「证据绑定（依赖 C004 采用）」，只核映射节点上的 C004 合同声明了对应条件 id，证据是否绑定被接收候选仍由 C004 VD-06 在运行时判定；表后列出第一阶段可用的规则子集。
- design.md §2：示例加 `[requires_allow]`，`[execution]` 标为只作记录。
- design.md §3：新增两条规则的判定式；\(T\) 定为 Flow 的终点节点。采用 C004 后，接收是合同节点受控放开的 `main` 边，C004 的装入校验要求每条到 \(T\) 的路径经过合同节点，与本方案的路径覆盖是同一算法。
- README：采用后判据与采用条件同步。

### 5. 锁定文件绑定完整检查输入与结果（中）

**判断：部分采纳，纠正一处事实。** 审阅说示例「只有约束摘要、计划摘要、版本和 `result=pass`」，这不准确：旧 design.md §4 的示例已有 `[mapping]` 表（含 `candidate_producers`），整份 `resources/` 也在 Workbook 目录摘要内；「计划或约束变更后重算、重新确认」也已写在 WG-07。

真正的冲突在别处：旧 WG-04 把「通过」和「无法结构判定」定义成互斥结果，示例却同时出现 `result = "pass"` 和非空 `unresolved`。示例也确实缺草稿装入摘要和用户确认记录。

**修改位置：**

- spec.md WG-04：改为「规则判定（通过 / 不通过）加未决清单」两个独立字段，并列出三种组合各自的处理与用语。
- design.md §4：示例改为 `rule_verdict` 加 `unresolved`，新增 `draft_load_digest`、`mapping_digest`，`candidate_producers` 改为 `not_candidate_producers`（与默认全选一致）；用户确认记录的格式留到第二阶段。
- design.md §7：第 6 问扩为「确认记录的格式与强度」。
- spec.md WG-06：锁定文件的内容同步。

## 审阅未列出的补充修订

- **确认到安装之间的窗口。** 仅在「安装前」重核摘要，仍留有重核之后、正式 add 之前被改动的窗口；本轮加入正式安装后的摘要比对（design.md §5 第 5、6 步）。
- **项目默认要求的存放位置属于输入闭包。** 旧 §7 第 1 问悬而未决，而放在仓库里会让执行 agent 能改约束，动摇「快照来自规划者之外」。本轮定为：第一阶段放在用户目录；放进仓库时只接受与仓库外记录的确认摘要一致的文件（spec.md WG-01、design.md §2）。这不是防篡改承诺。
- **终点集合 \(T\) 的定义。** 旧文写「采用 C004 时为接收点」，与 C004 现在把接收定义为合同节点受控放开的 `main` 边不一致，已改为终点节点。
