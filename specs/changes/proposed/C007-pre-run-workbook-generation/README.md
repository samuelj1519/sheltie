# C007：运行前生成 Workbook

状态：`proposed`
目标版本：`待定`（第一阶段不改产品代码；第二阶段视实验结果决定）
兼容性：`待定`（第一阶段无；第二阶段可能扩展 GF-17 的创建入口，候选 minor）
基线：`186ebd75d744fc2db83a72b715d36d05dd923883`
Owner：`待采用时指定`
权威性：未采用；不得据此修改产品代码、根规格或决定记录

## 范围约束

只处理**运行前**生成：Work 开始之前，由规划 agent 起草一份完整 Workbook，经过机器检查和用户确认后冻结，再按普通 Workbook 运行。

**运行中展开不在本 package 内。** Work 启动后、在授权范围内增加子流程，需要展开槽、继承规则和总预算，属于 GF-26，等真实任务显示“运行中无法确定工作结构”造成明显摩擦时再单独提出。

## 要解决的问题

1. 手写 Workbook 成本高：要写 Flow、节点、边、上限、输入输出合同和说明书。一次性的任务，用户往往不愿为它写一份 Workbook。
2. 让 agent 自己设计流程又有一个根本风险：**同一个 agent 既生成计划，又决定什么算完成**，就可能省掉检查点、放宽标准，让工作显得成功。
3. 只检查“有没有审查节点”不够：流程里有审查节点，也可能存在一条绕过它直达终点的路径。

## 首批用户

与 C004 相同：个人开发者的本地 Git 仓库，任务是一次性的代码库变更。

## 成功判据

采用前（第一阶段实验）：

- [validation.md](validation.md) 的 authoring 实验已执行：比较“生成 + 检查 + 确认”与手写 Workbook 的人工时间，同时报告质量；
- 结构检查的失败路径测试与用户价值分开报告（GF-19）。

采用后：

- 规划者只能依据一份来自规划者之外的**生效约束快照**生成流程，不能自己决定省略哪些检查点；
- 检查器按结构条件判定：每条接收路径都经过约束要求的检查与审查、必需门槛存在、上限有界、证据绑定被接收的候选；
- 通过检查的计划与约束版本、计划摘要一起冻结；之后修改计划或放宽约束都要重新确认；
- 结构检查通过只说明被检查的结构条件满足，不说明计划合理。

## 不做什么

- 不做运行中展开（GF-26）；
- 不另写一份“新章程”：约束直接复用 C004 的验收合同、C005 的执行绑定与自动执行政策；
- 规划者可以建议修改约束，但建议不会自动变成授权；
- 检查器不读说明书的自然语言下结论（INV-1、INV-2），不判断计划好坏；
- 不检查只能靠运行时累计的条件（例如多个分支、回环、重试合计后的总预算），也不检查“没有改变鉴权语义”这类只能靠实际验证或审查的要求；
- 第一阶段不新增临时启动入口：生成的 Workbook 走现有 `workbook add`，按普通版本安装。

## 采用条件

第一阶段（实验，不改产品代码）：

- 可以直接执行：规划者用 skill 起草，检查器用外部脚本实现，走现有 `workbook add`；
- 实验中的约束快照先手工整理；如果 C004、C005 尚未采用，用它们的候选字段作为格式参照，报告中注明。

第二阶段（产品化）：

- 第一阶段实验显示生成流程确实降低了用户的配置负担，且质量不下降；
- 人审定 [design.md](design.md) 的 ADR-E（检查器与约束快照的位置）；
- 如需临时启动入口，人决定 GF-17 的扩展。
