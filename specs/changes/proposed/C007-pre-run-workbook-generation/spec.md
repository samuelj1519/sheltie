# C007 产品 delta

状态：`proposed`，实验与实现均 `not_run`。基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。本文件是候选变化，不是当前产品合同；采用后再同步到根 `spec.md`、`roadmap.md` 与 `contracts/`。

## 1. 定位

**一句话（候选）：** 规划者提出结构，用户授权标准；结构检查只证明被检查的结构条件满足。

```text
用户目标 ─┐
          ├─▶ 规划者起草完整 Workbook ─▶ 检查器 ─▶ 用户确认 ─▶ 冻结 ─▶ workbook add ─▶ work start
生效约束快照（来自规划者之外）──────────────▲
```

根规格已经写明“AI 可以起草，人看过、改过、点头之后才算冻结”（spec.md §3）。C007 不改变这条原则，只补上三件事：规划者依据什么起草；机器能替用户核对什么；用户确认的是什么。

**与运行中展开分开：**

| 情况 | 什么时候决定结构 | 需要的机制 | 本 package |
| --- | --- | --- | --- |
| 运行前生成 | Work 开始之前 | 生成、检查、确认、冻结；运行中不改图（GF-03） | 是 |
| 运行中展开 | Work 执行中发现新任务 | 展开槽、继承检查点与上限、总预算 | 否，属于 GF-26 |

## 2. 首批场景

1. **一次性的代码库变更。** 用户说“给登录接口加速率限制”。规划者按项目默认要求（必须跑测试、合并前人工批准）起草一份四节点 Workbook；检查器确认每条到达终点的路径都经过测试与人工批准；用户看过差异后确认，安装并开始 Work。
2. **规划者想省掉一个检查点。** 规划者认为“这次改动很小，不需要审查”。它可以在差异说明里提出，但检查器仍按原约束判定为不通过；用户若同意，需要按约束自己的规则放宽，形成新的约束版本。
3. **审查节点可以被绕过。** 草案里有审查节点，但还有一条 `branch` 边从实现直达终点。检查器指出这条路径，判定为不通过。

## 3. 候选能力

编号 `WG-nn` 只在本 package 内使用；采用时再并入根规格的 GF 编号。

### 第一阶段：生成、检查、确认，走现有安装路径

`WG-01` **生效约束快照。** 规划者起草所依据的约束，由三部分合成：

| 部分 | 内容 | 来源 |
| --- | --- | --- |
| 部分 | 内容 | 来源 | 第一阶段（C004、C005 未采用时） |
| --- | --- | --- | --- |
| 项目默认要求 | 本项目每次都要满足的检查、审查、门槛和上限 | 用户维护 | 可用；只含现有 Workbook 能表达的门槛、图、上限与 `requires` 允许名单 |
| 本次确认的差异 | 用户为这次任务加严或放宽的条目 | 用户确认 | 可用，范围同上 |
| 执行政策限制 | 执行绑定允许的候选集合、自动执行政策、费用与数据边界 | C005 EX-08、EX-14 | 只作实验记录，不参与判定，不称为运行时授权 |

采用 C004、C005 后，验收条件的写法直接使用 C004 的验收合同（VD-01、VD-02），执行政策直接使用 C005 的执行绑定，不另立一份含义相近的新合同。未采用时，这些候选字段只作格式参照和实验记录，检查器不据此判定，报告中注明。快照有版本和摘要；**它必须来自规划者之外**，规划者只能读取，不能写入。

项目默认要求放在规划者与执行者写入范围之外（第一阶段放在用户目录，design.md §2）；若为了共享放进仓库，检查器只接受与用户上次确认摘要一致的文件，摘要记录在仓库之外，不一致时要求重新确认。同一 OS 用户下的 agent 仍能改写用户目录，这只是把约束移出正常工作范围，不是防篡改承诺。

`WG-02` **规划者的输入与输出。** 规划者读取任务目标、约束快照和编写规范（示例加规则，以 skill 或参考材料提供，GF-18），输出两样东西：

- 一份完整的 Workbook 草稿目录，符合 `workbook/v1`；
- 一份**约束映射**：约束快照中的每一项检查、审查和门槛，分别由哪些节点承担；候选生产节点集合 \(P\) 的显式排除清单（见下）；以及一份差异说明，列出规划者建议修改的约束条目。

**候选生产节点默认全选。** 除门槛节点和终点节点外，每个节点默认都算“可能产生新候选”的节点；规划者要把某个节点排除出 \(P\)，必须在映射中逐个列出，由用户确认。这样漏标就变成一条可见的排除声明，而不是一处看不见的遗漏。终点节点若实际会改动候选，属于映射错误，检查器发现不了，由用户确认或运行证据暴露。

规划者的建议不会自动成为授权（WG-06）。

`WG-03` **结构检查。** 检查器读取草稿、约束快照和约束映射，只按下列闭集规则判定：

| 规则 | 检查什么 |
| --- | --- |
| 可装入 | 草稿通过 `workbook add` 的全部装入校验（GF-03、GF-16），不执行脚本、不调模型、不联网。检查在隔离的临时 `SHELTIE_HOME` 中进行，不在正式管理根留下任何状态（design.md §5） |
| 映射完整 | 约束快照里的每一项必需检查、审查和门槛，都映射到至少一个节点；映射引用的节点存在 |
| 路径覆盖 | 每一条从入口到终点的路径，都经过每一项必需条件映射的节点；不只检查“图里有这个节点” |
| 候选之后 | 每一项必需条件映射的节点，位于同一路径上最后一个产生新候选的节点之后；返工回环后必须重新经过。产生新候选的节点按 WG-02 的默认全选、显式排除确定 |
| 门槛存在 | 约束要求人工批准的位置，映射的节点声明了 `gate = true`，并满足路径覆盖 |
| 上限有界 | 每个节点声明的 `max_visits`、`max_retries` 不超过约束给出的上限；由此推出的尝试次数上界不超过约束的总次数上限 |
| 不越权 | 第一阶段：Workbook 的 `requires` 落在约束快照给出的允许名单内。采用 C005 后：宿主资源与执行要求落在执行绑定允许的集合内；Workbook 不包含扩大自动执行政策的内容 |
| 证据绑定（依赖 C004 采用） | 约束中每一项 `machine_check` 与 `review` 条件，都对应映射节点上 C004 验收合同的一个条件 id；未采用 C004 时本规则不适用，报告中注明。检查器只核对合同声明存在，证据是否绑定被接收的候选由 C004 VD-06 在运行时判定 |

第一阶段可用的规则子集：可装入、映射完整、路径覆盖、候选之后、门槛存在、上限有界，以及只核 `requires` 名单的不越权。其余候选字段只作实验记录。

检查器的结论只对它收到的约束映射与 \(P\) 成立。映射到一个什么也不做的空壳节点、或把真正产生候选的节点排除出 \(P\)，图结构本身可以完全合规，检查仍会通过；这类错误靠用户确认发现，采用 C004 后可由运行时缺证据暴露，不计为检查器已拦截（WG-05）。

`WG-04` **检查结果：规则判定加未决清单。** 两者是独立字段，不合并成一个结果。

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| 规则判定 | 通过 / 不通过 | 上表中适用的每条规则是否都满足；不通过时列出规则、节点与路径 |
| 未决清单 | 零到多条 | 约束中结构检查表达不了的条目，逐条标为“需运行时控制”或“需人判断” |

| 组合 | 处理 | 可以怎样描述 |
| --- | --- | --- |
| 规则判定不通过 | 规划者修改草稿，或用户修改约束 | 不通过 |
| 通过，未决清单为空 | 进入用户确认 | 所有可检查规则通过 |
| 通过，未决清单非空 | 进入用户确认，未决条目逐条展示 | 所有可检查规则通过，另有未决条目；不能说整份约束已满足 |

未决清单（“无法结构判定”）的典型例子：多个分支、回环、重试合计后的总 token 或费用预算（需要运行时累计）；“没有改变鉴权语义”“兼容所有现有客户端”（需要实际验证或审查证据）。

`WG-05` **用户确认。** 用户看到的是：计划摘要、约束映射（含 \(P\) 的显式排除清单）、规划者的差异说明、规则判定和完整的未决清单。

**约束映射本身是用户确认的内容。** 引擎不知道哪个节点是审查（spec.md §3），检查器也只能核对映射在图上的覆盖，不能判断被映射的节点是否真的在做审查，也不能判断被排除出 \(P\) 的节点是否真的不改候选。采用 C004 时，接收点要求对应的证据记录，映射错了会在运行时表现为缺证据；未采用 C004 时，映射只是规划者的声明，由用户确认。

`WG-06` **冻结与绑定。** 用户确认后，约束快照版本、快照摘要、约束映射、规则判定、未决清单和草稿的装入摘要写进 Workbook 目录中的一份锁定文件，然后按普通版本 `workbook add`。Workbook 的目录摘要（storage.md）因此同时覆盖计划与它所依据的约束版本。

锁定文件由检查器生成，不由规划者写。安装前检查器重新计算计划与约束摘要，并在临时 `SHELTIE_HOME` 中装入最终目录；任一不一致时检查器报告不一致，由用户停止安装。正式 `workbook add` 返回的 `digest` 须与临时装入得到的摘要相同，否则检查器报告安装的不是确认过的字节（design.md §5）。第一阶段检查器拦不住用户或 agent 直接 `workbook add`，这些核对只是流程约定。节点也可以把锁定文件作为输入绑定，让工作 agent 看到本次的标准。

`WG-07` **修改与放宽。**

- 修改计划：升 Workbook 版本，重新检查、重新确认；
- 放宽约束：按约束自身的规则进行（C004 的验收合同修改、C005 的新授权版本），形成新的约束快照版本；不能借规划者的差异说明直接生效；
- 已开始的 Work 不受影响：它持有开始时的 Workbook 副本（GF-17）。

`WG-08` **生成的 Workbook 是普通 Workbook。** 引擎不区分它是手写的还是生成的，不为它设特殊状态；它与手写 Workbook 走同一套装入校验。

### 第二阶段：视实验结果决定

`WG-09` **临时启动入口。** 不装入全局 Workbook 库，直接从一份通过检查、已确认的目录创建 Work。它必须与 `workbook add` 共用校验与冻结逻辑，不能成为绕过检查的入口。需要扩展 GF-17。

`WG-10` **检查器产品化。** 检查器作为引擎之外的独立组件随 Sheltie 发布（design.md ADR-E）。它不进入 `sheltie-core`，引擎代码里不出现“审查”“测试”等业务词汇（GF-01）。

## 4. 承诺合同

| 承诺 | 信任前提与机制 | 强度 | 建议 |
| --- | --- | --- | --- |
| 规划者不能自己省略必需的检查点 | 约束快照来自规划者之外；检查器按路径覆盖判定（WG-01、WG-03）；只对用户确认的映射与 \(P\) 成立 | 第一阶段：流程约定，可被跳过；第二阶段：只有定义可信签发来源与 `work start` 核对合同后，才能说正常接口拒绝未经检查的计划 | 第一阶段实验验证 |
| 映射与 \(P\) 忠实反映计划 | 用户确认；采用 C004 后运行时缺证据可暴露部分映射错误 | 不承诺；空壳映射与 \(P\) 漏排由用户发现 | 如实声明，实验单独报告 |
| 被映射的节点真的在做审查或检查 | 引擎与检查器都判断不了；采用 C004 时由接收点要求证据 | 不承诺；C004 下缺证据会阻止接收 | 如实声明 |
| 计划与约束版本绑定，事后无法悄悄替换 | 锁定文件进入 Workbook 目录摘要；已装版本只读（GF-17）；正式安装后核对摘要 | 同权限程序仍可改管理根；`workbook verify` 可发现 | 第一阶段 |
| 锁定文件摘要一致表示用户授权或标准充分 | 摘要只证明字节一致 | 不承诺；用户授权的记录方式留待第二阶段 | 如实声明 |
| 结构检查通过表示计划合理 | 结构条件之外的问题检查不到 | 不承诺 | 对外用语明确 |
| 总预算不超限 | 需要运行时累计（GF-24） | 结构检查不承诺，列入未决清单 | 后续随 GF-24 |

## 5. 保证范围声明（对外用语候选）

第一阶段可以说：

- 经指定检查器处理、且用户确认映射的草稿，在已检查的结构规则上通过；
- 相对于你确认的约束映射，每一条到达终点的路径都经过映射的检查节点，图上不存在绕过这些节点的路径；
- 检查器查不了的要求会被逐条列出，不会被默默当作满足。

第二阶段只有在可信签发来源与 `work start` 核对合同定稿并实现后，才可以说“未经检查和确认的生成计划不能通过正常接口开始”。

任何阶段都不能说：

- 生成的流程在内容上满足你的检查、审查和门槛要求；第一阶段还不能说规划 agent 或用户无法跳过检查器；
- 被映射的节点真的在做审查，或被排除的节点真的不产生候选；
- 锁定文件摘要一致就说明用户授权过或标准充分；
- 检查通过就说明计划合理，或任务一定能完成；
- 结构检查能保证总费用或总 token 不超预算；
- 生成的流程运行中可以按需扩展（这是 GF-26）。

## 7. 后续决策与触发条件

| 方向 | 触发条件 | 已知约束 |
| --- | --- | --- |
| 临时启动入口（WG-09） | 第一阶段实验显示 `workbook add` 的版本管理造成明显摩擦 | 共用校验与冻结；不能绕过检查 |
| 运行中展开（GF-26） | 真实任务显示“运行前无法确定工作结构”造成明显摩擦 | 展开出的子流程继承检查点与上限；总预算需要运行时累计 |
| 按效果调整脚手架 | 同类任务积累了足够的质量与成本数据 | 固定的是授权与交付要求；拆分粒度、审查频率可以按效果调整 |
