# C007 产品 delta

状态：`proposed`，实验与实现均 `not_run`。基准：`186ebd75d744fc2db83a72b715d36d05dd923883`。本文件是候选变化，不是当前产品合同；采用后再同步到根 `spec.md`、`roadmap.md` 与 `contracts/`。

## 1. 定位

**一句话（候选）：** 规划者提出结构，用户授权标准；结构检查只证明被检查的结构条件满足。

```text
用户目标 ─┐
          ├─▶ 规划者起草完整 Workbook ─▶ 检查器 ─▶ 用户确认 ─▶ 冻结 ─▶ workbook add ─▶ work start
生效约束快照（来自规划者之外）──────────────▲
```

根规格已经写明“AI 可以起草，人看过、改过、点头之后才算冻结”（spec.md §3）。C007 不改变这条原则，只补上三件事：规划者依据什么起草；机器能替用户核对什么；用户确认的是什么。

**与运行中展开分开：**

| 情况 | 什么时候决定结构 | 需要的机制 | 本 package |
| --- | --- | --- | --- |
| 运行前生成 | Work 开始之前 | 生成、检查、确认、冻结；运行中不改图（GF-03） | 是 |
| 运行中展开 | Work 执行中发现新任务 | 展开槽、继承检查点与上限、总预算 | 否，属于 GF-26 |

## 2. 首批场景

1. **一次性的代码库变更。** 用户说“给登录接口加速率限制”。规划者按项目默认要求（必须跑测试、合并前人工批准）起草一份四节点 Workbook；检查器确认每条到达终点的路径都经过测试与人工批准；用户看过差异后确认，安装并开始 Work。
2. **规划者想省掉一个检查点。** 规划者认为“这次改动很小，不需要审查”。它可以在差异说明里提出，但检查器仍按原约束判定为不通过；用户若同意，需要按约束自己的规则放宽，形成新的约束版本。
3. **审查节点可以被绕过。** 草案里有审查节点，但还有一条 `branch` 边从实现直达终点。检查器指出这条路径，判定为不通过。

## 3. 候选能力

编号 `WG-nn` 只在本 package 内使用；采用时再并入根规格的 GF 编号。

### 第一阶段：生成、检查、确认，走现有安装路径

`WG-01` **生效约束快照。** 规划者起草所依据的约束，由三部分合成：

| 部分 | 内容 | 来源 |
| --- | --- | --- |
| 项目默认要求 | 本项目每次都要满足的检查、审查、门槛和上限 | 用户维护 |
| 本次确认的差异 | 用户为这次任务加严或放宽的条目 | 用户确认 |
| 执行政策限制 | 执行绑定允许的候选集合、自动执行政策、费用与数据边界 | C005 EX-08、EX-14 |

验收条件的写法直接使用 C004 的验收合同（VD-01、VD-02），执行政策直接使用 C005 的执行绑定，不另立一份含义相近的新合同。快照有版本和摘要；**它必须来自规划者之外**，规划者只能读取，不能写入。

`WG-02` **规划者的输入与输出。** 规划者读取任务目标、约束快照和编写规范（示例加规则，以 skill 或参考材料提供，GF-18），输出两样东西：

- 一份完整的 Workbook 草稿目录，符合 `workbook/v1`；
- 一份**约束映射**：约束快照中的每一项检查、审查和门槛，分别由哪些节点承担；以及一份差异说明，列出规划者建议修改的约束条目。

规划者的建议不会自动成为授权（WG-06）。

`WG-03` **结构检查。** 检查器读取草稿、约束快照和约束映射，只按下列闭集规则判定：

| 规则 | 检查什么 |
| --- | --- |
| 可装入 | 草稿通过 `workbook add` 的全部装入校验（GF-03、GF-16），不执行脚本、不调模型、不联网 |
| 映射完整 | 约束快照里的每一项必需检查、审查和门槛，都映射到至少一个节点；映射引用的节点存在 |
| 路径覆盖 | 每一条从入口到终点的路径，都经过每一项必需条件映射的节点；不只检查“图里有这个节点” |
| 候选之后 | 每一项必需条件映射的节点，位于同一路径上最后一个产生新候选的节点之后；返工回环后必须重新经过 |
| 门槛存在 | 约束要求人工批准的位置，映射的节点声明了 `gate = true`，并满足路径覆盖 |
| 上限有界 | 每个节点声明的 `max_visits`、`max_retries` 不超过约束给出的上限；由此推出的尝试次数上界不超过约束的总次数上限 |
| 不越权 | Workbook 声明的宿主资源与执行要求落在执行绑定允许的集合内；Workbook 不包含扩大自动执行政策的内容 |

`WG-04` **三种检查结果。**

| 结果 | 含义 | 处理 |
| --- | --- | --- |
| 通过 | 上表的每条规则都满足 | 进入用户确认 |
| 不通过 | 至少一条规则不满足，列出规则、节点与路径 | 规划者修改草稿，或用户修改约束 |
| 无法结构判定 | 约束中有结构检查表达不了的要求 | 逐条列出，标为“需运行时控制”或“需人判断”；不当作通过 |

“无法结构判定”的典型例子：多个分支、回环、重试合计后的总 token 或费用预算（需要运行时累计）；“没有改变鉴权语义”“兼容所有现有客户端”（需要实际验证或审查证据）。

`WG-05` **用户确认。** 用户看到的是：计划摘要、约束映射、规划者的差异说明、检查结果（含全部“无法结构判定”的条目）。

**约束映射本身是用户确认的内容。** 引擎不知道哪个节点是审查（spec.md §3），检查器也只能核对映射在图上的覆盖，不能判断被映射的节点是否真的在做审查。采用 C004 时，接收点要求对应的证据记录，映射错了会在运行时表现为缺证据；未采用 C004 时，映射只是规划者的声明，由用户确认。

`WG-06` **冻结与绑定。** 用户确认后，约束快照版本、快照摘要和检查结果写进 Workbook 目录中的一份锁定文件，然后按普通版本 `workbook add`。Workbook 的目录摘要（storage.md）因此同时覆盖计划与它所依据的约束版本。

锁定文件由检查器生成，不由规划者写；安装前检查器重新计算，内容不一致就拒绝继续。节点也可以把锁定文件作为输入绑定，让工作 agent 看到本次的标准。

`WG-07` **修改与放宽。**

- 修改计划：升 Workbook 版本，重新检查、重新确认；
- 放宽约束：按约束自身的规则进行（C004 的验收合同修改、C005 的新授权版本），形成新的约束快照版本；不能借规划者的差异说明直接生效；
- 已开始的 Work 不受影响：它持有开始时的 Workbook 副本（GF-17）。

`WG-08` **生成的 Workbook 是普通 Workbook。** 引擎不区分它是手写的还是生成的，不为它设特殊状态；它与手写 Workbook 走同一套装入校验。

### 第二阶段：视实验结果决定

`WG-09` **临时启动入口。** 不装入全局 Workbook 库，直接从一份通过检查、已确认的目录创建 Work。它必须与 `workbook add` 共用校验与冻结逻辑，不能成为绕过检查的入口。需要扩展 GF-17。

`WG-10` **检查器产品化。** 检查器作为引擎之外的独立组件随 Sheltie 发布（design.md ADR-E）。它不进入 `sheltie-core`，引擎代码里不出现“审查”“测试”等业务词汇（GF-01）。

## 4. 承诺合同

| 承诺 | 信任前提与机制 | 强度 | 建议 |
| --- | --- | --- | --- |
| 规划者不能自己省略必需的检查点 | 约束快照来自规划者之外；检查器按路径覆盖判定（WG-01、WG-03） | 流程约定（第一阶段）；正常接口会拒绝（第二阶段，前提是走检查器） | 第一阶段实验验证 |
| 被映射的节点真的在做审查或检查 | 引擎与检查器都判断不了；采用 C004 时由接收点要求证据 | 不承诺；C004 下缺证据会阻止接收 | 如实声明 |
| 计划与约束版本绑定，事后无法悄悄替换 | 锁定文件进入 Workbook 目录摘要；已装版本只读（GF-17） | 同权限程序仍可改管理根；`workbook verify` 可发现 | 第一阶段 |
| 结构检查通过表示计划合理 | 结构条件之外的问题检查不到 | 不承诺 | 对外用语明确 |
| 总预算不超限 | 需要运行时累计（GF-24） | 结构检查不承诺，列为“无法结构判定” | 后续随 GF-24 |

## 5. 保证范围声明（对外用语候选）

可以说：

- 生成的流程必须满足你事先确认的检查、审查和门槛要求；规划 agent 不能自己删掉它们；
- 每一条到达终点的路径都经过必需的检查，不存在绕过检查的捷径；
- 检查器查不了的要求会被逐条列出，不会被默默当作满足。

不能说：

- 检查通过就说明计划合理，或任务一定能完成；
- Sheltie 能判断某个节点是否真的在做审查；
- 结构检查能保证总费用或总 token 不超预算；
- 生成的流程运行中可以按需扩展（这是 GF-26）。

## 7. 后续决策与触发条件

| 方向 | 触发条件 | 已知约束 |
| --- | --- | --- |
| 临时启动入口（WG-09） | 第一阶段实验显示 `workbook add` 的版本管理造成明显摩擦 | 共用校验与冻结；不能绕过检查 |

| 按效果调整脚手架 | 同类任务积累了足够的质量与成本数据 | 固定的是授权与交付要求；拆分粒度、审查频率可以按效果调整 |
