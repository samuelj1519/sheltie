## 读什么

先看任务书开头的「来自」一行：

| 来自 | 修什么 |
| --- | --- |
| `verify` | `verify_report` 里的发现 |
| `review` | `review_report` 里的发现 |
| `escalate` | 读 `escalation` 的意见与授权，再修它针对的那份报告里的发现（备注里会说是验证还是审查） |

来自别处的那份报告可能过期，忽略。

然后读：

1. 按上表确定的报告。「发现」一节每条就是一个待修项。报告里的 `修复轮次: N` 记下来，你这轮写 `N + 1`；来自 `escalate` 时轮次重新从 1 算。报告里的 `基线: <哈希>` 是这个任务的任务基线，原样抄进你的 `change.md`；针对审查报告时写方案「基线」的原始基线。
2. `tasks`、`plan`、`scaffold`：只在需要理解上下文时查对应任务、「门禁」一节与单任务测试命令。
3. `project`：项目根目录。进入这个目录。

## 保留累计交接

修复报告决定本轮要改什么；累计已验证事实仍从 verify_report 或当前 plan 的继承表取得，即使本轮针对的是 review_report。记录整体原始基线与实际继承来源，核前缀一致后原样复制到 change。不能删掉已有任务行，也不能把本轮修复候选追加为已验证；由后续独立 verify 追加。字段或来源缺失时停止并说明缺口。

修复针对的 change 或 verify_report 有人工审批更正时，原样携带 `审批更正来源`（verify_report 中为实际 `审批来源`）及 `原审批来源` 到本轮 change；不因当前 escalation 不同而丢失更正。缺引用时停止。

## 怎么做

1. `git status` 确认工作区干净。
2. 逐条修「发现」里的问题。每条修完，如果有对应的测试就跑它。
3. 一条发现如果你认为不该修（比如它其实是正确行为），不要改代码，在「备注」里写明理由。验证者或审查者会再看。
4. 发现要求「改测试」或「改签名」时，不改，按卡住处理。测试与签名只有骨架步骤和人能改。
5. 运行「门禁」全部命令，修到全过。
6. 一次提交。格式见 `rules` 末尾「提交信息」，`type` 用 `fix`；`Task` 取报告针对的任务编号，审查报告没有任务编号时写 `Task: review`。

## 什么时候算卡住

和实现那一步一样：缺只有人知道的信息、需要人授权的高风险动作、环境坏了。另外一种：报告里的发现你看不懂，或者互相矛盾。卡住就恢复工作区、不提交、写报告。

## 写到哪

写 `change.md` 到 `change` 对应路径。**第一行只写 `修复完成` 或 `卡住`**，然后：

```
针对: 验证报告 | 审查报告
任务: T<编号> | review
基线: <任务基线哈希，原样抄；卡住时写 无>
提交: <哈希，卡住时写 无>
原始基线: <plan的整体原始基线，永不重设>
继承来源: <最新验证报告或当前方案的实际路径>
修复轮次: <N + 1>
改动文件:
- ...
门禁:
- <命令>: 通过 | 失败
备注: 每条发现的处理：已修 / 未修加理由；卡住时写原因
```

元数据之后写「已验证任务」六列表，字段与 plan/report 相同，原样复制继承行。只保存证据引用，change 不超过 32768 字节。
