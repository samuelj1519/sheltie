### R01 · P1：持久路径可以逃出管理根

定位：`home.rs:114` 的 `Home::rel` 裸拼路径，`fsx.rs:162–179` 只检查词法前缀并跳过 `ParentDir`；`service.rs:456,648` 使用 state 里的目录。`effects.rs:72,115` 只 serde 解码效果后执行。

反例一仅改合法 state 的 `work_dir` 为 `home/../outside`，外部放置匹配冻结副本作对照；真实 status/cancel 均成功，外部状态卡哨兵被覆盖。Standards 首个效果探针在临时库构造了待恢复 WriteFile；主审又补配对控制：使用真实已登记 begin 效果，模拟尚未标完成，只改变其中一个 `write_file.path` 为 `../<外部临时目录>/payload.md`。合法路径恢复不写根外；改单一路径后真实 cancel 恢复创建根外文件，字节摘要与登记相同。违反 INV-3、GF-32、storage §3.2/§3.3 与 T04/T07 的持久路径归属要求。这里是损坏持久数据的准确拒绝能力，不是在声称防御同账户所有恶意操作。

Owner：runtime 文件边界、Store/load、effects。先校验相对路径与 Home/WorkId 的对象身份，再执行；非法数据报 `STORE_CORRUPT` 且哨兵字节、权限不变。core 继续纯校验，不引入 I/O。证据：[state-path-results.jsonl](evidence/m1-2026-09-28/spec/state-path-results.jsonl)、[effects_path_probe.json](evidence/m1-2026-09-28/standards/effects_path_probe.json)、[extra-controls.stdout](evidence/m1-2026-09-28/extra-controls.stdout)。

### R02 · P1：封存离开已观察句柄，chmod 另一对象

定位：`fsx.rs:152–154`、真实 caller `effects.rs:155–165`。SafeFile 已打开并计算摘要后，原文件被 rename，原路径换为指向根外哨兵的软链。`set_readonly()` 返回成功，根外哨兵从 `0600` 变 `0444`，原观察文件仍 `0644`。现有 path-swap 测试只验读取，未验封存。

违反 storage §4 的“同一句柄”与 T04。Owner：fsx/observe/SealOutputs。使用句柄权限 API，贯通正常 submit 的观察与封存对象；恢复另核原引用。本机独立探针还确认只读 File 句柄可设置权限，代码注释所称 macOS 限制不能作为按路径 chmod 的理由。[Rust File 文档](https://doc.rust-lang.org/std/fs/struct.File.html#method.set_permissions) 提供该安全 API；[路径 set_permissions 文档](https://doc.rust-lang.org/std/fs/fn.set_permissions.html) 明确 Unix 跟随符号链接。证据：[safe_file_seal_probe.txt](evidence/m1-2026-09-28/standards/safe_file_seal_probe.txt)、[fchmod_read_handle.txt](evidence/m1-2026-09-28/standards/fchmod_read_handle.txt)。

### R05 · P1：重放仍依赖当前 @file

### R07 · P1：已提交错误的恢复协议不真实、不完整

定位：`service.rs:619–632,657–674,743–766`、`workbook_repo.rs:253–265`、`error_map.rs` 的 EffectPending 映射。

三个独立反例：begin COMMIT 后状态卡目标变为目录，返回普通 `IO`，但 requests 已存在且 revision=2；自己已提交 start 的发布原件被改，显式重放却报 `committed=false`、request_id 空串；旧 A 阻断新 B 时 B 的 request_id 也为空。已完成 begin 的父目录缺失则直接报 `STORE_CORRUPT`，未包成已提交 `EFFECT_PENDING`。正常 pending 重放能成功，为对照。

合同要求区分自己的已提交请求与阻断新请求的旧效果：自己的错误在顶层带 `committed/request_id/revision/original`；旧 A 阻断新 B 时顶层带 `committed=false/request_id=B`，detail 带 A 的 `pending_request_id/pending_original`。当前把提交标记和请求 id 塞进 detail，自己的原响应常为 `None`，原因也不是合同中的可识别错误码；不是单纯错误文案。Owner：统一请求恢复与 CLI 错误封装。证据：[probes.stdout](evidence/m1-2026-09-28/probes.stdout)、[probes.json](evidence/m1-2026-09-28/probes.json)；依据 storage §3.2、protocol §5。

### R11 · P1：删除结果不明被当成功，完成标记还共用一个名字

Owner：删除生命周期。使用真实 internal_id，验证归属、摘要与标记完整内容；两处都缺且无合法标记必须停止，保留原响应。依据 storage §3.2/§3.3/§5.2、M1 §4.2。证据：[probes.stdout](evidence/m1-2026-09-28/probes.stdout)、[probes.json](evidence/m1-2026-09-28/probes.json)。现有 `remove_writes_deleted_marker` 只看后缀与数量，不能证明关联正确。

### R18 · P1：发布持久化顺序不足

定位：`effects.rs:212–225` rename 前没有贯通原件及所需目录 sync，rename 后只 `fsync_dir(dst)`，未同步源/目标父目录；`fsx.rs:248–254` 还吞掉目录 sync 错误。之后能把 requests 标 published=1。

依据 storage §3.3 明确的源/目标父目录顺序，源码不能证明“标记完成即原件发布持久”。SQLite 的持久 COMMIT 不把外部 rename 纳入事务；[SQLite 原子提交文档](https://www.sqlite.org/atomiccommit.html) 与 [Rust sync_all 文档](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all) 支持这一区分。Owner：文件发布与 fsx；让必要 sync 的失败可传播，按合同完成再 mark。本轮未做断电/文件系统故障模拟，也未把进程 kill 等同断电验证；该缺口为静态机制确认。

### R19 · P2：真实 CLI 在取得管理根写锁前建库

定位：`commands/workbook.rs:45` 的 add 先 `Ctx::store(ReadWrite)`，`Store::open` 立即创建库；WorkbookRepo 后才 acquire_lock。attempt/gate/cancel 同样先开 RW Store。仓内并行 add 测试先串行建库，避开了这一窗口。
