# 整理完整交付

## 共有策略

读取本阶段指定的全部输入，按 `task` 的目标与验收、`project` 的仓库位置、初始候选、权限和检查规则工作。先核对正在操作的独立仓库副本与当前候选；输入不足、权限不符或候选无法对应时停止并记录，不补造任务标准。

只修改本次授权范围。遵守项目原有约定，使用已声明的模型、工具和本地检查；不安装宿主资源，不改宿主配置，不自动 push、merge 或发布。需要新增要求、扩大权限或改变固定方法时停止，交协调者处理，原记录保留。

每份报告第一行写明确结论。报告必须区分实际完成、失败、停止、未知和 `not_run`，指出具体文件、候选和原始证据。检查原件记录实际命令、工作目录、影响结果的环境、stdout、stderr、退出码及对应候选；零退出和自述通过不代替内容审查。未知 usage、费用或时间记为未知，不从 Attempt 统计推算。

把输出写到本阶段指定的目标路径。输入和已提交产物只读；不改旧报告或覆盖旧原件。新检查、重试和返工使用新记录，保留全部已投入成本。报告各不超过 262144 字节，patch 不超过 8388608 字节；达到限额、运行预算或固定次数上限时停止，不通过截掉必要事实或放宽边界取得成功。

阶段内可以合理拆解工作；不得增设额外流程节点。固定路径为 implement → review → deliver，review 可返工到 implement；implement、review 各最多访问 3 次，deliver 最多访问 1 次。每次到达最多失败重试 1 次。真实执行失败才记失败；审查建议返工仍是一次正常完成的审查。协调者依据报告选择下一阶段，执行者不自行判断引擎状态。

日常 review 与最终独立质量盲审是不同动作。deliver 默认不设门槛；流程外用户接受、独立质量审阅分别由真实参与者完成并计时。不得把 Work 成功、产物封存、门槛批准或命令退出 0 记成最终质量合格。

## 本阶段输入

读取 `task`、`change`、`checks`、`review`。从 `change` 取得候选、授权仓库、初始基线以及 `project` 预先声明的 patch 生成与独立应用检查方法；方法或位置缺失时停止，不临时选择另一套标准。

## 操作与输出

1. 核对全部输入指向同一最终候选，review 明确建议交付且未留阻断项，必需检查真实齐全。仓库当前候选与报告不同、检查失效或仍需改代码时停止，交协调者处理；本阶段不悄悄修改已审代码。
2. 按预先声明的项目方法生成 `change.patch`，完整覆盖相对初始基线的授权变更，包括需要交付的未跟踪文件、删除、重命名与必要二进制变更。核对实际文件集合与候选一致。单独 `git diff` 可能漏掉未跟踪文件；不得以一份缺文件的 diff 当完整 patch。
3. 在预先授权、与初始基线一致的独立检查副本，按已声明命令验证 patch 可应用及得到所述候选；不得在原仓库、宿主或另一组副本上试应用。保存实际命令、stdout、stderr、退出码和文件集合/内容核对原件。检查失败、缺授权副本、完整 patch 超过 8388608 字节或无法表达必要变更时停止，保留原因，不删掉必要文件取得成功。
4. 写 `delivery.md`：第一行为“交付材料已整理”或“停止”及原因；随后给任务、初始与最终候选、实际行为、完整 patch 和检查原件位置、实际应用验证、使用说明、已知限制及未完成项。说明哪些结论是执行者报告，哪些已由日常 review 核对。报告不超过 262144 字节。
5. 将两份必需输出交协调者。保留输入 `change`、`checks`、`review` 的原件与绑定身份；最终交付共包含这三份输入报告和本阶段 `delivery`、`patch` 两份输出。不把其他历史草稿或目录内容自动加入成果。

本方法默认没有 gate，不自动调用导出工具，不自动提交到外部服务。真实用户接受与实验独立质量盲审由流程外参与者依据最终代码、完整 patch 和真实原件分别执行并计时；材料整理完成不宣称两项已通过。
