# 任务执行与验证预算

用于工程任务的计划、实现、审查与验收。先确定要证明的行为，再选择验证范围和成本；复杂度按实际问题增加。强制门禁按[工程规范 §2.3](../engineering.md#23-命令)和 active plan 执行。本指南解释范围选择和证据复用；自动钩子复用尚未实现，不能将其视为可用功能。

## 1. 开工时固定交付和验证范围

在任务卡中记录以下内容，不额外建一套进度系统：

| 项目 | 必须回答的问题 |
| --- | --- |
| 交付 | 用户需要哪项可观察行为？哪些事本次不做？ |
| 依据与入口 | 对应合同、真实 caller、写入/恢复/失败停止路径是什么？ |
| 正反例 | 合法例和只改一个条件的拒绝例是什么？期望来自哪里？ |
| 检查 | 每条命令证明哪项义务？已经有可复用证据吗？ |
| 预算 | 预计条数、同范围基线耗时、并发、剩余时间范围是什么？ |
| 完成 | 必需项、明确例外、候选和 Reviewer 是否齐全？ |

普通文案、许可元数据和文档整理不默认扩为全产品审查。跨边界行为修复需要实际调用链证据，不能以编译或单元通过替代。新问题按影响和优先级进入对应任务；风格偏好、无近期消费者的抽象和额外性能实验不自动扩张当前验收。

## 2. 先用短反馈确认行为，再跑长验证

1. 用真实最小 caller 复现问题，写出精确失败信号。路径、字节、身份和状态使用独立期望，不让实现计算自己的答案。
2. 修复并跑受影响正反例，覆盖失败停止和恢复。接口变动同步全部真实消费者。
3. 在批量突变之前审查关键数据流：不可信输入在哪里变成可信对象，副作用何时开始，失败是否还会释放成功快照。
4. 修复反馈收敛后冻结候选。长验证运行期间不修改其输入；发现真缺陷时保留旧结果，先修复，再按依赖决定失效范围。
5. 完成受影响链后，按里程碑或发布要求运行整体门禁。结果满足任务卡就收尾；只有新变化、失败或未解决问题才追加检查。

对于未知缺陷，突变和专项验证仍有价值。重点是避免在已知缺陷未关闭、关键 oracle 未建立时反复启动完整流水线；不能用预算把必要但未完成的验证改为 PASS。

## 3. 按影响选择门禁

以下说明工程规范分层要求的适用方式，不按文件后缀直接判断风险。Cargo.toml 的许可字符串与依赖/feature 修改应分开判断。

| 变化 | 首选检查 | 整体验证触发条件 |
| --- | --- | --- |
| 文案、文档整理 | 链接、治理、保真与引用检查 | 文档参与测试、生成或业务输入时验证对应消费者 |
| 仅许可元数据 | Cargo metadata、包文件/正文、依赖许可策略 | 依赖、构建、发布配置同时改变时扩展 |
| 局部实现修复 | 格式/编译/lint、受影响模块及真实 caller 正反例 | 影响范围不明、跨 crate 接口或里程碑 |
| 持久格式、协议、文件与恢复 | 完整受影响链、独立状态/字节 oracle、必要故障窗口 | 核心状态或公共约束改变时跑整体基线 |
| 里程碑候选 | 稳定输入上的整体门禁及合同闭环 | 输入变化导致对应结果失效时重验 |
| 全量突变、平台、发布 | 独立任务、范围、Owner、预算和原文 | 计划明确要求；不作为每次小修复的默认附加项 |

大文件 exact/+1、平台原生路径和实际进程故障验证应保留；把它们放在相关能力或整体候选验证中，不让不相关的每个变异都重复读取整棵大树。快速反馈优先用已有真实接口和较小输入，不为加速引入测试专用 public trait 或第二套生产配置。

## 4. 长任务先测吞吐，再扩大批次

先跑同配置基线和覆盖不同成本类型的少量样本，确认实际选中了非零测试、调用真实产物，构建和执行可以完成。记录总墙钟、完成条数、失败/超时和资源并发；不同测试范围的样本不能混用均值。

在配置相同且样本有代表性时，用 `已完成样本墙钟 / 样本条数 × 剩余条数` 估计剩余时间范围。该均值已经包含当前并发效果，不能再除以并发数。样本少、超时或负载波动时降低估计置信度，不作确定承诺。

建议出现连续同类超时、测试数为零、产物身份不符或耗时超过预计上界时，停止派发同类新批次，先分类：

- 真实失败：修实现或 oracle，再核影响范围。
- 真实挂起：最小化触发条件，保留超时原文，不把超时当 caught。
- 环境拥塞：降低 mutation jobs、Cargo build jobs、Nextest 线程的乘积，检查 I/O/内存压力；不是简单增加 timeout。
- 工具/输入错误：校 package/filter、feature、目标目录和二进制来源；baseline 必须有实际用例。

同一输入只保留一个负责执行的长任务入口。续接先核进程、锁、输入、阶段进度和原文，不重启第二条流水线；只管理自己启动且身份已核实的进程。预算超限只触发调整和报告，不授予豁免、不自动标完成。

## 5. 突变按真实 consumer 验证

先生成所需范围的完整 inventory，并将每个 ID 绑定 diff、影响能力、消费者和验证组。只测试变异 crate 会漏掉 CLI 消费者；所有 missed 一律全 workspace 则可能把不相关成本乘到每一项。

有已执行且有效的直接检测时记录其真实范围；有便宜、精确的当前 producer/consumer 等价或不适用证明时复用；其余按能力组选择实际 caller 和独立 oracle。影响无法划清的项才升级到全 workspace。过滤后要求非零测试；复杂参数先做一次基线，不能把零测试解释为通过。

按共享 oracle 和相同证明归并工作，每个精确 ID 仍有记录。人工只处理异常和不能自动归类的差异；证明成本高于一次明确检测时优先检测。不为每个存活体写镜像测试，也不因成本高就擅自缩短已要求的 inventory 或遗漏 ID。

受控观察副本与正式候选单独绑定；正式 Missed/Timeout 原标签不因补充检测改写。平台暂停、未执行、编译不可构建、静态等价和实际捕获分别报告。没有证据的项保留缺失，不能用覆盖模式或核算完整代替验证通过。

## 6. 同一输入不重复执行同一门禁

可复用记录至少包含输入闭包、实际命令、scope、退出码、测试数、run ID 和原文位置。闭包按检查的真实依赖确定：源码、生成物、fixture、锁文件、配置、工具链、features、profile、filter、相关环境；涉及 Git 历史、文档或外部输入的检查还须绑定这些依赖。Git SHA 相同不自动足够，只有文档变更也不自动使所有检查失效。

将“执行 / 复用”与 PASS 分开。受影响闭包变了就重验；无法证明相同则保守重验。提交钩子的自动复用只有经专门实现和验证后才可用。CI 按实际候选与环境另行验证，不能从本地记录直接推定 CI PASS。

此类钩子复用需后续小任务实现并验证：旧记录、失败记录、环境/feature/filter 改变和零测试必须拒绝；有效同闭包记录才接受。先做最小记录校验，不建分布式缓存、数据库或通用调度平台。

## 7. 审查和证据只做一次有效工作

审查范围跟随实际风险。完整产品、跨边界或里程碑审查才需要完整两轴；简单元数据和保真整理可由一个独立 Reviewer 核实际差异。修复后的增量复核只检查影响链，不再次审查未改变部分。已确认缺陷、验收阻断与非必要建议分别记录，完成必要项后收尾。

在 package 的常规 review/validation 中保留结论、候选、命令与缺失范围；一份结构化索引映射共享原文。完整原文压缩或固定归档，不在多个阶段目录复制同一数据、源码全文和巨大 JSON。删除前按字节核恢复能力，特别检查被 Git 忽略的日志。跨机器使用时必须保证归档引用/对象真实可获取；文本里的 hash 不是备份。

## 8. 后续落地顺序

1. 在新任务计划中先固定交付、影响、样例、预算和停止条件，不增加额外流程文件。
2. 按工程规范执行分层检查；若自动钩子复用确有收益，另定最小记录校验并核其真实消费者，不先建缓存平台。
3. 为确有瓶颈的测试分组，保留必要的真实重型用例；验证过滤不会丢消费者。
4. 在后续真实任务记录总墙钟、主动执行/等待、重复运行及原因、有效缺陷和遗留项，比较相似任务；没有数据就不宣称节省比例或彻底防止复发。

脚本和钩子的自动复用没有实现；强制门禁以工程规范为准。C002 的诊断、计时口径和具体证据见[执行效率复盘](../changes/completed/C002-v0.2.0-reliability/review.md#执行效率复盘)。
