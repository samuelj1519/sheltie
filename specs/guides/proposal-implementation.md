# 分阶段搭建与实现

供 C004–C008 的实施计划引用。读者具备项目技术栈的基础能力，但第一次接触 Sheltie。本文统一任务执行方式；产品范围、阶段与进度仍由各 package 定义。提案未采用时，只能准备方案和评估材料，不能自行开始计划中的代码或实验。

## 1. 阅读入口

1. 读根 `AGENTS.md`、[CONTEXT](../../CONTEXT.md)、[文档地图](../README.md)和 [change 索引](../changes/README.md)，确认当前权威和 active package。
2. 读 active package 的 README、spec、design，以及 plan 的总表和本任务卡。
3. 读[工程规范](../engineering.md)，再从任务卡的现有路径与符号追到调用者、存储、恢复和测试入口。不要求通读无关历史。
4. 核对工作区、任务依赖、阶段骨架提交和允许文件。其他人的未提交工作不属于本任务，不改、不回滚。

计划中的「拟新增」路径不是已存在的接口。骨架作者必须在对应阶段开始前创建并核实这些路径，再把实际符号、测试名和骨架提交写回任务卡。

## 2. 三种职责

| 职责 | Owner | 交付 |
| --- | --- | --- |
| 总体设计和阶段骨架 | 强模型或有相应经验的开发者 | 上游合同、接口、依赖方向、失败路径；本阶段可编译骨架、独立期望、夹具和真实调用测试 |
| 实现 | 简单模型或初级开发者 | 按定好的接口实现一个完整行为；启用本阶段对应测试并完成验证 |
| 里程碑审查 | 未参与被审设计和实现的强模型 | 按合同审查整条调用链、正反例与故障窗口；给出通过、需修改或阻断 |

总体设计先固定各阶段的接口和关键验收场景。详细骨架与测试按阶段交付，不能用一次性编写全部禁用测试代替真实闭环。每个阶段结束后再搭下一阶段骨架；已证明稳定的接口继续复用。

## 3. 骨架任务怎么完成

1. 核现有真实调用者和 package 合同；确定数据如何进入、何时产生副作用、如何提交、拒绝及恢复。
2. 写本阶段需要的类型、签名和文档注释。基础文件操作、子进程控制、夹具与 oracle 由骨架作者完整实现，不留给初级实现者猜。
3. 未实现函数用带所属实现任务的 `todo!("C004-T04")` 等占位。不得把生产调用接到尚未实现的路径；既有行为和测试保持可运行。
4. 新行为测试先写全，归属对应实现任务；暂用同任务的 `#[ignore]`。至少有合法例、只改一个条件的拒绝例，以及该行为必要的真实 caller。期望不调用被测实现计算。
5. 将当前阶段实现任务卡的「验收用例」改为「测试」，列出真实测试名；其他未搭骨架阶段保留「验收用例」说明。`check-tests.sh` 会要求 active plan 中每条「**测试。**」列出的名称已经存在。
6. 运行格式、编译、lint、既有测试和当前文档门禁；对未实现行为运行定向测试，记录有意义的红例。编译错误、环境错误和零测试不算红。
7. 记录骨架提交、允许文件、实际符号和测试归属，再交给实现者。混合源码在 files/test_files 中逐一列相同的具体文件路径，不用源码目录代替；拟新增文件也必须在交接时展开。核整个受影响调用链的 Cargo member manifest 和内联测试都在范围内。在自有临时副本中改一行测试，证明 check-task 拒绝，再恢复原字节；不改真实候选来试门禁。骨架任务本身不要求虚构一组所属测试来运行 `task.sh`。

新增 `// Task: C004-T04` 必须紧贴测试属性，不能用里程碑 ID 当测试归属。同一接口变化必须在一个任务中处理全部真实调用者，不能靠空实现或兼容层把编译凑绿。

## 4. 实现任务怎么完成

1. 确认依赖和本阶段骨架已完成。新行为先运行 `scripts/task.sh <task>`，核对非零测试和预定失败信号；纯文档、外部实验没有 Rust 所属测试时按任务卡运行实际 oracle。
2. 只实现本任务占位和明确允许的调用接线。逐个让红例变绿，不改签名、约束、测试断言、快照或依赖。
3. 补齐既定合法路径、拒绝路径和恢复路径。完整场景如果已经通过，就保留其通过结果，不人为制造全红；运行已有场景本身不是新的实施任务。
4. 跑任务卡命令和[工程规范 §2.3](../engineering.md#23-命令)的提交门禁。本文没有豁免现行强制检查；范围和复用建议见[验证预算](task-execution-efficiency.md)。
5. 写入本任务的输入闭包、实际命令、退出码、测试数与原文路径。plan 改为 `done` 后，核范围并提交。

填空任务检查必须显式指定本阶段骨架或最新独立测试修订的提交：

```bash
scripts/check-task.sh C004-T04 <骨架或测试修订的完整提交> --staged
scripts/check-task.sh C004-T04 <同一个完整提交>
```

当前工具不会自动选择 `c004-*` 阶段 tag，也不检查 proposed package；不能在提案阶段把这些命令记为任务验收 PASS。`plan.md` 与 `tasks.toml` 自动属于允许范围；其他进度、验证与审查文件必须在任务白名单中。

提交采用 `type(scope): 中文摘要` 和实际 `Change`、`Task`、`Agent` trailer。采用范围内的任务按 plan 提交；任务提交不等于发布、推送或合并授权。

## 5. 停止与修复

合同冲突、接口不足、必须新增依赖、不能在白名单内接通真实 caller、oracle 矛盾、预计副作用超出授权，均停止当前实现并交回骨架作者。记录已经观察到的失败，不把猜测写成系统事实。

骨架作者在同一 active package 新增修复任务，写明影响、文件和测试 Owner；同步 plan 与 tasks 后修复。签名、持久格式、测试期望改变必须独立复核。实现者不静默改 oracle，也不靠改回旧测试获得绿色。里程碑 Reviewer 可以提出补测要求，但不能审查自己随后编写的修复。

## 6. 每个里程碑审什么

每个 package 的 plan 指定实际范围。Reviewer 固定候选与输入闭包，检查：产品承诺、架构职责、数据来源、全部真实消费者、失败停止、提交与恢复、正反例、对外用语。已有测试通过不自动说明用户价值或平台可用。

先审关键语义并运行短反馈，再在稳定候选上执行计划要求的突变或长验证。突变按实际变化与消费者选择范围，不把全 workspace 重跑设为每个阶段的默认动作；范围无法证明时才扩大。每个实际执行的突变 ID 都要有原结果与处置，超时和未执行不记为捕获。复用必须证明输入闭包相同，不能仅比较 Git SHA。

里程碑和纯文档任务也显式传审查开始时的完整候选作为 check-task 基准，不能让早先骨架的快照更新被算成本次审查修改。每个里程碑只在本 package 的 `review.md` 增加一行结论与阻断项；完整命令和运行索引在 `validation.md`，交接在 `progress.md`。不另建逐阶段报告体系，不复制任务状态或日志全文。最后一个里程碑审完整闭环及用户实验，修复后只复核变化的影响链。

## 7. 方案与实验的完成边界

方案整理可以通过结构检查与独立文档审查；它不等于 package 已采用。实验任务报告真实样本、配置、首次与复用成本、质量及缺失，结果允许是不值得实施。实验完成不自动授权产品化；实现完成不自动授权发布。
