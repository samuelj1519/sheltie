# 按完整行为制定和实施方案

本指南供后续 change 使用。方案准备、方案采用、产品实施、实验和发布是不同动作；proposed package 可以被重写和审阅，但实际任务只在其采用范围内执行。当前进度只看 active package plan。

## 1. 从用户结果制定范围

1. 写清实际使用者、任务触发、现行做法、痛点、最终可接受成果。把已经观察到的证据和待验证假设分开。
2. 区分一次准备的方法与每次任务输入，分别计算作者、使用者、执行者和审阅者成本。方法作者与使用者可以同一人，不要求先有分发平台。
3. 对每个机制说明真实消费者和不可省略义务。明确的当前合同、可验证近期需求或真实摩擦均可立项；不必先发生事故，也不按能力编号凑齐功能。
4. 先固定质量标准、最大投入和停止条件，再选最小实验。允许结果是只改说明、暂不加能力或停止方向。
5. 将候选行为写在自己的 package；采用后再同步根规格、架构和合同。不把提案字段放进当前接口说明。

无兼容需求时只设计一套载荷和调用路径，不加迁移、双格式或长期兼容分支。已有真实数据与产物不自动删除或重写；采用新格式先按准确版本拒绝，保留原件。

## 2. 阅读和负责人

第一次接触项目时读 AGENTS/CONTEXT、specs 入口、active README/spec/design、plan 总表与本任务卡，再读工程规范和实际源码入口。确认工作区、采用范围、候选、依赖、允许文件和独立判定依据（oracle）。

实施默认面向首次接触项目、具备技术栈基础的初级开发者。总体契约、架构、格式、系统信任与独立 oracle 先由复杂模型或同等经验作者确定；简单模型或初级开发者按已冻结接口完成有界主体、接线或实验操作。复杂模型还须完整实现进程、句柄、同快照读取等高风险原语，不能只留下函数名。

每个任务指定一名实际 Owner，模型称谓表示需要的能力，不是产品依赖或宿主安装要求。独立复杂 Reviewer 未参与被审设计、原语、代码或 oracle。小实验由复杂作者一次准备完整方法/工具，初级执行者只运行；无需先搭空脚本让另一个模型填。

具备足够能力的负责人可以合并设计与实现，须在采用计划写理由并保留独立期望和阶段审查。不为降低模型档位把一个真实行为拆成过多交接，也不以减少任务数将架构决策留给初级实现者。

## 3. 阶段准备与交接

产品任务通常分成“架构/原语/测试就绪”和“完整行为/真实使用”两个阶段。每阶段的 M 任务由独立复杂模型审查，范围写入 plan；M1 的基础通过不等于公开功能或用户收益通过。实验 M1 核协议/方法/小工具和首次读者可操作性，M2 核真实执行、质量、成本与结论，不跑无关 Rust 门禁。

复杂作者在阶段开始前：

1. 固定本阶段实际接口、数据流、所有 caller、字段与错误；完成必须由经验承担的原语。接口耦合导致半编译时完整处理，不加入假成功或兼容路径。
2. 创建窄骨架、所有本阶段需要的真实测试、fixture 与独立期望。未完成主体可以有任务所属占位，必须不接正常命令入口。已有正确行为保持回归；不要求人为全红。
3. 将基础原语测试归准备任务并跑绿，新行为测试归实现任务暂 ignore，实际用 task.sh 跑出至少一个预定行为失败和必要真实 caller 失败。编译/环境/零测试或单凭占位 panic 不算行为红。
4. 将任务卡“验收用例”更新为真实测试名。混合源码在 files/test_files 登记同一个具体文件；新文件在交接前实际创建并核范围。准备任务可以改测试，简单实现任务 allow_test_changes=false。
5. 在 package 的 stage-1.md、runbook.md 或 plan 指定手册写实际命令、参数来源、工作目录、测试数/退出码/输出期望、允许改的主体、停止交回人、完整骨架/测试提交及原始证据。不能让初级执行者靠猜测补协议、审批或系统调用。
6. 交独立 M1 核准备闭包与可操作性。准备既有接口或测试后来改变时，重新固定修订提交和影响链复核；不能静默修改冻结 oracle。

实验不强制 Rust 占位或 ignore：复杂作者完整制作实际脚本与必要机制 tests，初级执行者只用已验证工具，不改 protocol/fixtures/oracle/source。正式运行前 M1 通过，不从夹具通过推出真实价值。

## 4. 任务卡必须足够实施

| 项 | 内容 |
| --- | --- |
| 结果 | 一个用户或真实调用者可以观察的完整行为 |
| 前提 | 采用理由、实际依赖、冻结输入和边界 |
| 入口 | 已存在文件/符号与拟新增位置；沿全部真实消费者定位 |
| 决定 | 字段、状态转换、失败与恢复、来源和副作用顺序 |
| 正反 oracle | 合法例、只改一个条件的拒绝例；期望独立于实现 |
| 范围 | 文件/测试 Owner；混合源码逐文件登记；接口变更包含所有消费者 |
| 验证 | 实际命令、所证义务、非零测试、预算和停止条件 |
| 交接 | 候选、真实输出、未完成义务、下一个可执行动作 |

拟新增路径不是可调用接口。尚未实现的测试以“验收用例”说明；复杂作者准备阶段创建真实测试，再在对应实现任务卡的 `**测试。**` 行写实际名称，手册链接同一清单。产品任务卡使用 `### Cnnn-Tnn` 标题；check-tests 从这个标题归属测试，不扫描手册里的名字。Python 实验不虚构 Rust 归属。目录白名单在采用开工时按真实消费者收窄，不能把必要调用者留到后续任务。

任务按完整行为划分，不按 core/runtime/CLI 分层交付。合同变化可先作独立设计任务，但不得把半接通的生产路径、假成功、占位或禁用测试暴露给用户。

## 5. 实施与检查

1. 核依赖与开工候选，先准备能区分正确/错误行为的真实最小 oracle。缺陷修复先复现；新功能先说明预期失败；已有正确场景无需人为造红。
2. 简单实现者只完成准备作者交出的主体和真实接线，运行并启用既定测试，不改签名、断言、快照、格式、依赖或政策。复杂作者可在明确修复任务中补必要测试，独立复核后重固定基准。Rust 测试的 Task 注释紧贴属性，不用里程碑 ID 归属。
3. 根据[工程规范](../../specs/engineering.md#23-命令)选择验证。纯记录用文档/治理检查；方法或 fixture 验证实际消费者；跨 crate、状态、协议和持久格式变化用完整工程门禁。
4. 若任务有 Rust 所属测试，运行 `scripts/task.sh <task>` 并确认非零实际执行；外部实验按任务卡跑真实 CLI/脚本 oracle，不虚构 Rust 测试。
5. 每个完整行为在 done 前由未参与该行为编写的 Reviewer 复核受影响语义、真实消费者和 oracle，先短反馈再长验证；简单记录按保真与计算范围复核。在本 package review 记结论，不额外建里程碑或重复整套门禁。保存候选、输入闭包、命令、退出码、测试数和原文路径；完成义务才更新 plan 为 done。一个任务一个提交；未授权的推送、合并、安装和发布不随任务完成发生。

简单实现任务显式传阶段骨架或最新独立测试修订完整提交；文档、准备和审查任务用本任务开工候选：

```bash
scripts/check-task.sh "$task_id" "$baseline_commit" --staged
scripts/check-task.sh "$task_id" "$baseline_commit"
```

调用前将 `task_id` 设为 active plan 的真实任务 ID，`baseline_commit` 设为阶段骨架或最新独立测试修订的完整提交。没有 active change 时不运行任务实施门禁，也不把历史任务 ID 用作当前任务。

准备/专门修复任务在 tasks 中写 allow_test_changes=true；冻结实现任务用 false。测试不能改成迁就实现的答案，合同/期望改变须说明并独立复核。Reviewer 的任务只写审查和证据，不代写修复。plan/tasks 自动允许，其他证据文件在任务白名单中明确列出。工具只检查 active package，提案静态检查不能称为 task 验收。

## 6. 停止、修复和工作区

合同冲突、来源不明、必要权限缺失、API 不足、不能接通真实 caller 或预算持续超出预估时停止相关动作。先缩小或修正问题，不默加兼容层、第二状态库或未经授权副作用。任务难度本身不是停止理由。

保留他人的修改和真实原件。工作区有未归属变更就核对或隔离工作；禁止以全工作区 checkout/reset/clean 作为通用退出步骤。只有能证明是本任务自己的临时资源才可按既定范围清理。

初级执行者发现接口/测试/权限不足时保存实际失败交复杂作者；不在停止时全工作区回滚。复杂作者在同一 active package 新增必要修复任务，分配 Owner、范围和 oracle，改 plan/tasks 后实施。Reviewer 复核影响链，不审查自己随后编写的修复，不要求逐项普通返工找用户批准。

## 7. 阶段与完整独立审查

每个 M 任务由未参与对应准备/原语/实现的复杂模型执行；同一独立 Reviewer 可负责多个阶段。每任务短审与里程碑对同闭包已完成的工作直接引用，只补阶段新增义务，不能要求重复全套检查。

稳定完整候选的独立里程碑覆盖产品承诺、INV、真实来源、状态与文件、全部消费者、失败/恢复、文本/JSON、方法使用和交付质量。关键语义先短反馈，长验证随后执行；没有输入变化不重审未受影响部分。

突变只针对采用要求和实际风险，在运行前固定 inventory、consumer、测试组、吞吐预算与停止条件。无法证明影响范围时扩大；未执行/timeout/暂停不记 caught。同闭包复用引用原 run ID，不仅比较 Git SHA。详细方法见[验证预算](validate-change.md)。

plan 保存进度，progress 保存交接，validation 保存共享原文索引，review 保存结论和阻断项。原始输出只保存一次，不建设逐阶段并行账本。

## 8. 完成边界

方案文档可通过独立审阅与结构检查，仍保持 proposed。实验只对真实样本及实际观测作结论；合成 fixture 只证明机制，agent 演练不证明真人首次使用。组合试用不自动分离证明每项能力的收益。

实施完成需要全部采用义务、真实候选和独立结论。条件未满足的可选方案继续留在 proposed。产品发布需要其自己的候选、验证和授权。
