# 架构与恢复原理

[English](architecture.md) | 简体中文

Sheltie 把容易重复且能机械核验的事情留给引擎：状态、显式边、冻结来源、门槛与上限。Workbook 说明业务方法，协调者判断内容并选路。这个边界让同一二进制可以运行写作、代码变更或其他方法。

## 为什么分为三层

CLI 将人的参数转成请求，并表达准确结果。runtime 负责文件、进程身份、数据库和真实观察。core 接收已观察事实，用纯函数决定状态、合法下一步与所需效果。依赖方向是 cli → runtime → core。

纯 core 使规则可以用手写状态与独立期望验证，无需临时数据库或 mock I/O。runtime 的真实测试核事务、文件身份、恢复与错误；CLI 测试核公开消费者，避免只证明内部 helper 正确。维护者可以沿[源码导读](source-tour.zh-CN.md)看完整调用链。

## 为什么数据库提交与文件发布分开

SQLite 能原子登记状态、请求响应和效果义务，无法把文件系统 rename 或权限修改放进同一个数据库事务。引擎先持久记录“已经提交什么、还要发布什么”，再执行登记的文件效果。

因此错误可能发生在提交之前，也可能发生在状态已提交之后。后者不能简单返回“什么都没发生”，否则协调者可能重做已发生的业务。恢复错误保留准确提交身份及 original；后续写操作先证明旧效果完成，再执行新决定。

重放返回原请求提交时的响应，当前查询返回新的读取快照。历史响应中的 next 可以已经过时，这正是接续要先查询 status 的原因。只读查询不承担发布和恢复。

## 为什么核对象，不能只核路径

路径在两次系统调用之间可能被替换；同一个 inode 的内容也可能改变。核路径字符串、核文件对象、核实际字节分别解决不同问题。受管目录句柄与同文件句柄读取把观察、摘要与动作尽可能绑定到同一对象；不能证明归属或完整性时停止。

Work 的方法副本与输入绑定同样按字节冻结，避免方法升级或同名文件变化悄悄影响运行。可编辑导出副本是另一份交付对象，它可以改变，但不反向成为 Work 的状态或结果来源。

## 为什么查询要用同一快照

状态和 next 若来自不同 revision，消费者可能拿新状态配旧资格。Store 的 read_work_bundle 与可信加载将状态、关联请求和效果放在一个读取上下文中；status、stats、result 从它投影，引用绑定到具体 Attempt。

最终成果查询只是列举明确选择；真正消费字节时还需同 revision、同 key 与受限句柄核验。参考见[数据模型](../reference/data-model.zh-CN.md)和[限制](../reference/limitations.zh-CN.md)。

## 为什么外围工具独立

导出器只需要公开成果与原字节，不需要接触 Store。作者工具只需要完整草稿、真实结构判定和新 ZIP，不需要推进 Work。小接口将权限与恢复义务限制在真实用途内，不让浏览器草稿或外部副本变成第二事实来源。

实现必须守住的规则见[架构约束](../../specs/architecture.zh-CN.md)，设计选择的正式理由见 [ADR](decisions/README.zh-CN.md)。
